## Quelmara v3.12 — HTTP 客户端接收两层 O(n²) → O(n)（性能）

用户要求"继续推进进度以及优化它的性能"。做法是**横向扫同类缺陷**：v3.09 在
`std/net` 修过 `out = out + part`，v3.12 就去 grep 整个 `std/` 找同一形状，结果
`std/httpc_net` 的接收循环原封不动留着，而且是**两层**：每轮 `buf = buf + part`
复制全部已收字节 + 每轮 `httpc_parse_response(buf)` 整段重解析；`_dechunk` 内部
还有第三层（逐块 `body + slice`）。探针实测 512KB 21ms → 1MB 70ms → 1.5MB 141ms
→ **2MB `heap_limit_mb exceeded`**。

改法：可扩容缓冲（几何扩容 + mem_copy）+ 头块只解析一次（`_RespHead`）+
增量 chunk 状态机（`_ck_feed`）+ 64MB 上限。2MB 28ms / 8MB 45ms，线性。
提交 `0c31a71`。主回归 PASS=326 → **327**（新增 t168）。

**两个踩坑（都很值钱）**：
1. **增量状态机第一版写错**：把 `pos` 当"下一个 size 行起点"，块数据没到齐时反复
   `return` 同一个 pos，于是每次续收都把已搬过的数据再搬一遍。7 字节的老用例
   `t92_httpc` 全绿看不出来，8KB 块（> 半个 16KB recv 缓冲）立刻错。**验证增量
   状态机要用跨 recv 边界的形状**，这是 v3.09「验证 O(n²) 要用最坏形状」的镜像。
2. **`_ck_feed` 传了句柄而不是数据指针**：`_bptr(rx)` 才是数据指针，`rx` 是
   {ptr,cap,len} 的 mem 块。症状是 chunked body 长度 0、complete=0（静默，不崩）。
   凡 `mem_*` 系列一律要指针，缓冲句柄只在 `_b*` 内部用。
3. 顺手：`HttpResponse { ... }` 在 `std/httpc_net` 里**编不过**——跨模块 struct
   字面量按设计不支持（`02-language.md` §1），得加 `httpc_make_response` 工厂。

**新发现（未做）**：`std/tls_net` 的 `tls_recv_exact`（第 40 行）与 `tls_connect`
（第 74 行）还有同一形状，但记录 ≤16KB、握手 ≤16 轮，代价可忽略，已登记 07-gaps §5。

## Quelmara v3.14 — 自旋等待被 LICM 编成死循环（编译器真 bug）

本轮本想做 §5 的 futex/WaitOnAddress，第一步跑 `bench/wg_bench.qma` 取基线时
**300 s 不返回**。编译器同时报了 `possible infinite loop in 'spin_wait'`。

最小复现：`while mem_load64(w,0) != 0 { spin_hint() }` 编出来是死循环。
IR 里 `load` 被提到循环头之前，循环里每轮比同一个旧值。

**根因**：`opt_licm` 的 `readonly` 判据是「循环里没有 call/store/atomic」，
而 `spin_hint()` 发射的 `('pause',)` 在 `vreg_mentions` 里读写集都是空
（`if op in ("mfence","pause"): return [], []`）。于是自旋循环被判成**纯读**，
`load` 被外提。**这条判据从原理上就是错的**：自旋等待的正确性恰恰来自
**别的线程**在写同一块内存，循环体自己当然不写。

**修复**：`readonly` 排除集加 `pause`/`yield`/`rdtsc`。没采用「循环里有 load
就不外提」——那会吐回 v2.60 起的收益（`a[i]` 的句柄/长度 load 外提是 b4_array /
b7_sort 的大头）。判据是"这个循环会不会让别的线程跑"。

**证据**：`tests/t169_spin_wait.qma` 对旧代码 15 s 不退出、新代码通过；
`bench/gbench` A/B 各 3 次，除 0.3 ms 的 nested（±20% 噪声区）外全部 ±3%。
主回归 PASS=331 → **332**。提交 `e885153`。

**顺带纠正**：`06-status` §3.5b 原来记纯自旋 CPU 51–82%，那是在对照组编错的
情况下测的（低得不合逻辑——自旋等待本就该吃满一个核）。实测 **101%**。

**最值钱的一条教训**：`check_suspicious_loops` 早就在报这条警，而且报得对，
但它是 `warning:`、从不影响退出码 → 被当成背景噪音。
**一条从不影响退出码的告警，迟早等于不存在。**
下次看到 "guard variable never updated in body" 先怀疑编译器，不要怀疑源码。

**futex 那条没做**，但现在基线是真的了（wg_bench 能跑出 202 ms / 0% CPU），
下一轮可以直接对比唤醒延迟。

## Quelmara v3.15 — WaitGroup 长等待改 WaitOnAddress park

`wg_wait` 第 3 段退避原来是 `sleep_ms(1)`（本机 15.6–25 ms 时钟片），长等待唤醒
要等一整个片。改用 KernelBase 的 `WaitOnAddress`（`@ffi` 支持显式 DLL 名，
**不用动 PE 导入表白名单**）。

**实测**（`build/probe_wake2.qma`，200 ms 忙等，交替各 7 次）：

| 实现 | median | max |
|---|---|---|
| 旧 sleep 片 | 1194 µs | 1824 µs |
| 新 park | **55 µs** | 74 µs |

中位 **21.7×**，CPU 仍归零。主回归 PASS=332 → **333**。提交 `ee05e07`。

**两段负结果（都值钱）**：

1. **`mutex_lock` 不能 park**：16 线程 × 20 万次加锁 **281 → 1568 ms（慢 5.6×）**，
   加「先 yield 1024 次」门槛后仍 855 ms。根因不是 park 慢，是**判据缺信息**——
   锁的临界区约 88 ns，每个线程等锁被切成很多几十 µs 的小段，
   「已经等多久」区分不了「马上就好」和「要等很久」。park 只对
   **等待时长 ≫ 系统调用开销、且只等一次**的场景有利（WaitGroup 是，锁不是）。

2. **省系统调用的 parked 计数会漏唤醒**：`wg_done` 读到 parked==0 跳过 Wake，
   而等待方可能刚好在「跨过退避门槛、还没登记」的窗口里 → 睡到 1000 ms 兜底
   超时（实测 lag ≈ 953 ms）。这个窗口**关不掉**（两次独立原子操作之间无序，
   Win32 没有把「减计数+检查+Wake」做成原子事务的原语）。改成无条件 Wake。

**探针也踩坑**：第一版让 worker `sleep_ms(ms)` 再算 `wall - ms`，测出 park
"慢 2 倍"——真因是 **Windows 的 15.6 ms sleep 粒度把 µs 级延迟整个淹掉了**。
改成 worker 忙等到精确时刻 + 记 `wg_done` 前的 `now_ns` 才量到真值。
**测 µs 级的东西，夹具里不能出现 ms 级定时器。**

**注意**：`std/sync` 现在含 `@ffi`，在非 PE 后端是**声明期硬失败** —— 之前它只用
内建、能在 native 编译，现在不能了。已登记 `07-gaps.md` §4。
Linux 侧要恢复得先做 `futex(FUTEX_WAIT/WAKE)`。

## Quelmara v3.18 — 用户可调的 `syscall` 内建

v3.17 查 Linux futex 时发现三堵墙，第一堵是「`syscall` 只是编译器内部的发射指令，
用户发不了系统调用」。本版补上内建 `syscall(n, a0..a5) -> int`。

**语义**：调用号必须**编译期常量**（内核在 `rax`/`x8` 读它，笔误要在编译期抓）；
最多 6 个实参不足补 0；返回内核**原样**返回值，**负值即 `-errno`**，
不置 errno 不抛异常；**仅 Linux**，Windows 编译期 fail-fast（诊断直接指向 `@ffi`）。

**执行级验证** `tests/t171_syscall.qma` 接进 **CI linux job 的 `[7]` 段**：
`getpid` / `write` / 非法编号返回 `-ENOSYS`。x86-64 直跑 `syscall ok`，
AArch64 走模拟器 `syscall ok`。**主回归跑不了它**（Windows 上 fail-fast）。

**顺带修 `tests/a64_emu.py`**（这条值得记）：未实现的调用号原来
`raise RuntimeError`，两个问题 ——
① 与内核语义不符（内核返回 `-ENOSYS`），`t171` 的 `[3]` 组会假红；
② **同一编号在不同架构上是不同调用**（`202` 在 x86-64 是 `futex`、
在 AArch64 是 `accept`），按 x86 编号写的探针撞进来时，抛异常会让人
误判成模拟器缺陷。改成一律返回 `-ENOSYS`。另补 `getpid(172)` / `brk(214)`。

**边界（重要）**：编号**架构相关**而语言**没有条件编译** ——
同一份源码没法自动选对编号，只能"两个常量都写、按返回值符号选"。
这是 `syscall` 最实际的限制，要根治得做条件编译。**futex 本身仍未做**，
本版只补地基。提交 `27c83ad`。

## Quelmara v3.19 — target_os/target_arch 编译期探测 + Linux futex park

v3.18 补了 `syscall` 后，Linux futex 只剩「编号架构相关」一条障碍。
新增两个**编译期常量**内建：

```quelmara
target_os()   -> 1 = Linux / 2 = Windows
target_arch() -> 1 = x86_64 / 2 = aarch64
```

**折叠证据**（`--dump-ir`）：`('jcc','ne',('imm',1),('imm',2),...)` 在 a64 上、
`('imm',2)` 在 win 上 —— 常量已折叠，无运行期调用。

**实测澄清（重要）**：**它们不是条件编译**。`@ffi` 在 ELF 后端是**声明期**
硬失败，`if target_os() == 2 { ... }` 守卫**救不了声明本身**。所以跨平台 park
只能拆文件：

| 文件 | 后端 | 实现 |
|---|---|---|
| `std/park` | 仅 Windows PE | `WaitOnAddress`（`@ffi`） |
| `std/park_linux` | 仅 Linux | `futex(2)`（`syscall`） |

同一组 API，调用方按目标 import。

**`std/park_linux` 的三处实质差异**（写在模块头）：
① futex 的 `val` 是**直接整数**不是指针；② timeout 是 `timespec*` 而本模块传
`NULL` = 永久等待（靠调用方谓词复查兜底，所以不会挂死）；③ `-EAGAIN`
**也算被唤醒**（值变了没睡）。

**顺带发现 `irdiff` 契约要扩展**：加完这两个内建后，任何用它们选常量的源码
都会被判 IR 分叉。**这不是 bug** —— `irdiff` 原本只归一化 `syscall` 编号
（"唯一允许的架构差异"），现在多了一类。新增 `TARGET_IMM_RE`，**只匹配
`jcc` 里两个 `imm` 做 `ne`/`eq` 的特征形态**，不碰普通常量。
四条单元判据确认没过度归一化：target 形态相同 / 普通常量仍可分叉 /
变量比较不受影响 / syscall 归一化未退化。`irdiff` PASS=108 FAIL=0。

**`t172` 只接 CI linux job 的 x86-64**：AArch64 没有 `spawn`，
park 验证必须有第二个线程唤醒。是能力边界不是遗漏。
主回归 PASS=333 无变化。提交见下。

## Quelmara v3.20 — UDP over IPv6（AF_INET6 平台差异）

**先做了 P1 复核，发现三条文档滞后**（实现早就有、条目没划掉）：

教训：**能力表里的"未做"要定期对着夹具复核**。实现做了而条目没划掉，
与"文档说做了其实没做"一样误导排期，只是方向相反。
（`vec[map]` 在 v1.37 打了删除线，同一行的 `map[str]Struct` 却没打。）

**新增五个内建** `udp_open6`/`udp_bind6`/`udp_sendto6`/`udp_recvfrom6{,_to}`
+ `std/net/udp6`。拆成独立内建而不是加 family 参数：地址家族在 `socket()`
那刻就定死，调用方拿到的是不透明 fd，后续 `sendto` 无法判断该按 16 还是
28 字节构造地址。

**三个静默失败（每个都真卡了一次，都不是崩溃而是返回错误值）**：

1. **`sin6_family` 写死 10** → Windows 的 `bind` 返回 `-1` 且不报错。
   **Windows 的 `AF_INET6` 是 23、Linux 是 10**。`__udp_open6` 按平台分叉了，
   但 `udp_sin6`（构造地址结构那个）没有。**同一个事实在 `tcp_peer_raw`
   的注释里早就写着**（"2=v4 / 23=v6"），当时没串起来。
2. **`__net_fail_<tag>` 标签要手工在运行库定义**（原来只有 3 个），
   否则链接期 `KeyError`。每个 `net_fail` 调用点对应一个必须存在的标签，
   这是内建层的隐式契约，无编译期检查。
3. **`recvfrom` 必须返回 `buf+8`**（数据指针）不是 `buf`；且 `_to` 版
   超时该返回**空串**不是 fail-fast。

**所以 `t173` 必须做真实回环收发**，不能只验"能编过"。
主回归 PASS=333 → **334**。

## 项目要点（下次接手先看这几条）
- 本机是 Windows/aarch64？不是：win32 x64。原生后端默认产 **ELF**，要跑必须用
  `tools/stage0/qlm_pe.py build`（PE32+），`qlm_native.py` 是 Linux ELF 路径。
- 全量回归 `python tests/run_win_tests.py` 约 9–12 分钟（看 build/ 缓存热不热），v3.20 起输出 `PASS=334 FAIL=0 SKIP=0`（v3.11 记的 `SKIP=1` 是 WSL 交叉验证，本机复跑为 0）。
- **`target_os()` / `target_arch()`（v3.19）返回编译期立即数**，用来选常量。
  **但别指望它们做条件编译** —— `@ffi`/`syscall` 的声明期硬失败，
  `if` 守卫救不了声明本身。跨平台模块只能**拆文件 + 调用方按目标 import**
  （`std/park` / `std/park_linux` 是样板）。
- **改 `std/` 里任何带 `@ffi` 或 `syscall` 的东西之后**，务必手动跑一次
  `build <夹具> --target native` 和 `--target arm64` —— 主回归在 Windows 上，
  覆盖不到 ELF 后端（v3.15 就是这么把 CI 打红的）。
- **`syscall(n, a0..a5)` 是 v3.18 起用户可调的内建**（仅 Linux）。调用号必须编译期常量，
  返回负值即 `-errno`。要调内核新接口就用它，不要指望 `@ffi`（ELF 后端不支持）。
  注意**编号架构相关**，而语言无条件编译 —— 跨架构代码得"两个常量都写、按返回值选"。
- **`@ffi` 是后端专属的硬失败**：别往共享 `std/` 模块里直接放 `@ffi`，否则
  所有 import 它的非 PE 后端全部编不过（v3.15 踩过）。要么拆成独立模块让调用方
  显式 import，要么用 `static_word` + 函数指针注入（`std/sync` 的
  `sync_set_park` 是样板）。
- **验证矩阵要覆盖所有后端**：Windows 主回归全绿 ≠ CI 全绿。CI 的
  `run_native_tests.sh`（Linux/a64）里有主回归不跑的东西，改 `std/` 之后
  至少手动跑一次 `build <夹具> --target native` 与 `--target arm64`。
- 文档门禁两条：`python tools/dev/check_docs.py`（版本号同源/数字单一来源）、
  `python tools/dev/gen_stdlib_doc.py --check`（03-stdlib 与源码同源）。
- `03-stdlib.md` **只能**用 `gen_stdlib_doc.py` 重生成；用 `qlm_cli.py doc std -o` 会把
  它覆盖成裸 dump（踩过）。
- 提交时 `git -c core.safecrlf=false commit`，否则 LF/CRLF 警告刷屏。
- 一次任务 = 一个版本文件夹 + 一个 commit（docs/00-convention.md）。
