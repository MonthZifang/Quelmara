# 性能通用性与百万连接指南

> 2026-10-21。回答两个问题：**优化收益是通用的还是针对基准文件特调的**；
> **百万连接怎么配、内存怎么算**。数据来源见 `bench/gbench.qma`（通用形状
> 基准）与 `bench/loadgen.py`（网络负载，临时 Python 工具）。

## 1. 优化是通用机制，不是单文件特调 —— 逐项归因

| 优化 | 作用域 | 为什么是通用的 |
|---|---|---|
| str 长度前缀 ABI（85.9ms→22µs） | **语言数据表示** | 所有字符串代码的 `len`/`s[i]`/越界检查从 O(n) 变 O(1)，与源文件无关 |
| 2 的幂除法/取模特化 | **代数恒等式** | `x/2^k → 移位` 对任何代码成立，不认识"collatz" |
| 掩码值域建模（`and`/`mod`） | **值域分析** | 任意 `i & mask` 形状的环形下标都受益 |
| 8 字节块 memcpy | **运行时原语** | 所有拼接/拷贝/扩容共用同一份运行时 |
| `__realloc` 原地延展 | **分配器** | 所有 vec/map/spill 扩容路径 |
| 内联热函数白名单 | 半通用 | 只对运行时函数名开口子（避免体积膨胀），用户函数走通用阈值 |

**诚实的另一面**：优化器整体仍是"窗口匹配型"（性能报告 §5 的判断依然成立），
不是全功能编译器。基准测量用的当然是具体代码——但本轮用 **8 个从未参与
调优的全新代码形状**（`bench/gbench.qma`：词法器/状态机/str 哈希表/日志
组装/模式搜索/矩阵/散列链）复测，全部正常工作且量级合理（§2）。通用性
的最终裁判是这些未调优形状，不是调优期用例。

## 2. 通用形状基准实测（bench/gbench.qma，进程内 now_ns）

| 形状 | 工作量 | 实测 | 单位成本 |
|---|---|---|---|
| tokenizer（分支密集解析器） | 512KB 文本 | 4.0 ms | 0.78 ns/字节 |
| mix_arith（乘加移位依赖链） | 10M 迭代 | 58 ms | 5.8 ns/迭代 |
| map[str]int（字符串哈希表） | 1 万插+1 万查 | 4.4 ms | ~220 ns/op |
| branchy（数据依赖状态机） | 10M 迭代 | 43 ms | 4.3 ns/迭代 |
| str_build（日志行组装） | 1000 行×5 字段 | 0.8 ms | 800 ns/行 |
| buf_scan（模式搜索） | 1MB | 2.0 ms | 1.9 ns/字节 |
| nested（300×300 矩阵行和） | 9 万格 | 0.37 ms | ~4 ns/格 |
| hashmix（位散列链） | 10M 迭代 | 55 ms | 5.5 ns/迭代 |

**本轮基准还抓出并修复了两个真编译器 bug**——这正是"通用形状验证"的价值：

1. **LICM 外提触发 x64 分配器布局敏感段错误**（已默认禁用 licm，
   `QLM_ENABLE_LICM=1` 可开；A64 模拟器同程序全绿，QuIR 语义等价，
   纯 x64 分配器问题，根修另立轮次）；
2. **循环展开常量溯源不严谨**：60 条宽窗口把别的 `mov imm` 误当循环
   上界 + 展开副本被下一轮 LICM 二次处理。已修：窗口收紧 12 条、
   上界定义唯一性验证、unroll 移出收敛循环、body 含内层循环不展开。

修复后 PE 回归 **96 项全绿**。

## 3. 百万连接：内存账与配置

### 每连接内存 = 槽位层 + reactor 记录，两笔账

| 项 | 每连接 | 十万连接（默认档） | 百万长连接 |
|---|---|---|---|
| 槽位层（预分配，slot_words=80） | 640 B | 64 MB | 640 MB |
| reactor rec（**惰性分配**，80+recv_buffer+8） | 4184 B @默认 | 用多少占多少 | **4.2 GB @recv_buffer=4096** |
| reactor rec @ `recv_buffer = 512` | 600 B | — | **600 MB** |

### 关键机制

- **reactor rec 是惰性的**：连接关闭归还空闲链 O(1) 复用——**短连接
  场景 rec 不累积**（先到先复用），百万短连接只需几十个 rec 轮转。
- **百万长连接**才需要收缩 `recv_buffer`：`Quelmara.toml [net]` 改
  `recv_buffer = 512`（编译期定尺），1M 长连接总账 ≈ 600 MB + 槽位层
  640 MB（可再降，见下）。
- **协议槽位紧凑档**：`http_serve_max(port, backlog, handler, max_conns)`
  已暴露 max_conns；slot_words=80 中 512 B 是内联收发缓冲，溢出路径
  自动扩堆（上限 1MB/连接），纯控制面连接可调低（规划中：`slot_words=32`
  → 256 B/连接，1M = 256 MB）。

### 长连接 vs 短连接（实测，本机沙箱）

- **长连接（keep-alive）**：流水线 2000 请求 **0.001s**（客户端聚合口径
  ~300 万 req/s——keep-alive 路径每请求仅缓冲操作 + 一次 send，无系统
  调用逐请求开销）。
- **短连接**：通道功能正常（连接→请求→响应→关闭→rec 复用），但本沙箱
  对每次 connect/close 注入毫秒级监控开销，绝对值不可信；生产环境以
  keep-alive 为主（这也是 HTTP/1.1 的设计意图）。
- **静态链接**：Quelmara 产物本就是**无 CRT 静态单文件**（45–104 KB），
  无运行时依赖，`http_demo.qex` 双击即跑——静态链接是默认属性。

### 沙箱数据的诚实声明

本机（安全监控沙箱）对进程/网络操作注入 400–700ms 级 CPU 开销，所有
**绝对吞吐数字仅供相对比较**（长连接 vs 短连接的比值是可信的），百万
连接全量压测需要干净环境 + 多客户端源 IP（单机回环 ephemeral port
上限 ~16K/目标地址，C1000K 测试的正确姿势是多 IP 或多机）。

## 5. 标准库四件套实测（v1.6，`bench/p0_bench.qma`）

进程内 `now_ns`，已扣除启动开销；本机沙箱对进程/网络有注入，**绝对值仅供纵向比较**。

| 负载 | 实测 | 单位成本 | 评价 |
|---|---|---|---|
| SHA-256 1 MiB 单遍 | 71 ms | 14.7 MB/s | 标量实现，**不是能打的水平**（OpenSSL 同机通常 300–500 MB/s） |
| `str_split` + `str_join` 1 MiB（65537 段） | 30 ms | 28 MB/s | 单遍扫描 + 字节缓冲，无 O(n²) |
| URL 解析（scheme/host/port/path/query/fragment + 取值）×100k | 103 ms | 1.0 µs/次 | 每次 6 段线性扫描，符合预期 |
| JSON 解析 92.9 KB / 2000 对象 | 4–11 ms | 8–23 MB/s | DOM 式（每节点 6 字 + 字节缓冲） |
| JSON 遍历 2000 对象取 id 求和 | 1 ms | 0.5 µs/对象 | 线性 + 字符串键比较 |

### 为什么没继续堆优化

写这四件套时抓到一条**必现误编译**（已在 v1.8 修掉，回归在 `tests/t53_regress.qma`）：
循环内 `substr` 的长度来自函数调用结果、结果又 push 进 `vec[str]` 时，开优化必错、
`--no-opt` 正常。它指向**寄存器分配/生命周期**，和 LICM 默认禁用是同一类问题。

在这种状态下加 SIMD / 重开 LICM，等于在漏的地基上加层。所以本轮的性能结论是：

1. **先修分配器**（b1），修完再谈"更快"；
2. 修完后按 **LICM 复开 → 动态长度越界消除 → SIMD（canonical reduction）** 推进；
3. SHA-256 是下一个可见的性能靶子：8 字节加载 + 轮展开 + 常量表常驻，
   预期 3–5×（14.7 → 45–75 MB/s），仍不等于 OpenSSL，但足够做 ETag/签名。

**不宣称"赢过 C/Go"**：目前只有 `loop_sum` 这类可闭式折叠的形状赢（11–13ms vs gcc 231ms），
通用形状（哈希/解析/字符串）仍是 C 的 1/3 – 1/10。等 b1 修掉、SIMD 落地后再测一轮。

### 5.1 gzip / AES-GCM（v1.6 第二批）

| 负载 | 实测 | 说明 |
|---|---|---|
| gzip 1 MiB 高度重复 | 7,658 B / **117 ms** | 137×，约 9 MB/s 输入 |
| gzip 820 KB 英文重复 | 6,816 B / **90 ms** | 120×，约 9 MB/s |
| AES-128 单块 | 未单独计时 | 纯查表前实现，约 10 轮 × 16 字节 |
| GCM 1 KiB 加密 | 未单独计时 | **GHASH 逐位 128 次/块**，只适合握手/短消息 |

结论：gzip 的瓶颈是 CRC32 逐位 + LZ77 链长 8；GCM 的瓶颈是 GF(2^128) 逐位乘法。
两者都需要"查表化"才能进 MB/s 级——这是 TLS 吞吐的前置条件，不是可选项。

### 5.2 `@simd` 归约（v1.8）

4096 个 `int64` 求和 ×200 次（`bench/tmp_simd.qma` 同形状）：

| 版本 | 每次耗时 | 说明 |
|---|---|---|
| 标量 `while` | 3 µs | 每次元素访问带越界检查 |
| `@simd for` | **1 µs** | SSE2 `paddq` 两路 + 标量尾，**跳过逐元素越界检查** |

倍数 ≈3×。为什么不是 2×（两路）也不是 4×：标量版有越界检查与循环开销，
向量版把它们全省了，但两路 `paddq` 的理论上限就是 2 倍数据通路。
要更高需要 AVX2 四路（`vpaddq ymm`），那是下一步。
