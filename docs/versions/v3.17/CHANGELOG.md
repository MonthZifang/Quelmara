## 负结果一：`@simd` 函数放弃 XMM 分配，实测**测不出代价**

### 背景

`qlm_native.py` 的 `_xmm_candidates` 里有这么一段：

```python
# **SIMD 归约函数直接放弃**：`vsumd`/`vdotd` 的发射把 xmm0/xmm1 当固定
# 临时寄存器用（movupd/addpd/movhlps 全写死），与 XPOOL 的 0-3 直接冲突。
# 这类函数整体退回"f64 住 GPR"，正确性优先。
if any(ins[0] in ("vsum", "vsumd", "vdot", "vdotd") for ins in fn.instrs):
    return set()
```

`07-gaps.md` §5 一直写着「真修要把 SIMD 临时挪到不参与分配的寄存器」，
暗示这是一笔值得付的债。**先测它值多少。**

### 测法

`build/probe_simd_xmm2.qma`（未入库）：两个同形函数，各持 **8 个 f64 累加器**、
跑 10 万轮 `a = (a * y + 1.5) / 2.25`，唯一差别是其中一个含 `@simd` 归约
（因此整个函数放弃 XMM）。8 个累加器是刻意选的 —— GPR 池只有 5 个变量
寄存器，8 个必然溢出到帧槽；而 XMM 池有 10 个（XMM6-15）。这是能放大差距的形状。

### 结果

各 3 次交替：

| 轮次 | with_simd（放弃 XMM） | no_simd（正常 XMM） | 比值 |
|---|---|---|---|
| 1 | 3564 µs | 3601 µs | 98% |
| 2 | 3557 µs | 3668 µs | 96% |
| 3 | 3907 µs | 3905 µs | 100% |

**完全在噪声内**（`06-status.md` §3.50：本机分辨率 ±20%）。

### 为什么测不出

不是探针写错了 —— IR 层面确认过两者 `fbin f64` 数量几乎相同（**111 vs 110**），
`with_simd` 只是多了 16 条 `store`（那个 `@simd` 数组的初始化）。
**"放弃 XMM"只影响寄存器分配阶段，不改变 IR 形态**，而：

- 8 个累加器在 GPR 路径上本来就要溢出到帧槽；
- XMM 路径下它们住寄存器，但**帧槽访存与 XMM 寄存器访问在这条依赖链上延迟相当**
  （每轮 4 次浮点运算，除法 15 周期是瓶颈，访存被掩盖）。

所以"整体放弃 XMM"在这个形状上不构成瓶颈。

### 处置

**不改代码**。`07-gaps.md` 那一条改成负结果，并写明重启条件：
**要先造出一个"XMM 明显更快"的负载**，再谈改分配器。不能凭"看起来应该有收益"
就去动寄存器分配 —— 这正是 v2.60 / v3.02 那几条负结果反复验证过的纪律。

## 负结果二：`std/tls_net` 的两处 O(n²)，代价可忽略

### 背景

`tls_recv_exact` 的 `out = out + part`（第 40 行）与 `tls_connect` 的
`buf = buf + hdr + body`（第 74 行），是 v3.12 修 `std/httpc_net` 时登记下的
"同类残党"。

### 测法

`build/probe_tls_recv.qma`（未入库）：复刻 `tls_recv_exact` 的同一形状
（`while len(out) < n { out = out + tcp_recv(...) }`），用真实规模测。

### 结果

| n | 耗时 |
|---|---|
| 16 KB | **0 ms** |
| 64 KB | **0 ms** |
| 128 KB | **0 ms** |
| 256 KB | **2 ms** |

**262 KB 已经是 TLS 的最坏情况**（记录上限 16 KB + 256、握手最多 16 轮），
2 ms 完全可接受。

### 处置

**不改代码**。形状确实是同一个，但"形状像"不等于"代价大"——
v3.12 修 `httpc_net` 时那边是 **2 MB 就堆爆**，这里 256 KB 才 2 ms，
差三个数量级。`07-gaps.md` 改成实测数字 + 重启条件（谁把记录上限或
握手轮数调大才会踩）。

## 没做的：Linux futex —— 前置条件不满足

`07-gaps.md` §5 的「Linux futex」看起来是下一步，但查下来**语言层不支持**：

1. `syscall` 在 `qlm_native.py` 里是**内部发射指令**（`fn.emit("syscall", ...)`），
   不是用户可调的内建 —— 用户代码发不了 futex 系统调用；
2. 语言**没有条件编译**（没有 `cfg` / `target` 分支），所以没法在
   `std/park` 里写"Windows 走 `@ffi`、Linux 走 syscall"；
3. `@ffi` 在 ELF 后端是声明期硬失败，而 ELF 是静态可执行文件
   （无 `PT_INTERP`），本来就没有外部符号可解析。

要做得先给语言加两个能力之一：**用户可调的 `syscall(n, ...)` 内建**，
或**按目标选实现的条件编译**。那是语言层的工作，不是标准库的。
已记在 `07-gaps.md` §4 与 §5。
