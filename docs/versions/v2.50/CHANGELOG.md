# v2.50 — 变量寄存器按使用次数分配：`b7_sort` 快 19%

- 日期：2026-10-25
- 任务：严重优化性能与加速比
- 影响面：自举层（`_alloc` 前新增 `_alloc_vars`）/ 基准 / 文档

## 怎么找到的

本来按 §7.31(e) 准备把 `RDI`/`RSI` 加进变量寄存器池，但先做了个实验 —— **7 个
标量变量时到底谁溢出**：

```quelmara
let a = 1 … let f = 6      // a-e 拿 RBX/R12-R15，f 落帧槽
let mut s = 0              // s 落帧槽 [rbp-0x10]
let mut i = 0              // i 落帧槽
```

**分配是"按创建顺序"的**：`_new_var` 里前 5 个标量拿 `RBX/R12-R15`，第 6 个起
落帧槽。于是 `let n / v / i / s / t / t0 / t1` 这种 7 个变量的函数里，**最热的
累加器 `s` 和循环变量 `i` 跟第 6、7 个一起溢出**，热循环每轮多两次内存往返，
而且 store→load 形成**串行依赖链** —— 实测 `b4_array` 每元素 21 个周期（C 只要 5）。

## 修法

`_alloc` 之前加一趟 `_alloc_vars`：扫一遍 IR 统计每个 vreg 被读几次，然后
**贪心交换** —— 反复找"使用次数最少的寄存器标量"和"使用次数最多的槽内标量"，
互换位置，最多 8 轮（每轮至少提升一个，够用）。

**两条安全边界（这是关键，别绕开）**：

1. **只动标量。** 聚合变量的"值 = 区域地址"，槽号在降级期就被 `OP_ADDRV`
   烧进 IR 了（全代码 15 处），搬了就错。
2. **标量也要查槽号有没有被 `OP_ADDRV` 引用过。** 一遍扫 IR 时顺手把
   `OP_ADDRV` 的 `imm` 记进 `baked` 位图，`baked[slot] == 1` 的变量不许搬。
   反过来**寄存器里的变量不可能被烧过**（它压根没有槽），所以降级永远安全 ——
   这就是为什么"贪心交换"只需要单向检查。

缓冲区 `ucnt` / `baked` 由 `_compile_range` 持有、跨函数 `clear()` 复用
（v2.44 的教训：别在每函数里 `vec.new`）。

  曾出现 59.3 ms，min-of-5 是 42.4 ms）。

## 下一步：`RDI`/`RSI` 扩池（这次没做，原因具体）

`RDI`/`RSI` 在 Win64 里是 **callee-saved**，理论上可以当第 6/7 个变量寄存器，
让 7 个以上变量的函数也全进寄存器。**但这轮没做，因为它不是"加两行"**：

- `__memcpy` 是**手写字节循环**，直接用 `RSI`/`RDI` 当源/目的指针
  （`mov al,[rsi]; mov [rdi],al; inc rsi; inc rdi`），不是 `rep movsb`。
- `_gen_str_cat` 也把 `RDI`/`RSI` 当临时寄存器用。
- 调用点有 5 处（`OP_COPY`/`OP_MEMCPYN`/`OP_ZERO`/`OP_ZERON`/`OP_RETAGG`）。

**漏改一个就是静默改值**（变量被例程悄悄改掉，不崩溃）。做这件事的正确顺序是：
先把所有 `_gen_*` 的寄存器用法审计一遍（最好用反汇编脚本机械核对），给用到的
例程加 `push rsi/push rdi` + 对应 `pop`（注意 `__str_cat` 里有调用，要保持 16 字节
对齐），再把 `_cs_reg`/`_cs_index` 扩到 7 个。收益估计 10–15%。
