# v4.109 — 定位 `b28_matrix` 三个 `imul` 的真正阻断点

- 日期：2026-11-11
- 任务：消掉 `b28_matrix` 内层循环重复的 `r*n`（每轮 2 个多余 imul）
- 影响面：文档（改动均未合入 —— 见下）

## 一句话

查清了 `b28` 的三个 `imul` 为什么消不掉：**不是越界检查、也不是变量失效，
而是 `c.set(...)` 之后的临时值让 CSE 表在关键位置被清空**。三个尝试里两个
正确性通过但收益为零，第三个有漏洞，全部撤回。

## 已确认的事实（`b28_matrix` 内层循环的 IR）

`c.set(r*n + j, c.get(r*n + j) + av * b.get(k*n + j))` 展开后，三处 `r*n`
的 IR **操作数完全相同**：

```
z=256  MUL dst=193 a=187 b=1     ← 第 1 处 r*n
z=271  MUL dst=201 a=187 b=1     ← 第 2 处，与上面同一个键
z=284  MUL dst=211 a=187 b=1     ← 第 3 处
```

CSE 的键是 `(op, va, vb, imm)`，这三条完全一致。**理论上第 2、3 处都该命中
第 1 处**。实测只有第 3 处命中（`i=284 hit=201`），第 2 处没命中。

### 尝试 1：把越界检查四连视为透明（正确但无效）

`_vec_check` 的形状：

```
JCMPVLEN i,[h+8] -> ok     界内 → 跳到 ok
LAB fail                   冷路径起点
JMP trap                   跳到函数尾陷阱桩（自旋，永不返回）
LAB ok                     界内继续
```

正常执行只走 `JCMPVLEN` → `LAB ok`，四条对寄存器/内存**零副作用**。
实现了按位置识别这四连并跳过清表。

**结果**：`b28`/`b49`/`b75`/`b35`/`b23`/`b11` 全部 checksum 正确，
但 **`imul` 仍是 3 个，循环仍是 32 条** —— 收益为零。撤回。

### 尝试 2：追踪表为什么被清（找到真正阻断点）

加诊断打印 `keys` 长度变化，定位到：

```
[scan] i=256 op=5  bc=0 keys=0     ← MUL r*n 入表
[scan] i=257 op=3  bc=0 keys=4
[scan] i=258 op=73 bc=1 keys=8     ← JCMPVLEN（透明化生效）
[scan] i=261 op=12 bc=1 keys=8     ← LAB ok（透明化生效）
[scan] i=266 op=2  bc=0 keys=8
[scan] i=267 op=1  bc=0 keys=0     ← 表被清空！
[scan] i=271 op=5  bc=0 keys=0     ← MUL r*n 重新入表（错过了第 1 处）
```

`i=267` 的清空来自 **v4.108 的保守失效**（写任何 `vpin != 0` 的变量就清整表）。
`i=266` 的 `MOV dst=191` 写了变量 191，于是表被清。

所以真正的阻断是**保守失效**，不是越界检查。

### 尝试 3：精确失效（有漏洞，撤回）

用值编号做精确失效：`vn[dst]` 或 `dst` 出现在表项的 `ka`/`kb` 里才丢弃该项。

**结果**：`b28`/`b75`/`b35`/`b23`/`b11`/`q2` 全部正确，但
**`b49_floyd` 变成 0**（应 173）。撤回。

**漏洞原因**：取 `dv = vn.get(ins.dst)` 时，`vn[dst]` 已经被前面的
`MOV` 传播改成了新值，取到的是**新**编号而不是旧编号，失效比对因此错位。
修法是把取值移到传播之前（下一轮的第一个动作）。

## 为什么三个尝试都没拿到收益

就算精确失效修对，也未必能让 `b28` 的 `imul` 从 3 变 1 —— 因为：
- 第 3 处（`i=284`）已经能命中第 2 处（`i=271`）
- 要让第 2 处命中第 1 处，中间 `i=256..271` 这一段必须**完全不被清表**

而那段里有 `c.get(...)` 的完整序列（含 `LOAD`/`ADDRX` 等）。`_cse_ok` 白名单
只收纯算术，所以 `LOAD` 不入表、也不清表 —— 这不是问题。真正的清表点是
变量写（`i=266`）。

## 下一轮的确切动作

1. **修精确失效的取值顺序**：`dv` 必须在 `vn` 传播**之前**取。
   现在的代码顺序是「传播 → 失效」，应该改成「失效（用旧 vn）→ 传播」。
2. 修好后重测 `b49_floyd`（应 173）与 `b28` 的 `imul` 数。
3. 如果 `imul` 仍不到 1，检查 `i=256..271` 区间还有哪些清表点。

## 已知边界 / 遗留

- `b28_matrix` 仍是全项目最差项（CI 上 quelmara/C = 12.7×），
  内层循环 32 条里 4 次 store→load 往返、5 条冗余 mov、3 个 imul。

  所以"重复的地址计算"仍需值编号推广 + 别名分析才能消除。
