# v4.111 — 修正审计口径：原来统计的"浪费"大半是必需的搬参

- 日期：2026-11-11
- 任务：全局扫描找性价比最高的优化目标
- 影响面：工具链（`tools/dev/asm_audit.py`）

## 一句话

跑了一次全项目扫描，然后发现**统计口径是错的**：原来算进"冗余 mov"的
大部分是**函数调用实参准备**（必需），不是浪费。修正后真正的优化目标只剩
一个 —— `b28_matrix` 的 4 次溢出往返。

## 原来的口径哪里错了

`asm_audit` 把循环里所有 `mov rX, rY` 都算成"冗余"。但看 `b9_json` 的热循环：

```
40115b: mov  rcx,rbx      ← 第 1 实参
40115e: mov  rdx,r12      ← 第 2 实参
401161: call 0x400ccf
401166: mov  r8,rax       ← 返回值落位
401169: mov  r12,r8
```

前三对是**调用的实参准备**，一条都省不掉。只有 `mov r12,r8` 紧跟
`mov r8,rax` 那对才是真冗余（可合成 `mov r12,rax`）。

按老口径统计，`b9_json` 报 24 条 mov、45% 浪费；按新口径只有
**4 条真冗余 + 11 条必要搬参 = 8%**。差了 5 倍多。

## 新口径

把 `mov rX,rY` 分成三类：

| 类别 | 判据 |
|---|---|
| **真冗余** | `mov X,Y` 后面**紧接** `mov Z,X`（同一值连搬两次，可合成一条）|
| **必要搬参** | 后面 2 条内出现 `call`，且 `X` 是实参寄存器（rcx/rdx/r8/r9/rdi/rsi）|
| 其他 | 剩下的（可能有机会，但要人工判断）|

新输出（`上限占比` = (溢出往返×2 + 真冗余) / 循环指令数）：

```
bench                      循环指令   溢出往返   真冗余mov   必要搬参   上限占比
b75_fib_matrix                215        0         10          0        5%
b28_matrix                     32        4          0          0       25%
b9_json                        53        0          4         11        8%
b35_branch                     10        0          0          0        0%
```

## 结论：方向要换

| 基准 | 老口径 | 新口径 | 判断 |
|---|---|---|---|
| `b75_fib_matrix` | 71 条 mov（33%） | **10 条真冗余（5%）** | 不值得做 |
| `b9_json` | 24 条 mov（45%） | **4 条真冗余（8%）** | 不值得做 |
| `b28_matrix` | 3 个 imul（我上轮的目标）| **4 次溢出往返（25%）** | **唯一值得做的** |

前两轮我一直在追 `b28` 的 `imul`（收益上限 6%），而真正的浪费是**寄存器溢出**
（25%）。这是方向选择的错误，本轮通过改口径纠正了。

## 下一轮的确切目标

**`b28_matrix` 的 4 次 store→load 相邻往返**（占内层循环 25%）。

```
401518: mov [rbp-0x170],rax    ← 溢出
40151f: mov r11,[rbp-0x170]    ← 立刻读回
```

根因是内层循环活跃值超过可用寄存器：3 个变量 + 多个临时值抢
7 个变量寄存器（RBX/R12-R15 等）+ 4 个临时池（R8-R11）。

可行方向（按风险从低到高）：

1. **缩短临时值活跃区间**：`_lower_expr` 生成的临时值常常在本条语句内
   就死掉，但 `vstart`/`vend` 记的范围过宽。如果分配器按真实区间分配，
   溢出自会减少。**风险最低，先试这个。**
2. 给临时值池扩容（比如把 `RAX`/`RDX` 在纯算术段借出来用）。
3. 重写分配策略（按区间长度而非定义顺序）。
