# v3.29 — 单条消息上限等于连接缓冲上限：上限之内的消息反而收不全

- 日期：2026-10-30
- 任务：用户要求"继续"；v3.28 遗留的"超长消息 1009 与 64 位长度档没覆盖"
- 影响面：**标准库**（`std/ws` 的 `WS_DEFAULT_MAX_MSG` 1 MB → 960 KB，
  超限时补发 close 1009），夹具从 15 项扩到 17 项
- 版本：按 `00-convention.md` §5.1 建版本目录

## 起点

v3.28 的 CHANGELOG 末尾写着：

> 超长消息被拒（`plen > maxmsg` → close code **1009**）与 64 位长度档
> （`plen >= 65536` 走 8 字节长度）没有覆盖。

补它们的过程又撞出一个缺陷。

## 缺陷：上限之内的大消息会永久卡死

扫边界（发一条消息、看能否 echo 回来）：

| 载荷大小 | 结果 |
|---|---|
| 500 000 | ok |
| 1 048 476 | ok |
| **1 048 576**（正好 = 上限） | **NO RESPONSE** |
| 1 200 000 | NO RESPONSE |

1 MB 是 `WS_DEFAULT_MAX_MSG` 的值，理论上"不超限"，**却卡死**。

## 根因：两个 1 MB 撞在一起

```quelmara
// std/ws.qma
const WS_DEFAULT_MAX_MSG = 1048576    // 单条消息上限 1 MB

// std/net/core.qma
const CONN_MAX_BUF = 1048576          // 单连接累积上限 1 MB
```

一条消息要收全，缓冲区里得同时放得下「帧头 + 掩码 + 载荷」。两个上限
相等时，载荷还没收完连接缓冲就先到顶了：

1. `conn_append` 返回 -1，后续数据被丢弃；
2. `_frames` 里 `n - off < hl + plen` **永远成立**（`n` 到不了 `hl+plen`）；
3. 于是 `break` 出去等下一段数据 —— 而下一段永远收不进来。

**永久卡死，而且连 1009 都发不出去**（`plen > maxmsg` 那条判断压根没机会执行）。

实测边界：1048476 过、1048566 卡死（差 100 = 帧头 + 掩码）。

## 修法一：消息上限必须明显小于连接缓冲

只留 64 字节余量是不够的 —— 试过 `1 MB - 64 B`，`plen` 略超上限的帧
仍会先把连接缓冲塞满才轮到 `_frames` 判 1009，那时 socket 里堆着未读数据，
发 close 帧后立刻关闭会被 RST 吃掉，**客户端一个字节都收不到**
（实测：收到 0 字节 + `WinError 10054`）。

留 **64 KB** 余量：

```quelmara
const WS_DEFAULT_MAX_MSG = 983040     // 960 KB（1 MB - 64 KB）
```

这样超限帧的帧头能在缓冲未满时被解析到，1009 正常触发（那条路径实测可用）。

## 修法二：缓冲溢出时补发 1009

`ws_on_data` 里 `conn_append` 失败原本是静默关闭：

```quelmara
if r < 0 {
    return 0                        // 缓冲超限：直接关闭
}
```

改成先发 close 1009 再关。虽然**极端情况下仍可能发不出去**（数据把
socket 塞满、RST 覆盖），但比静默断开好 —— 至少能读到的场景会告知原因。

## 一个必须如实说明的边界

**"客户端一次性猛灌超过连接缓冲的数据"仍会卡死。** 这不是 ws 协议
缺陷，是 TCP 背压问题：

* 服务端连接缓冲上限 1 MB，客户端 `sendall` 一次推 1.2 MB；
* 服务端还没解析帧头，数据就把缓冲塞满了；
* 服务端的接收窗口关掉，客户端 `sendall` 阻塞 —— 双方互等。

真实客户端会分块发送（浏览器、`websockets` 库都是），不会一次猛灌。
夹具里也**只发帧头、不发载荷**来测 1009 —— 那才是"协议是否拒绝"的
正确问法。

## 夹具扩到 17 项

| # | 判据 |
|---|---|
| 13 | 超长消息（声明 1 100 000 B）被拒，close code **1009** |
| 14 | 上限之内的大消息正常收发（900 KB，走 64 位长度档） |

### 关于第 14 条的诚实说明

它**抓不到**这次修的 bug。那个 bug 只在"载荷恰好逼近 1 MB"时暴露，
而边界值差几十字节 —— 钉死具体数字的测试会非常脆（试过：旧上限下
1048560 仍能过，1048570 才挂）。

所以第 14 条钉的是"大消息这条路通"（顺带覆盖 64 位长度档），
边界由第 13 条的 1009 侧兜住。这个取舍写进了测试注释，免得后来者
误以为"这条能防边界回归"。

## 回归

全量 Windows 回归 PASS=344 FAIL=0 SKIP=0（v3.28 是 344，主回归条数不变，
ws 脚本内部断言 15 → 17）。

## 遗留

`CONN_MAX_BUF` 与协议层消息上限的**数量关系**目前靠人工约定
（ws 取 960 KB）。若将来再加一个协议层（比如基于 TCP 的自定义帧协议），
同样容易踩"上限相等"的坑。真要收口得让 `conn_append` 在超限时
**先通知协议层**（返回一个可区分的错误码），由协议层决定怎么告知对端。
那要改 `std/net/core` 的接口，留待后续。
