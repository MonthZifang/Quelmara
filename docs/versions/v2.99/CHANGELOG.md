# v2.99 — ECDSA P-384 / SHA-384：让内置根证书库真正能用

- 日期：2026-10-28
- 任务：补库 —— gaps §2 TLS 行的 "P-384 / SHA-384"
- 结论：v2.97 建好根证书库后，五站点普查暴露了覆盖面真相——**12 个内置根里
  7 个验不了自签**，Let's Encrypt 现役链、Google Trust Services、Sectigo E
  系列**整条链验不过**，因为每一环都是 `ecdsa-with-SHA384` / P-384。
  本版补齐 P-384 曲线与 RSA-SHA384，自验证覆盖 **5/12 → 11/12**，
  两条真实 P-384 链（deno.com / cloudflare.com）执行级验通。

## 先修一个比 P-384 更基础的错误：摘要 ≠ 曲线

写代码前先看真实链的算法分布，发现的不是"缺 P-384"这么简单：

| 证书 | 公钥曲线 | 签名算法 |
|---|---|---|
| deno.com 叶 | **P-256** | **ecdsa-with-SHA384** |
| Let's Encrypt YE2 | P-384 | ecdsa-with-SHA384 |
| cloudflare 叶 | P-256 | ecdsa-with-SHA256 |
| Google WE1 | **P-256** | **ecdsa-with-SHA384** |

**摘要算法与密钥曲线是独立的**。而 v2.97 及之前的 `_x509_link` 按"签发者密钥
宽度"硬绑摘要（P-256 → SHA-256，RSA → SHA-256），所以：

- `P-256 密钥 + SHA-384 签名` 这类链（deno 叶、WE1）**永远验不过**，
  即使补了 P-384 也没用；
- 修法不是加分支，而是**按子证书的 `signatureAlgorithm` 选摘要**，
  曲线由签发者密钥决定。这是本版最重要的一行改动。

配套按 FIPS 186-4 §6.4 处理摘要长度不匹配：`e` = 摘要的**最左 n 位**
（n = 曲线阶位数）。P-256 配 SHA-384 时取左 32 字节——不是报错、也不是取右侧。

## P-384 实现

`std/p384.qma`，680 行 → 12 limb 版本，结构与 `std/p256` 逐函数对应：
同一套 Montgomery SOS 乘法、同一套 Jacobian 倍点/点加公式（dbl-2001-b /
add-2007-bl）、同样的 `_q_*` 前缀把 8 limb 换成 12。

**刻意不做"通用曲线参数化"**：两份直白的手写常量表比一份带分支的元实现更
容易逐行核对，且 p256 已在生产路径上验证了一年多。代价是代码重复，收益是
P-384 第一版就能一次跑对（见下）。

顺带补 `sha384_str`（返回 48 字节原始摘要）——ECDSA 要字节，不是十六进制串。

## RSA-SHA384

`sha384WithRSAEncryption`（1.2.840.113549.1.1.12）是 Amazon Root CA 1 的自签、
microsoft.com 全链、大量企业 CA 的算法。原 `rsa_verify_pkcs1_sha256` 把
DigestInfo 前缀与摘要长度写死，本版抽出 `_rsa_pkcs1_verify(n, e, sig, hash,
di, hlen)` 主体，两个公开函数只差前缀与长度：

```
SHA-256: 30 31 30 0d 06 09 60 86 48 01 65 03 04 02 01 05 00 04 20
SHA-384: 30 41 30 0d 06 09 60 86 48 01 65 03 04 02 02 05 00 04 30
                                          ↑算法序号        ↑长度
```

## 验证：两侧用完全不同的代码路径算同一条曲线

| 夹具 | 内容 | 结果 |
|---|---|---|
| `t160_p384.qma` | Python 纯 bigint 独立生成的 P-384 向量（d/k 固定，Python 侧先验过）+ 6 类负向（篡改 hash/r/s/公钥、r=0、s=0）+ 长度守卫 | **p384 ok** |
| `t161_p384chain.qma` | 两条 2026-10-28 抓的真实链：deno.com（YE2/Root YE 是 P-384，叶是 P-256 配 SHA-384，四层到 ISRG X2）、cloudflare（P-256 配 SHA-384，到 GTS R4）；含域名不符/缺中间证书负向 | **p384chain ok** |
| `t159_roots.qma` | 12 根自验证计数 | **5/12 → 11/12** |
| win / arm64 交叉编译 | t160、t161 | PASS |

自验证覆盖 11/12，唯一剩下的 Certum Trusted Network CA 是 **SHA-1 自签**
（RFC 9155 已弃用），明确不实现。

## 一次值得记下的误判

t161 第一版把 **Root YE 当信任锚**，链验证失败。我据此怀疑 P-384 实现有 bug，
花了几轮在 TBS 提取、公钥点编码、DER 偏移上排查，最后用 openssl + 独立 Python
实现双向确认"输入的每个字节都对、P-384 验签本身也对"。

真相是**链构造错了**：`Root YE` 由 `ISRG Root X2` 签发，它自己不是自签根。
拿一个非自签的中间 CA 当锚，在密码学上本来就不成立。

修正后的负向断言反而更有价值——现在 t161 明确断言
`x509_verify_self_p384(Root YE) == 0`，把"它不是自签根"这件事钉在测试里。

> 教训：验证失败时**先怀疑输入**再怀疑算法。区别在于"我构造的测试数据是否
> 符合协议"是可以被外部工具（openssl）独立裁判的，而"我的实现是否有 bug"
> 不能自证。先让外部工具裁判输入，能省掉大段无效排查。

## 边界（不做的）

| 项 | 理由 |
|---|---|
| SHA-1 签名（Certum 根、老企业 CA） | RFC 9155 弃用；主流浏览器早已拒绝 |
| Ed25519 / Ed448 证书 | 公网占比很低，且需要完全不同的域运算 |
| RSA-PSS **证书**签名 | 本栈的 PSS 只服务 TLS 1.3 CertificateVerify；证书用 PSS 极少 |
| OCSP / CRL 吊销检查 | 独立子系统（要 HTTP 客户端 + ASN.1 + 缓存），不塞进曲线补丁 |
