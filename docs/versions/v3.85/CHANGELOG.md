# v3.85 — 正式登记 §7.46：qlmc 完全不支持窄类型

- 日期：2026-11-02
- 任务：把"qlmc 不支持窄类型"从注脚提升为正式缺口登记。
- 影响面：`docs/07-gaps.md`（新增 §7.46）
- 代码改动：无（纯文档）

## 为什么单独登记

这条以前只在 §7.28 的注脚里出现过一句（"窄标量 `vec[u8]` 也走同一条标签
通道，但 qlmc 不支持窄类型"），既没说影响面，也没说优先级。查了一下实际
情况，值得正式记一条。

## 现象

```quelmara
fn main() {
    let a: u8 = 200      // qlmc: line 2: 未知类型 u8
    print(a)
}
```

`as` 转换同样不支持（`200 as u8` 报"未定义变量 as"）。

## stage-0 支持什么

6 种窄类型（`NARROW_BITS`）：`u8`/`u16`/`u32`（无符号）、
`i8`/`i16`/`i32`（有符号）。语义是"**所有存储点截断**"（v1.40/v1.56 做全）：
let / 形参 / 返回值 / 赋值 / struct 字段 / enum 载荷 / vec 元素 / 定长数组 /
切片别名写入；表达式内部按 C 提升不截断。

## 影响面（实测，不是估计）

全仓库只有 **17 处**窄类型注解，集中在 4 个 stage-0 侧测试文件：
`t49_width` / `t85_narrowstore` / `t123_derive_enum` / `t115_derive`。

**`std/` 里一处都没有** —— 那几个模块（`tls13` / `tls_client` /
`net/dns` / `net/udp` / `serialize`）只在**注释**里提到 `u32`（比如
`udp_parse_ip` 的"网络序 u32"），代码里用的是 `int`。

所以两件事可以确认：

1. qlmc 的 **69/69 覆盖率是真实的**，没有靠"避开窄类型"刷数字；
2. 这 4 个测试**不在** `tests/qlmc_test.py` 的差分列表里 —— 是**已知且被
   明确排除**的边界，不是遗漏。

## 为什么登记为"待做"而不是"待修"

窄类型要改的是类型系统 + 截断语义 + 全部存储点，是"贯穿式"改动；而实际
需求只有 4 个 stage-0 侧测试。**收益与成本不匹配。**

优先级定在 §7.31（性能）之下：窄类型不影响任何 `std/` 模块、不影响
`examples/`；而 §7.31 影响所有真实程序的性能。

## 如果要做，检查清单

1. `_type` 认 6 个窄类型名 → 新类型码（`TY_BYTE=4` 已预留但未用，
   可能需要位宽 + 符号的编码，不能只用一个码）；
2. 每个存储点都要截断（stage-0 的 `t85_narrowstore` 就是逐个钉的）；
3. `as` 转换；
4. 表达式内部**不截断**（按 C 提升）；
5. 差分夹具：把 `t49_width` / `t85_narrowstore` 加进 `tests/qlmc_test.py`。
