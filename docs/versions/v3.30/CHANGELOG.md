# v3.30 — 负结果：消掉归纳变量那条 `mov` 测不出收益

- 日期：2026-10-30
- 任务：用户要求"继续"；`07-gaps.md` §5 里 `loop_sum 三件套` 的第 ① 项
  "phi copy 消除（分配器 coalescing）"
- 影响面：**无代码变更**（`opt_phi_copy` 实现并验证后回退），
  新增 `tests/t178_phi_copy.qma` 钉住归纳变量化简的正确性
- 版本：按 `00-convention.md` §5.1 建版本目录（负结果也要留痕）

## 起点

`07-gaps.md` §5 的 `loop_sum 三件套` 写着：

> 循环 10.8 → ~4 cycles/iter
> ① phi copy 消除（分配器 coalescing）

`examples/loop_sum.qma` 的 `work()` 循环体 IR 里确实有一条搬运：

```quelmara
('mov', 7, 10)                 # tmp = r
('bin', 'add', 10, 10, imm 7)  # r += 7
('cssub', 10, 10, imm 13)
('bin', 'add', 1, 1, 7)        # acc += tmp
```

`opt_copy_prop` 消不掉它 —— 它的前提是"源 vreg 只被定义一次"，
而 `r` 在循环里每轮重定义。

## 实现：`opt_phi_copy`

变换是**重排**（不只是删除）：

```
mov tmp, r           ->    acc += r        # 提到 r 更新之前，读旧值
r 更新 ...                  r 更新 ...
acc += tmp
```

安全条件（缺一不可）：`tmp` 只用一次、区间内只有 r 的自更新、
使用点另一个操作数不是 r、目标不是 r。

实现后验证过 IR 确实变了：

```quelmara
# 变换前（5 条）
('mov', 7, 10)
('bin', 'add', 10, 10, ('imm', 7))
('cssub', 10, 10, ('imm', 13))
('bin', 'add', 1, 1, 7)
('bin', 'add', 2, 2, ('imm', 1))

# 变换后（4 条）
('bin', 'add', 1, 1, 10)
('bin', 'add', 10, 10, ('imm', 7))
('cssub', 10, 10, ('imm', 13))
('bin', 'add', 2, 2, ('imm', 1))
```

正确性用 Python 现算的已知答案验过（`t178_phi_copy.qma`，
含 `n=0/1/2` 边界、两个不同模数、交换结合顺序、周期校验）。

## 实测：零收益

进程内 7 轮取 best/avg（`build/phi_bench3.qma`，2 亿次迭代）：

| | best | avg |
|---|---|---|
| 有 pass | 253 ms | 254 ms |
| 无 pass | 257 ms | 261 ms |

看起来有 1.6%–2.7%，但**重复测量后差异消失**：

| 轮次 | ON best | OFF best |
|---|---|---|
| 1 | 254 | 254 |
| 2 | 253 | 254 |
| 3 | 253 | 254 |

完全重合。

### 换成"mov 占比更高"的形状也一样

怀疑是 `loop_sum` 循环体太长（4–5 条）稀释了收益，于是造了循环体只有
3–4 条的形状（`i % 3` 归纳，`build/phi_bench4.qma`，3 亿次迭代）：

| | ON best | OFF best |
|---|---|---|
| tight | 333 / 334 / 333 | 333 / 335 / 337 |
| double_use | 381 / 381 / 380 | 380 / 381 / 380 |

同样完全一致。**确认 pass 在这些形状上真的生效了**（IR dump 显示 mov 已消除），
不是空操作。

## 为什么零收益

x86-64 的 `mov r64, r64` 在**寄存器重命名阶段就被消掉**，不占执行端口。
这与 v2.02 那条负结果的机理完全相同：

> SHA-256 轮展开 —— 每轮 8 条搬移全部消失，1 MiB 仍是 41–42 ms。
> 瓶颈不是搬移而是**指令数**……x86 的 `mov` 在重命名阶段就消掉了，
> 省它不省时间。

## 一个差点被误导的测量

第一版探针用了这个对照：

* base：`acc += (i*7)%13`（1 条 mov）
* plus1：`let t = acc; acc = t + (i*7)%13`（2 条 mov）

结果 **255 ms vs 328 ms（+29%）**，看起来"一条 mov 值 29%"。

**这个结论是错的。** 看 IR 就明白：plus1 多出来的是

```quelmara
('bin', 'add', 9, 3, 8)   # acc 写到新 vreg 9
('mov', 1, 9)             # 再搬回 acc
```

它同时**增加了两个活跃 vreg**（`3` 和 `9`），寄存器分配变差才是那
73 ms 的来源，不是 mov 本身。

正确的对照必须是"同一段代码，只差一条 mov" —— 也就是这次实现 pass 之后
用 `QLM_SKIP_PASSES=opt_phi_copy` 做 A/B。那种对照给出的是零收益。

**教训**：源码层的"看起来等价"很容易悄悄改变寄存器压力。
判断某条指令的代价，要用 pass 级 A/B，不要用源码改写。

## 决定：回退

按 §5 的两条铁律：

> 1. 单点核对全对 ≠ 装起来对——必须反汇编对照或单元素 trace。
> 2. 前置条件不满足就回滚并登记重启条件；错误代码比没有代码更糟。

以及贯穿多条负结果的原则：**测不出好处就不留这份复杂度**。

`opt_phi_copy` 已从 `qlm_opt.py` 回退，代码不在树上。

## 保留的东西

`tests/t178_phi_copy.qma` 留着，并已进主回归。它钉的不是这个 pass，
而是**归纳变量化简本身**（`i*7%13` → `r += 7` / `cssub`）的正确性 ——
那也是重排型变换，错了会静默算错。已知答案由 Python 现算：

```
n=5     -> 18
n=13    -> 78
n=100   -> 590
n=1000  -> 6000
n=13000 -> 78000（100 个完整周期 × 78）
```

## 重启条件

若将来出现下列任一情况，可以重新评估：

1. **寄存器压力模型**先落地（`07-gaps.md` §5 "溢出代价模型"那条）——
   有了它才能区分"这条 mov 的代价"与"多一个活跃 vreg 的代价"；
2. 目标架构换成 `mov` 有真实延迟的（AArch64 的 `mov` 同样是别名，
   但某些 RISC 架构不是）；
3. 出现实测 ≥5% 的循环热点，且 IR 里 phi copy 占比显著。
