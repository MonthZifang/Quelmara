## 结果：两个优化都撤回了，本轮没有性能改动

按项目纪律（**净收益为负就不留在树上**），如实记录过程，避免下一轮重走。

### 尝试 1：位运算后省掉冗余的比较（撤回）

`if (i & 3) == 0` 的结构是：

```qma
mov r9, r14
and r9, 3        ; x86 位运算本身已设置 ZF
cmp r9, 0        ; ← 完全多余
jne ...
```

**判定**：`AND/OR/XOR` 之后紧跟 `JCMPI dst,0`（且条件码是 je/jne）时，
那条 `cmp` 可以整条省掉。实现了，正确性也过了（76/76 checksum 一致、
自举不动点成立），`b35_branch` 热循环从 13 条降到 12 条。

**但实测**：`b35_branch` **83 → 88 ms（慢 6%）**，稳定复现（各 7 次取最小）。

反汇编确认两版循环起点**完全相同**（都在 `0x400d37`，mod16 = 7），
唯一差别是循环体从 13 条变成 12 条 —— 这是 Silvermont 的取指/解码带宽效应，
少一条反而跨了某个边界。

`b8_threads4` 一度显示 −29.4%，复测是 **167 vs 167**（完全一样），
那是并发基准的噪声，不是真实收益。

**结论**：净收益 0、局部回退 6%，撤回。

### 尝试 2：循环头 16 字节对齐（撤回）

v4.93 做过一次，`b15_loopsum` 从 1.35s 变成 1.40s，当时判定"不是取指对齐问题"。
本轮 `b35` 的证据看起来像对齐问题，但既然循环起点本来就相同（0x400d37），
对齐不是原因 —— 所以**没有再做**。

## 查明的两处根因（留给下一轮）

### 1. `b34_bitops`：临时值溢出，每轮 2 次无效内存往返

`(i << 3)` 算出来后要参与 `xor`，但分配器把它溢出到 `[rbp-0x58]`，
紧接着 `xor rax,[rbp-0x58]` 又读回来。同理 `[rbp-0x50]`。

**根因**：循环里 `acc`/`i` 占 2 个变量寄存器，7 个临时值抢 4 个临时池寄存器
（r8-r11），不够就溢出。要修得改分配策略（比如优先给"只用一次、但跨指令存活"
的值分配），风险较高。

### 2. `b35_branch`：qlmc 13 条 vs C 4 条

C 版本（clang -O2）做了**循环展开 + 分支内联**：把 `i&3` 的四种情形展开成
两个内层循环（连续 `add` 直到 `test al,3` 失败），每轮只 4 条。

qlmc 没有循环展开，所以每条 `if/else` 都要 `cmp` + `jcc` + 两个分支各自的
`jmp`。**这是结构差距，不是单条指令的问题** —— 要追上得做循环展开，
那是独立的一次改造。

## 已知边界 / 遗留

- `asm_audit.py` 的热循环识别只认"`cmp 大常数` + `jcc`"起头的形态，
  `b17_bubble`/`b28_matrix` 这类嵌套循环会匹配到外层或运行库循环（显示
  43 条、7%），**不代表它们真的只有 7% 浪费**。识别逻辑需要按"最深回边"改进。
- 只统计 3 类模式（store→load 同槽、`mov rX,rY`、循环指令数），
  没有覆盖分支布局、指令选择、向量化机会。
- 本轮没有性能提升。`b34` 的 45% 浪费是下一轮最明确的着手点。
