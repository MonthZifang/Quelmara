## 坏掉的部分与定位过程

stage-1 编译 qlmc 自己得到的 stage-2，**编任何程序都 rc=5 静默崩溃**
（连 `fn main() {}` 都不行）。但 stage-2 的 `dump` 与 `irdump` 都**正常**
—— 崩在**发射阶段**。

### 决定性对照实验

```
v3.62 的 stage-1  编 v3.65 源码 -> stage-2 能正常工作  ✅
v3.65 的 stage-1  编同一份源码 -> stage-2 坏了        ❌
```

同一份源码、同样大小（668160 B），但 `.text` 差 60 字节 ——
**是 v3.65 的 stage-1 在编译 qlmc 时生成了错误的机器码**。
这一步把"我的改动有 bug"和"wine 环境限制"彻底分开了。

### 反汇编对拍找到的具体差异

| VA | v3.62 s1 产物（对） | v3.65 s1 产物（错） | 含义 |
|---|---|---|---|
| `0x114c5` | `shl r9, 6`（×64） | `shl r9, 3`（×8） | `vec[Node]` 步长应为 64 |
| `0x1164d` | `imul r9, rsi, 0x38`（×56） | `shl r9, 3`（×8） | `vec[Fn]` 步长应为 56 |

**"vec 的元素类型被当成标量"** —— `_vtypes_elem` 返回的值让 `_ty_size`
走了 `return 8` 分支。

## 顺手修掉一个真 bug（但没解决问题）

`_ty_size` 里 `if ty >= TY_ENUM { return 16 }` **没有上界**，而
`TY_VEC(0x8000) > TY_ENUM(0x2000)`，所以 **vec 句柄被算成 16 字节**
（应该是 8）。

这个 bug 一直存在但从未暴露：调用 `_ty_size` 的地方传的一直是**元素**
类型（标量/struct/enum），从没传过 vec 类型。v3.65 让 `vec[vec[T]]` 合法
之后，`_vtypes_elem` 会返回 vec 类型码，立刻踩中。

已改成两头都卡（`>= lo && < hi`）。**但改完 stage-2 仍然坏** ——
说明还有第二个原因没找到。

> **教训**：区间判定必须两头都卡。只卡下界的写法在本项目里已经出过多次
> 问题（§7.18 的 `_ty_size`、v3.14 的 LICM readonly 判据）。

## 下一步该从哪查

1. 反汇编差异已定位到 VA `0x114c5` / `0x1164d`，**先从这两处反查是哪个
   函数的哪条 `vec[T]` 访问**（用 stage-1 的 `irdump` 对比同函数 IR，
   看 `BINI` 的 `imm` 是 8 而不是 64）；
2. 重点查**跨模块**：`_vtypes_add` 在 parse 期按模块顺序登记，而
   `TY_STRUCT + si` 里的 `si` 是**全局** struct 序号 —— 确认 lowering 期
   `_vtypes_elem` 读到的 `si` 与 parse 期写入的一致；
3. 实测一次 `VTYPES_BASE`（7217）与 `FMOD_BASE + NFN_MAX`（7217）的边界
   —— 算术上不重叠，但值得验证；
4. 怀疑 `_vtypes_str` 的 `exit(2)` 路径被绕过（stage-2 是 rc=5 不是 2）。

## 为什么回退而不是继续调

* 改动完整保存在 `git stash`（`stash@{0}`，154 行），**没有丢**；
* 半成品留在工作区会让下一次改动带着一个已知坏的基线；
* 这个缺陷需要**反汇编级的逐步对拍**，不是再调几轮能收敛的。

> **最重要的教训**：类型系统改动必须**先跑通 stage-2** 再谈覆盖率。
> 本轮 stage-1 全绿（40/40 差分 + 68/69 覆盖率 + 嵌套 vec 语义完全正确），
> 但 stage-2 坏了 —— 如果只看覆盖率就提交，等于把一个
> **编译器不能自举**的版本推上去。
> **`bootstrap_test --strict` 是这类改动的第一道门，不是最后一道。**
