- 日期：2026-10-22

## 为什么是 SHA-256

AES-GCM 做到 19 ms/MiB 之后，`06-status.md` 里最差的数字变成 SHA-256 的
**70 ms/MiB（15 MB/s）**。软件 SHA-256 的正常水平是 150–300 MB/s，差了一个数量级。

看代码发现根因很直白：**每轮调 6 次 `sha256_rotr`**（每块 64 轮 → 384 次调用），
再加每轮 1 次 `sha256_k`（6 层判定树）。1 MiB 要 737 万次函数调用。

## 实现要点

- **常量位移是免费的**：`sha256_rotr(x, n)` 里 `n` 是运行期参数，编译器只能生成
  "移位量在 CL"的变体（多一次寄存器搬运 + 依赖链）。内联成 `(x >> 6) | (x << 26)`
  之后位移量是立即数，还能被强度削减。
- **K 表没有可测收益**：改完 44 → 45 ms（噪声内）。保留的理由不是快，而是热路径
  不再有 6 层分支（分支预测更稳、代码更直）。这一点在下面"已知边界"里写明。
- 公开 API 没动：`sha256_block(state, block, w)` 与 `sha256_k(i)` 都还在，签名不变。

## §7.5 的归因修正（重要）

v1.33 把"`xmm_pxor(7,7)` 清零后 GHASH 全错"记成了"优化器把无结果指令当死代码删掉"。
这次查了 IR，**这个结论是错的**：

- `--dump-ir` 显示 `('xmm_pxor', -8, -8)` 完整保留；
- DCE 根本不会删它（条件是 `op in PURE and defs and ...`，无结果指令 `defs` 为空，跳过）；
- CSE 的 `_cse_key` 对 xmm 族返回 `None`，不参与去重。

所以真正的原因是 **§7.4 那一类**：多一条指令改变了寄存器分配/溢出决策，把某个
潜在的发射层缺陷暴露出来。这类 bug 的共同特征是"改动与症状无关"。已改写 §7.5，
并把 §7.4/§7.5 合并成下一轮的"分配器正确性"专项。

## 已知边界 / 遗留

- **只快了 1.6×，没到数量级**：剩下的是每轮的计算本身（8 个状态变量 + 若干临时量，
  寄存器压力大）。标准解法是 **8 轮展开 + 状态变量改名轮转**（消掉每轮 8 条搬移），
  预期再快 1.5–2×，但代码量 ×8、可能反而溢出，要实测。已登记 §5。
- **K 表是"整洁税"不是"性能税"**：44→45 ms，收益在噪声内。留着是因为热路径更直；
  如果哪天要省这 512 字节内存，删掉 `_sha256_ktab` 回到 `sha256_k(i)` 也完全正确。
- **HMAC 没动**：`hmac_sha256_*` 走同一个 block 函数，自动受益。
- **没有 SHA-NI**：本机 CPU 无该扩展（`cpu_sha()` 实测 0），所以这条路走不通。
