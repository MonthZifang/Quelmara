# v4.100 — `parfor` 引用外部变量时给出可操作诊断

- 日期：2026-11-10
- 任务：让 `parfor` 的失败可诊断（"无缝迁移"的可用性收尾）
- 影响面：编译器（解析期诊断）

## 问题：迁移时最常踩的坑，报错看不懂

单线程代码想并行化，最自然的改法是把 `for` 换成 `parfor`。但真实的循环几乎
都要读外部数据：

```qma
let a = vec[int].new(n)
// ... 填充 a ...
let mut total = 0
parfor i in 0..n reduce total { total = total + a.get(i) }   // ← 想这样写
```

原来报的是：

```
qlmc: 未定义变量 a
```

用户完全看不出这是 **`parfor` 的限制**，会以为是变量声明写错了 —— 而 `a`
明明就在上一行声明过。

## 改动：解析期检查 + 可操作诊断

新增 `_parfor_check_captures`：合成 worker 之前，先扫一遍循环体，把
"引用了、但不是本体定义、也不是循环变量/归约变量/函数名"的标识符挑出来。

现在的报错（带行号）：

```
qlmc: line 6: parfor 的循环体不能引用外部变量 `a`：
并行 worker 是独立函数，看不到外层的局部变量。
改写方式：把该值先拷进循环体能自己算出来的形式（例如用 `for` 串行），
或把整个计算包成一个顶层函数、用 `parfor` 之外的 `spawn` 手动分块。
```

## 为什么本轮**没做**自由变量捕获（诚实记录）

我先做了三天的尝试（`with (a)` 显式捕获列表），技术上卡在两道架构限制上：

1. **解析期没有类型信息**。`_ty_of_expr` 需要 `FnCtx`，只有降低期才有。
   所以没法自动推断要捕获的变量的类型 —— 形参一律写成 `TY_INT`，
   于是 `a.get(i)` 报"只有 vec 有 .get 方法"。
2. **编译顺序按函数下标升序**，而 worker 是解析期合成的，下标比调用方小 ——
   **worker 会先被编译**，那时父作用域的变量表还没建起来，回填进去的类型
   已经用不上了。

试过的解法与结果：

| 方案 | 结果 |
|---|---|
| 降低期从父作用域回填类型 | worker 已经编完，来不及 |
| `with (...)` 显式列捕获变量 + 回填 | `wf.np` 正确、`parfor-lower` 也走到了，但 worker 先编，仍报错 |
| 两遍编译（跳过 worker，第二遍补编） | `[pass]` 诊断根本没输出 —— 报错发生在编译循环之前 |

要真正绕开这两条，需要改编译流水线（延迟编译 + 类型表跨函数传递），
那是独立的一次改造，不是本轮能收尾的。

按项目纪律（**同一个方向连续多次修不好就换路**），本轮只把**诊断**做对，
并把上面三条尝试的结论写进这里，让下一轮不用重走。

## 已知边界 / 遗留

- **`parfor` 体仍不能引用外部变量**。这是本轮最大的功能缺口，也挡住了
  "真实业务循环直接并行化"（读容器是常态）。
- 已定位的两道拦路石（见上表），下一轮的入手点：
  - 让 `FnCtx` 能访问"调用方作用域类型"，或
  - 改编译流水线为"延迟编译 worker + 类型表跨函数传递"。
- `parfor` 块数 1:1 于核数，未做超核数细粒度切块。
- `parfor` 只支持 `acc = acc + expr` 形态归约。
