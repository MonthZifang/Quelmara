## 结果：整数部分通了，小数部分卡住

照 §7.26 的配方写了一个 `__f64_fmt(rcx = 缓冲, rdx = 源槽)` 运行库例程，逐段验证：

| 部分 | 状态 |
|---|---|
| `0` / `-0` → `0`；NaN → `nan`；±inf → `inf` / `-inf` | ✅ |
| 符号位判断（看位模式最高位，不靠浮点比较） | ✅ |
| 定点分支的整数部分（`u = (i64)(|x|*1e6+0.5)`、`ip = u/1e6`、走 `__i64_fmt`） | ✅ `100.0` → `100` |
| 去尾零（找 `e`、只删尾数、删掉孤立的小数点） | ✅ |
| **定点分支的小数部分** | ❌ |

小数部分的现状：把 `fp` 交给 `__i64_fmt` 打出来，**无论输入是什么都得到同一个常数**
（实测恒为 `536872`）—— 传进去的值是垃圾。已排除：

- `div` 之后 `fp` 存 `[rsp+0x50]` 再取回 —— `fp == 0` 的分支能正确跳过（`100.0` 走这条路），
  证明取回的值是对的；
- `mov rdx, rax` 的编码、`add rax, 1000000` 的编码（去掉这条结果一样）；
- 暂存区：换成"直接写进输出缓冲再左移一字节"，结果不变。

下一步该查 **运行库例程之间互相调用的寄存器约定**。`_gen_print_bool` → `RT_PSTR` 是唯一的先例，
可以拿它逐条对照（它只传一个 str 指针，我这里传 buf + 一个整数）。

## 这轮踩到的两个纯编码坑（已进坑表）

1. **`49 B9` 是 `mov r9, imm64`** —— 用 `_w32` 写立即数只会写 4 字节，后面的指令全被吃掉。
   现象：`1.5` 打印成 `1500000`（`u` 本身，除法根本没执行）。
2. **REX 前缀漏位**：
   - `lea r9, [rcx+r10±k]` 需要 `REX = W|R|X`（`0x4E`）。漏 REX.R 时**目的寄存器悄悄变成 rcx**。
   - `mov byte [rcx+r10], imm` 需要 `REX.X`（`0x42`）。漏掉时**索引悄悄变成 rdx**。
   这两处都不会报错，只是结果错 —— 手写机器码时"寄存器编号 ≥ 8 就要检查 REX 的每一位"。

## 为什么回退而不是留着半成品

`print(f64)` 打印出来的数字**必须是准的**，半成品比 fail-fast 更危险（用户会以为对）。
所以回退到 v2.39 的 fail-fast，把已经验证过的四段逻辑和卡点写进 §7.26，下次直接从那一段接手。
