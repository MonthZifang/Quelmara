# v2.41 — `map` 满表语义修正（`has` 不再杀进程）；发现「map 不扩容」是与 stage-0 的真分歧

- 日期：2026-10-25
- 任务：给 `map` 加扩容
- 影响面：自举层（`_map_*` 五个函数）/ 文档

## 先说结论

原本要做「map 扩容」，动手前先做了一轮对照实验，发现两件事：

1. **stage-0 的 `map` 会扩容** —— `map[int]int.new(2)` 塞 9 个键，全部正常存取。
   而 **qlmc 的 map 是固定容量**，第 3 个 `set` 直接死。**这是真语义分歧**，
   现有夹具没抓到是因为它们用的键数都没超过容量。
2. **stage-0 的 `map.get(缺失键)` 是 fail-fast**（打 `quelmara: map key not found
   (fail-fast)` 并退 1），而 `has(缺失键)` 正常返回 false。

扩容需要改布局（键值对从「内联在句柄后面」改成「独立数据块」，否则调用方手里的
句柄在扩容后仍指向旧块）。这一版试过整块改（`_map_base` 变读指针 + `_map_new` 分配
独立块 + `_map_slot_of` 满时返回 0 + `_map_set` 扩容），但**连不扩容的基础用例都崩了**，
代码已回退，细节与嫌疑点记在 07-gaps §7.27，下次从"最小用例 + 反汇编 `_map_new`"入手。

## 这一版实际留下的：满表语义修正（不改布局）

| 场景 | 改前 | 改后 |
|---|---|---|
| `has(k)` 在**满表**上查不存在的键 | **静默 `exit(1)`**（一次读操作干掉进程） | 正常返回 `false` |
| `get(k)` 在**满表**上查不存在的键 | 静默 `exit(1)` | `exit(1)`（对齐 stage-0 的 fail-fast 退出码） |
| `set(k,v)` 在**满表**上插新键 | 静默 `exit(1)` | `exit(2)`（与"编译期参数错误"区分开） |

做法：`_map_slot_of` 满时**返回 0**（不再自己 exit），由三个调用方各自决定怎么办。
这样"读操作把进程干掉"这个不合理的行为就没了 —— 这是这一版唯一的代码改动。

实测：

```
map.new(2) + set(1,11) + set(2,22)
  has(1) → 1     has(9) → 0     get(1) → 11      （满表上查不存在的键不再死）
  set(3,33) → 退 2
```
