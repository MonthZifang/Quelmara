## 结论：CSE 仍不启用，但根因从"未知"推进到"还剩一个"

本轮**没有代码改动**。但把 CSE 失败的原因查清了两层，前几轮一直停在第一层。

### 第一层根因（已修复并验证）：`use[]` 没跟着改

CSE 把 `MUL dst, a, b` 改写成 `MOV dst, hit` —— 操作数从 `a`/`b` 换成了 `hit`。
但 `use[]`（每个 vreg 被读几次）是**在这之前**统计好的，CSE 改完没调它。

后面的 `_opt_copy` / `_opt_dce` 拿过时的 `use` 做判断（比如 `use.get(d) == 1`
才做拷贝传播），于是做出错误优化。

**验证**：在 CSE 内部同步维护 use（`a`/`b` 各减 1，`hit` 加 1）之后，
`b49_floyd` 从 **0 变回 173（正确）**。

这条信息前几轮一直没查到 —— v4.93 记录里写的是"排查过 keys/vals 压缩失配、
`b` 槽非 vreg 两类，都修了但现象不变"，说明当时没往"分析数据失效"这个方向想。

### 第二层根因（未解决）：`b75_fib_matrix` 仍错

修好 use 之后，`b75_fib_matrix` 仍然是 **988098**（应 491479）。

缩小范围做了两个实验：

| 实验 | `b49_floyd` | `b75_fib_matrix` |
|---|---|---|
| 全白名单 + 维护 use | **173 ✓** | 988098 ✗ |
| 只留 `OP_MUL` + 维护 use | ✓ | 988098 ✗ |

**只留 `OP_MUL` 就能复现**，所以不是某类运算的特殊语义。

`b75` 的结构：

```qma
while n > 0 {
    if n % 2 == 1 {
        let t = (a0 * a1 + a1 * a3) % 1000003
        let u = (a0 * a2 + a1 * a3) % 1000003   // ← 与 t 共享 a1*a3
        ...
        a0 = t ; a1 = u                          // 改 a0/a1
    }
    let b1 = (a0 * a1 + a1 * a3) % 1000003      // ← 块外，表达式又相同
    ...
}
```

`a1 * a3` 在 `if` 块内出现两次（`t` 和 `u` 各一次），块外 `b1` 又一次。
块内改过 `a0`/`a1` 之后，块外的 `a1*a3` 必须是新值。

**怀疑点**：块内 `u` 复用 `t` 的 `a1*a3` 是对的（中间没改 `a1`/`a3`），
但 `a0 = t ; a1 = u` 这两条赋值之后，CSE 表里的 `(MUL, a1, a3)` 项
**应该失效而没失效**。失效逻辑写的是：

```qma
if ka == ins.dst || kb == ins.dst { 丢弃这项 }
```

`a1 = u` 的 `ins.dst` 是 `a1` 对应的 vreg，理论上应该命中 `ka == that`。
但 `a1` 作为**变量**在 IR 里可能有多个 vreg（每次 `E_VAR` 求值都可能新建），
所以 `ins.dst` 与表项里记的 `ka` 可能不是同一个编号 —— 这就是没失效的原因。

要验证这条需要打印"表项里 `ka` 的编号 vs `a1 = u` 的 `ins.dst` 编号"，
本轮时间用尽，留作下一轮的**第一个实验**。

## 顺带记一个坑：`cwd` 会让编译"假失败"

本轮多次出现"编译器报告写了 754176 字节，但文件不存在"。

原因是**在 `/root/Quelmara/Quelmara` 目录下把产物输出到 `/tmp/`**——wine 的
路径映射在这个组合下会静默失败，而编译器仍然打印成功信息。

**规矩**：跑 wine 时如果产物在 `/tmp`，就用 `cd /tmp` 作 cwd 并用绝对路径给源文件。

```bash
# 会假失败
cd /root/Quelmara/Quelmara && wine build/qlmc.exe build bootstrap/... -o /tmp/x.exe

# 正常
cd /tmp && wine /root/Quelmara/Quelmara/build/qlmc.exe \
    build /root/Quelmara/Quelmara/bootstrap/qlmc/qlmc.qma -o /tmp/x.exe
```

这个坑让我一度误判"CSE 破坏了编译器自举"，实际自举是好的（`FIXPOINT OK`）。

## 下一轮的第一个实验

打印 CSE 失效时"表项 `ka`/`kb` 的编号"与"写指令 `ins.dst` 的编号"，
确认 `a1 = u` 这类**变量赋值**为什么没让 `(MUL, a1, a3)` 失效。

如果确认是"同一变量有多个 vreg"导致，修法是：失效时不比对 vreg 编号，
而是比对**变量身份**（用 `fc.vloc` 反查，或记录"哪些 vreg 属于同一变量"）。

这个修法比之前所有尝试都更接近本质 —— 因为 CSE 需要的是
"**同一变量的所有 vreg 视为同一个内存位置**"，而这套非 SSA 的 IR 里没有这个信息。
