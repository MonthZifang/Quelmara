# v4.93 — LICM 第四次实现（正确）+ CSE 撤回记录

- 日期：2026-11-10
- 任务：优化最低性能项（`b28_matrix` 8.99×、`b22_knapsack` 8.83×…）
- 影响面：编译器（优化 pass）

## 结果先说：**本版没有性能收益**

LICM 做了四版终于正确，但实测收益为 0 —— 循环里真正"不变"的值本来就不多。
CSE 发现了真问题（`b28` 内层有 2 次冗余 `imul` + 3 次无用 store/load），
但三版修复都没修对，已按项目纪律**撤回**。

## LICM：四次迭代，把判据从"错的"逼成"可证明的"

前三版都被 checksum 打回。每一步的错误都是真实的语义理解偏差：

| 版本 | 现象 | 根因 |
|---|---|---|
| v1 | `b1_int` 的 acc 归零 | 判据"操作数在循环头之前有定义"对**非 SSA** vreg 不成立 —— 累加器在循环里反复重定义，但在头部之前也有定义 |
| v2 | `b11_nqueens` 184000 → 36000 | 补了"循环内 dst 集合"，但**内存写**（`col.set(r,c)`、聚合字段）改的不是 vreg，dst 集合看不见 |
| v3 | `b28_matrix` 960991321 → 326563275 | 判据漏了"外层循环变量"：`r` 在外层循环里定义，对**内层**循环不是不变量 |
| v3.1 | `b11_nqueens` 仍错 | **形参**（`OP_PARAM`）在每次调用（尤其递归）时拿到新值，被判成不变量 |
| **v4** | **全部正确** | 加上"定义点不能落在任何包含本循环的外层循环里"（`_licm_in_outer_loop`）+ 排除形参 |

### v4 的判据（可证明）

`v` 相对循环头 `h` 不变，当且仅当：

1. `v` 不在本循环 `(h, e]` 内被定义；
2. `v` 的**每一处**定义都满足：
   - 不在本循环内；
   - 不被任何**包含 `h` 的外层循环**包住（否则每个外层轮次都会重算）；
   - 不是 `OP_PARAM` / `OP_PARAMSTK`（形参每次调用都变）。
3. 只对 `_licm_arith` 白名单（纯算术，不含 MOV/CONST/任何访存）做外提。

最后一条是关键：**纯算术 + 不跨外层循环**，从根上绕开别名问题。

### 为什么收益是 0

`b28_matrix` 内层循环里看起来"该提"的 `r*n` —— 它的 `r` 正是外层循环变量，
按正确语义**不能**提。提了就是 v3 的 checksum 崩溃。剩下真正循环不变的值
（如 `n`）本来就只有一两条 `mov`，提上去省不了什么。

**这是必要条件，不是充分条件**：正确性约束把大多数看似可提的表达式排除了。

## CSE：发现了真问题，但没修对，已撤回

`b28_matrix` 内层循环（`401492`–`401558`）里 `r15*n` 被算了**两次**
（`40149e` 与 `4014fd`），每次都是 `imul` + 一次 `[rbp-0x170]` store/load 往返。
这是标准的 CSE 缺口。

实现了局部 CSE（同基本块、纯算术、键 = `(op,a,b,imm)`），但：

- 第一版：`b49_floyd` checksum 5994 → **0**。怀疑 keys/vals 压缩失配，修了。
- 第二版：现象不变。怀疑 `OP_BINI`/`OP_DIVC` 的 `b` 槽不是 vreg 导致键冲突，修了。
- 第三版：**现象仍不变**。

连续三次"修了一个怀疑、现象不变"，说明对这套 IR 某条语义的理解仍有偏差。
按 `docs/07-gaps.md` 的纪律（**现象没解释清楚就不留在树上运行**），
CSE 从流水线移除；`_opt_cse` 实现保留在源码里但标注撤回，供下一轮定位。

## 已知边界 / 遗留

- LICM 正确但无收益。要真降 `b28` 的 9× 差距，CSE 是更对的方向 —— 但需要先
  把"为什么 CSE 让 floyd 归零"搞清楚，建议下一轮先做 IR dump 逐条对比。
- `b28` 慢的根本原因可能不止缺优化：`vec` 是**双重间接**（句柄 → data 指针
  → 元素），C 只需一次寻址。这个结构性差异靠 pass 吃不掉，要改内存布局。
