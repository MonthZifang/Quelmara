# v3.76 — WS E2E 偶发失败：三个独立缺陷叠在一起

- 日期：2026-11-02
- 任务：收 §7.45（CI 上连续三次红在 windows 的同一条用例）。
- 影响面：`std/ws.qma`、`std/net/core.qma`（部分写入）、
  `tests/run_win_tests.py`（失败摘要）、`tests/ws_e2e_test.py`（多读字节）
- 代码改动：约 70 行

## 这一条耗了很多轮，因为"失败点"一直是错的

### 缺陷一：失败摘要按**位置**截断

`tests/run_win_tests.py` 的 `test_ws_e2e` 直接截 `r.stdout[-400:]` 拼进
失败消息。而 e2e 脚本的 stdout 里最后 400 字节往往只装得下后面几条
`[PASS]`，真正的 `[FAIL]` 行在更前面被截掉。于是 CI 日志显示：

```
[FAIL] WebSocket E2E 失败 rc=1 同掩码 key 都能正确解出明文
```

"同掩码 key 都能正确解出明文"是用例 [5] 的**通过**文案。连续几轮排查
全围绕用例 [5] 的掩码解算展开 —— 方向从一开始就是错的。

**修法**：先挑出所有 `[FAIL]` 行再拼消息（`test_ws_e2e` / `test_sse_e2e`
都改）。

> 截断日志做失败摘要时，截的是"最后 N 字节"，不是"失败相关的那些行"。
> 只要 PASS 比 FAIL 多、且 PASS 在后面，截断就必然误导。

### 缺陷二：`send()` 部分写入没人管 —— 帧会被截断

`std/ws.qma` 的 `_ws_frame_raw` 与 `std/net/core.qma` 的 `conn_send`
都只调一次 `tcp_send_n` 就把返回值交给调用方。而 `tcp_send_n` 是
`send()` 的直接包装，**内核发送缓冲区快满时可以只写一部分**。

`_ws_frame_raw` 更糟：发完就 `mem_free(buf, total)`，剩余字节直接丢失。
对端收到半截帧，`recv_frame` 永远等不齐 → 超时。

**修法**：两处都循环到写满，指针按已写字节数前移；`w <= 0` 立即跳出。

**效果**：失败率从约 25%（4 轮 1 次）降到约 2%（49 轮 1 次）—— 改善明显
但**没消失**，说明还有第三个原因。

### 缺陷三（真正的根因）：握手时多读的字节被丢弃

`tests/ws_e2e_test.py` 的 `handshake()` 用 `read_until(b"\r\n\r\n")` 收
响应，而 `recv(4096)` 一次可能把 `101 响应 + on_open 推送帧` **一起**读
进来 —— 多出来的那段在返回值 `rest` 里。但 `main()` 里：

```python
status, hdrs, rest, key = handshake(sock)   # rest 被赋值后直接丢弃
```

`recv_frame` 于是从 socket 重新读，而帧头已经被 `read_until` 吃掉，它等的
是一个永远凑不齐的帧 → 5 秒超时。

**这不是服务端的问题，是测试客户端的问题。** 101 与 on_open 是否落在同一
个 TCP 段取决于内核怎么分段，所以约 2% 的连接会中 —— 与"偶发"完全吻合。

**修法**：`rest` 存进模块级 `_LEFTOVER`，`recv_frame` 的 `rd()` 先消费它
再读 socket。

## 验证

| 判据 | 修复前 | 修复后 |
|---|---|---|
| 连续 40 轮 WS E2E | 预期约 1 次失败 | ✅ **0 次失败** |
| 失败率（缺陷二修完、缺陷三未修时） | — | 约 2%（49 轮 1 次） |
| 失败率（缺陷二未修时） | 约 25%（4 轮 1 次） | — |

`std/ws.qma` 与 `std/net/core.qma` 均能被 qlmc `-lib` 编过。

## 为什么这一条值得记

三个缺陷叠在一起，且**第一个（误导性日志）让后两个无法被发现**。修掉第二个
后失败率从 25% 降到 2%，这个"改善但不消失"的信号才是继续挖第三个的线索 ——
**如果当时接受了"降到 2% 就够了"，根因永远不会被找到。**
