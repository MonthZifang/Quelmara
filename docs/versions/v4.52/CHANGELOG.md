# v4.52 — 16 字节 movdque memcpy 终于落地：真凶是 labs 容量边界

- 日期：2026-11-05

  与 movdqu 指令**无关**的真因。
- 结论：**已修复并落地**，自举 42/42 + RT 3/3 + 差分 110/110。

## 五轮失败的真凶：`ctx.labs` 预分配容量边界

16 字节版需要 5 个标签（lX/lq/lqloop/lb/ldone），原 8 字节版 3 个
——**多 2 个 `_newlab`**。而主编译路径的 `ctx.labs = vec[int].new(64)`
预分配 64 槽，运行库标签总数恰好压在边界上：多 2 个标签触发 vec
扩容路径，**生成期**某处（labs 邻接 vec 被踩 / grow 后读旧块）让
fix 回填拿到垃圾 → 产物错 → stage-2 rc=1。

### 变体对照（每轮一次构建，二分闭环）

| 变体 | 内容 | 自举 |
|---|---|---|
| F | v4.50 原样 + sub/add rsp,24 | ✅ 42/42 |
| G | F + 10 字节 nop（纯变长） | ✅ 42/42 ← 长度无关 |
| I | F + 仅 2 个 `_newlab`（不发射代码） | ❌ 0/42 ← **标签数触发** |
| J | I + labs 容量 128 | ✅ 42/42 ← **容量边界实锤** |
| H | 16B + and rcx,7（labs 64） | ❌ 0/42 |
| 最终 | 16B + and rcx,7 + labs 128 | ✅ **42/42** |

变体 I 是关键一刀：**不加任何代码、只多占两个标签 id** 就崩——
彻底排除指令语义（movdqu/REX/xmm/尾部掩码全部无罪）。

### 修复

1. `ctx.labs = vec[int].new(128)`（规避容量边界）
2. 16 字节段：`movdqu xmm0,[r9]` / `movdqu [r8],xmm0`（REX 在 legacy
   prefix 之后、xmm0 保存恢复、lX/lq/lqloop/lb/ldone 五标签）
3. 尾部保持 `and rcx,7`（qword 段已消耗 16k+8q，尾部=n%8；
   `and rcx,15` 会多拷 8q——旧尝试的另一处真 bug，一并修正）

### 验证

* RT 单测 3/3（含 37 字节尾部：4 qword + 5 字节）
* 自举五级链 42/42 + 不动点 4.8s
* 差分 110/110
* 校验和：b31=12499999 / b28=960991321 / b23=1498 / b82=9999999

## 遗留（记录在案）

**vec 扩容在生成期的深层问题**：为什么 `labs` 多 2 个标签会踩坏
生成期状态？候选：vec.grow 的 realloc 与相邻 vec（ctx 字段相邻）
交互、grow 后旧块读取。这是 **vec 运行时实现的潜在 bug**，影响
任何"接近预分配容量"的 vec —— 本次用 128 规避，但根子问题需要
单独一轮：给 vec.grow 写压力测试（RT 通道）。

## 追加：vec.grow 压力测试 —— 否定 grow-stale 假设

`tests/rt/vec_grow_stale.qma`：vec.new(4) 经 fill() push 300 项
