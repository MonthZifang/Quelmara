# v3.25 — 核实 `static_word(0)` 的共享：不是隐患，是既有语义

- 日期：2026-10-30

- 影响面：**只有测试与文档**（新增 `tests/t176_slot0_share.qma`，

## 上一版留下的说法

v3.23 的登记表把 `static_word(0)` 记成 http / ws / sse **共享**，
`07-gaps.md` §4.2 里留了一句：

> 三者同时在跑时会互相覆盖。要真正支持并发多协议得改成连接表，
> 那是另一个量级的改动。

这句话听着合理，但**没有验证过**。v3.24 的教训是"先写探针实测，
再决定改不改代码"，所以这一版照做。

## 核实分三步

### 1. 三个框架的状态块布局相同吗？

看源码，三个都是：

```quelmara
let st = conn_state_new(max_conns, 80)
mem_store64(static_word(0), 0, st)
```

`std/http.qma:118`、`std/ws.qma:75`、`std/sse.qma:45` 一模一样。
所以不存在"按 A 的布局读 B 的块"这种结构性错误 —— 共享在**结构上**安全。

### 2. 两个服务能同时在跑吗？

不能。`net_serve`（`std/net/reactor.qma`）的 acceptor 在**主线程**上：

```quelmara
while true {
    let c = _accept(s, 0, 0)
    ...
}
```

永不返回。所以进程内**起不了第二个服务** —— 第一次调用就把主线程占死了。

### 3. 那么 slot 0 的语义是什么？

"最后写入者获胜"。这跟 `net_serve` 的单实例语义**一致**，
不是共享槽额外引入的风险。

## 结论：不改实现

`static_word(0)` 的共享是**正确**的。原来那句"要改成连接表"是过度保守 ——
真要做多端口/多协议并发，卡点不在 slot 0，而在 `net_serve` 本身是单实例的
（`R_STATE_W` 也只有一个槽）。那是一项独立的大改动，不属于"槽位分配"范畴。

这一版的产出是**把判断钉住**：

- `tests/t176_slot0_share.qma` —— 验证槽位是"最后写入者获胜"，
  且覆盖槽位不会改坏两个状态块自己的内容（共享安全的**结构前提**）。
- 门禁加 `SHARED_LAYOUT`：共享槽位必须**证明布局一致** —— 声明所有共享者
  都要调用同一个构造函数（slot 0 = `conn_state_new`），门禁逐个模块检查。
  共享未声明布局、或某个共享者没调那个构造函数，都判失败。
  这样"共享"不再是文档里的一句话，而是可执行的约束。
- `07-gaps.md` §4.2 改写：从"待改的隐患"变成"核实过的既有语义"，
  并写清真正的卡点在哪。
- `02-language.md` 的槽位表第 0 行补上核实依据。

## 一个方法论上的提醒

v3.23 写那句"得改成连接表"的时候，`static_word` 的抢槽问题刚修完，
顺手就把 slot 0 也归进"待办"了 —— **共享**和**抢槽**是两件事：

| | 抢槽 | 共享 |
|---|---|---|
| 定义 | 两个模块**互不知情**地用同一个号 | 多个模块**约定**用同一个号，语义一致 |
| 判据 | 布局不同 / 用途不同 | 布局相同 + 生命周期不重叠 |
| 处理 | 必须改 | 登记 + 声明布局即可 |

门禁的 `REGISTRY` 用"模块列表"表达共享，但当时**只登记了归属、没校验布局**
—— 于是"共享"仍然可能悄悄退化成"抢槽"。v3.25 补上的 `SHARED_LAYOUT`
就是这个缺口的闸门。
