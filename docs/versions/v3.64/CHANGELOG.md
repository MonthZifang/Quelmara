## §7.18（`vec[vec[T]]`）：量化后确认"顺手做"是错的

**改动面**：`TY_VEC` 在 `bootstrap/qlmc/qlmc.qma` 出现 **23 处**：

| 形态 | 处数 | 风险 |
|---|---|---|
| `ty - TY_VEC` 取元素 | 7 | 类型码自描述的直接后果 |
| `>= TY_VEC && < TY_xxx` 区间判断 | 8 | **依赖类型码全序** |

**最容易想到的方案是错的**。我算过三条路：

| 方案 | 结论 |
|---|---|
| 把 `TY_VEC` 搬到 `0x100000000` | ❌ 破坏全序，**8 处判断静默失效** |
| 元素类型压进低 12/13 位 | ❌ `elem` 可能是 `TY_ARRAY`（`0x100000`），装不下 |
| 给嵌套 vec 单开标记 `0x9000` | ❌ 撞 `vec[struct si>=16]`（`0x8000+0x1010`） |

现在的全序是 `TY_VEC(0x8000) < TY_MAP(0x10000) < TY_SLICE(0x20000) <
TY_FN(0x30000) < TY_ARRAY(0x100000)`，而 `_lower_method` 里写着
`hty < TY_VEC || hty >= TY_SLICE`（`for k in` 只接受 vec/map）。
**搬 `TY_VEC` 会让这类判断全部走错分支，且不报错。**

**正解**：改成"类型表下标"（`TY_VEC = 0x8000 + ti`，`ti` 索引 `fc` 里的
类型表），嵌套退化成一次查表。但这要求 `TY_MAP` 的 K/V 同步改造 ——
**是一次类型系统重构，不是补丁**。

已在 §7.18 补上 **6 步检查清单**（含"注意保持全序不变"这条硬约束）。

## §7.44（泛型）：不是"支持不完整"，是**完全没有**

新增条目。最小复现与 `std/gen` 无关，纯语法：

```quelmara
fn pick[T](a: T, b: T) -> T { return a }
→ qlmc: line 1: 期望标点 #1
```

`#1` 是 `P_LPAREN` 的编号 —— parser 在 `fn 名字[` 之后期望 `(`，
看到 `[` 就报错。**`std/gen` 的报错在第 24 行、也就是第一个泛型函数声明处，
后面 80 行根本没被解析。**

stage-0 从 v1.36 起有完整泛型（多类型参数 + 推导 + 四种能力约束 +
泛型 struct/enum/method 的解析期单态化），qlmc 一样都没有。

已补 **5 步检查清单**，并写明与 §7.18 的**耦合**：`vec[T]` 一旦要支持嵌套
就同时踩 §7.18 —— 做泛型时 `std/gen` 里凡是 `vec[T]` 的形状仍会失败。

## 优先级建议

**先做 §7.18，再做 §7.44。** 理由：

* §7.18 解开的是**已写好的库**（`std/csv`，142 行，逻辑完整）；
* 泛型要从零造一个子系统（parser + 单态化 + 约束），而 `std/gen` 只有
  103 行 / 10 个函数；
* 两者耦合，先做类型系统那块，泛型才有地基。

> 顺带记一条**取舍**（不替项目负责人决定）：`std/gen` 手写成非泛型版本
> 的成本远低于实现泛型。但那是"绕过缺口"而不是"修缺口" —— 要不要这么做
> 是产品决策，不是技术决策。
