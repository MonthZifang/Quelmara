# v2.98 — parfor 归约的概率性错误：clone 分流前写共享 pid 表

- 日期：2026-10-28
- 任务：修正确性 —— `examples/parfor_sum.qma` 有 ~2/60 概率算错
- 结论：**不是浮点、不是优化器**，是 `clone()` 之后**父子双方都执行了一条本
  该只有父线程执行的 store**。修复后同形状压测 **0/500**；旧二进制对照 **22/300（7.3%）**。

## 怎么发现的

v2.97 跑完整回归时 `[4] parfor_sum 多核` 偶发报错：

```
❌ 输出 [8640000635]      # 正确值 11519999978
```

差值 `11519999978 − 8640000635 = 2879999343` —— 正好是**一个 chunk 的和**
（6_000_000 / 4 核 = 1.5M 个元素的 `heavy()` 累加）。这不是"算错"，是
**少合了一个分片**。

## 排除法

| 假设 | 检验 | 结论 |
|---|---|---|
| v2.97 引入 | v2.97 只动 std/x509 与文档 | 无关（该跑也确实在 v2.96 上复现） |
| 内联阈值 60 引发（v2.93 的老问题） | th28 = 2/120、th60 = 3/120 | **同复现率**，与内联无关 |
| worker 被内联砸父栈 | worker 有 `no_inline=True`（v1.4 起） | 已被防护 |
| 归约槽本身有竞态 | 每 worker 写自己的 `out[tid]`，无共享读 | 不成立 |

复现率：单独跑 1/60～3/120；当压测跑满 300 次是 **22/300（7.3%）**。
且**差值恒等于一个 chunk**——指向"某个 worker 的结果没被等到"。

## 根因：`clone()` 返回后父子同名一段指令流

`lower_parfor` 的 POSIX 分支原本是：

```python
fn.emit("syscall", pid, clone, [...])
fn.emit("store", ("ga", pid_gid), ("imm", t), pid)   # ← 父子都会执行
l_child, l_after = ...
fn.emit("jz", pid, l_child)
```

`clone()` 是**一次返回两次**：父得到子 pid（>0），子得到 **0**。两者从
**同一条指令流**继续。那条 `store pid_gid[t] = pid` 因此被执行两遍：

- 父：写进真 pid；
- 子：写进 **0**，且因为 `CLONE_VM`（`0x511`）`pid_gid` 是**共享内存**，
  这是一次真实的跨线程写。

只要子线程抢在父前面（或父子交错），`pid_gid[t]` 最终是 0。join 阶段：

```python
wait4(pid_gid[t], ...)     # 拿 0 -> wait4(0) 是"收任意一个子进程"
```

于是**先退出的另一个 worker 被这个槽收走**，轮到它自己的槽时已无子可等
（`wait4` 立刻返回 ECHILD，代码没检查返回值，静默继续）。随后归并读到那个
**还在跑**的 worker 的 `out[t]`——它还没写，是 0 → 少一个分片。

差值恰好一个 chunk、复现率与调度相关、与优化无关，三个观测全部对上。

## 修法

把 pid 登记挪到**父子分流之后**，只在父路径执行：

```python
fn.emit("syscall", pid, clone, [...])
fn.emit("jz", pid, l_child)        # 子线程立刻跳走
fn.emit("jmp", l_after)
fn.emit("label", l_child)
...
fn.emit("label", l_after)
fn.emit("store", ("ga", pid_gid), ("imm", t), pid)   # ← 只有父到这里
```

同型审计：`spawn` 与 `thread_start` 的 clone 段**没有**这个问题——它们在
分流前只写新栈的私有槽（`st[(STACK_SZ-264)//8]`），那是 clone 前完成的、
且不共享。AArch64 后端无线程实现、Windows 走 `CreateThread` 无 fork 语义，
**竞态只存在于 x86-64 POSIX parfor 这一处**，而它就在共享的 `Lower` 里，
一处修复覆盖两架构的发射路径。

## 验证

| 项 | 结果 |
|---|---|
| 修复后压测 | **0 / 300**（另一次 0 / 200，合计 **0/500**）|
| 旧二进制对照（同机、同形状，300 次）| **22 / 300 = 7.3%** |
| `run_native_tests.sh [4]` 新增哨兵 | 10 连跑（单跑只有 ~2% 检出率，10 连跑把它抬到 ~20%，代价 ~20 s） |
| 完整 native 回归 | 见下（本轮实跑） |

## 为什么它是"长期潜伏"而不是"新引入"

`pid_gid` 的 store 从 parfor 有这个后端起就在分流之前（`git log -S` 可追到
初版）。它之所以一直没被抓住，是因为**单次运行约 7% 概率出错**，而每次发版只跑
一次回归：93% 的把握判绿，实际是红的。这类缺陷不能靠"跑一次绿了"证明不存在——**要么压测，要么
让门禁多跑几次**。本版两件都做了。

> 同类教训在 `docs/00-convention.md` 里已有先例（"单点核对全对 ≠ 装起来对"）。
> 这次补的是另一面：**概率性错误不能用单次绿证明修好**。
