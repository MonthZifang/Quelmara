# v2.48 — 常数除法魔数乘法：`b1_int` 快 4.8 倍

- 日期：2026-10-25
- 任务：严重优化性能与加速比（攻 §7.31 的头号瓶颈：`idiv`）
- 影响面：自举层（新增 `OP_DIVC` + `_emit_divc`）/ 基准 / 文档

## 上一轮为什么没做

有符号魔数（Granlund–Montgomery）的推导我验不到项目要求的强度。一个具体的反例：
`d=3` 用 `M = ceil(2^64/3)`、`s=0` 在 14 个采样点上全过，但误差项
`e = M*d - 2^64 = 2`，而充分条件要求 `e*(2^64-1) < 2^64`（即 `e ≤ 1`）——
**小样本"通过"是假的**。`%` 算错是静默错值，比崩溃危险，所以上一轮宁可不做。

## 这轮换了可证明的构造

**不用有符号魔数，用「无符号魔数 + 显式符号分离」。**

记 `d ≥ 2`、`l = ceil(log2 d)`、`s = l-1`、`m = ceil(2^(64+s)/d)`、`e = m - 2^(64+s)/d`。
对 `0 ≤ u ≤ 2^63`：

```
floor(u*m / 2^(64+s)) = floor(u/d + u*e/2^(64+s))
u*e/2^(64+s) ≤ 2^63 * e / 2^(64+s) = e/2^l < 1/2^l ≤ 1/d
```

扰动**永远跨不过整数边界**，所以 `floor(u*m/2^(64+s))` 严格等于 `u/d`。
（`e < 1` 严格成立：`d` 是 2 的幂时 `e = 0`，否则 `e` 是分数。）

于是：

```
x/d  = sign(x) * floor(|x|/d)          （向零截断）
x%d  = x - (x/d)*d
```

**这一步是可证明的**，不依赖任何推导技巧 —— 这是和上一轮的本质区别。

## 验证（8.4M 个采样点，零失败）

| 范围 | 采样 |
|---|---|
| `d = 2..2000` | 每个 d 用 16 个边界值（`0/±1/±d/±(d±1)/±2^62/±(2^63-1)/-2^63`）+ 2401 个全小范围（-1200..1200）+ 200 个全范围随机 |
| 8 个关键除数（3/7/13/100/1000/9973/2^31-1/2^32+1） | 各 402 417 个 x（400k 全范围随机 + 全小范围穷举 + 边界） |
| `m` 的编译期算法 | 验证"用 int64 回绕算"与"用大整数直接算 `ceil(2^(64+s)/d)`"在 `d=2..2000` **完全一致** |

## `m` 怎么在编译期算（`2^64` 装不进 int64）

```
floor(2^63/d) = -(INT64_MIN/d)      // 有符号除法对负数向零截断，正好等于 -floor
r63 = INT64_MIN - q63*d             // 利用 int64 回绕得到正确的正余数
q64 = 2*q63 + (2*r63)/d
r64 = -(q64*d)                      // 回绕
m   = (q64<<s) + ((r64<<s) + d - 1)/d
```

全程允许回绕 —— 我们要的就是模 `2^64` 的值。

## 发射序列

`x / d`（13 条）：

```
mov    rcx, x            ; rcx 全程保留 x（取模要用）
mov    rax, rcx
sar    rax, 63           ; sign
mov    rdx, rcx
xor    rdx, rax
sub    rdx, rax          ; rdx = |x|
mov    rax, rdx
movabs rdx, m
mul    rdx               ; rdx:rax = |x| * m（无符号）
mov    rax, rdx          ; 取高 64 位
shr    rax, s
mov    rdx, rcx          ; 重算 sign（x 还在 rcx）
sar    rdx, 63
xor    rax, rdx
sub    rax, rdx          ; q
```

`x % d` 再加三条：`imul rax, rax, d` / `sub rcx, rax` / `mov rax, rcx`。

只有 `RAX`/`RDX` 被毁，`RCX` 保留 `x` —— 这样取模不用额外寄存器。

## 结果

同一工作量（4000 万次）下的前后对比：

| 基准 | v2.47 | **v2.48** | 变化 |
|---|---|---|---|
| `b1_int`（2000 万次） | 203.3 | **41.6** | **−80%（4.9 倍）** |
| `b8_threads1`（4000 万次） | 406.8 | **84.0** | **−79%（4.8 倍）** |
| `b8_threads4`（4 × 1000 万次） | 109.2 | **31.7** | **−71%** |
| 其余 8 项 | — | — | 噪声内（除法不是它们的瓶颈） |

比预估的 2 倍好很多 —— 说明 `idiv` 的实际代价比"30 周期"更重（它堵住除法单元，
还会拖累后面的迭代）。

### 顺带发现：并发基准的"尺子太短了"

`b8` 变快 4.8 倍之后，4000 万次口径只剩 **21 ms/线程**，而 4 线程的固定开销
（线程创建 0.86 ms + 调度/降频）约 10 ms —— 加速比从 3.72× 掉到 **2.65×**。
这**不是并行变差**，是工作量太小了。

实测同一程序在 1.6 亿次口径下加速比是 **3.75×**（单线程 381.0 → 4 线程 101.7）。
所以把 `b8` 的工作量从 4000 万提到 **1.6 亿次**（4 线程各 4000 万），让这个指标
重新有意义。同一工作量下：qlmc **3.75×** / C 1.76× / Go 3.59× / Python 0.91×（GIL）。

C 的加速比反而最低，因为它单线程只要 95.7 ms，4 线程时的降频与争用占比更大。

**40 个校验和全部不变**。

## 限制（写在代码注释里）

- **除数必须 2..2^31-1**。再大 `2^s*r64` 会溢出 int64（`r64 < d`、`2^s < d`，
  所以 `2^s*r64 < d^2`，d ≤ 2^31 时 < 2^62 安全）。超范围保持 `idiv`。
- `d = 1` 上面已经化成 `MOV`；`d ≤ 0` 保持 `idiv`（符号要另外处理）。
