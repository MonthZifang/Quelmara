## 主结论：这条崩溃不在 qlmc 的代码里

上一版把 §7.25 记成"qlmc 的错误路径崩溃"。这轮追到底，定性变了：

**`qlmc.exe`（stage-1）是 stage-0 编出来的** —— 它跑起来的代码是 stage-0 的产物。
所以那条崩溃落在 **stage-0 的 codegen** 上，不在 qlmc 自己的后端里。

对照实验（同一个输入，两个编译器）：

| 输入 | stage-1（stage-0 的产物） | stage-2（qlmc 的产物） |
|---|---|---|
| 未定义函数 | rc=2 ✓ | rc=2 ✓ |
| `import` 找不到模块 | rc=2 ✓ | rc=2 ✓ |
| **解析错误（`let x =`）** | **rc=139 ✗** | **rc=2 ✓** |
| **未知类型** | **rc=139 ✗** | **rc=2 ✓** |

也就是说：**qlmc 自己的后端在错误路径上是正确的**，退化的只有 stage-0 的产物。
这是个挺有意思的结果 —— 自举出来的编译器在这里比引导它的那个更好。

## 为什么之前四轮"修法"都白试了

因为我在改 **qlmc 的源码**（= 改 stage-0 的输入），而不是改 stage-0。
每次改动都会改变 stage-0 生成的代码布局，于是 rc 在 139 与 2 之间跳 ——
看起来像"布局敏感"，其实是**改了错误的那个编译器**。

试过并回退的四个变体（都是布局运气，一个都没留）：

| 变体 | 结果 |
|---|---|
| `eprint(<表达式>)` 原样 | rc=139 |
| 消息先落变量 `let m = …; eprint(m)` | 时好时坏 |
| 换成 `print`（stdout） | 时好时坏 |
| `__eprint_str` 去掉第二次写换行 | 时好时坏 |
