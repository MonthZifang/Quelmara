# v3.97 — 修 `RT_CGT`/`RT_SYSCALL` 破坏 RSI/RDI（§7.50 的 A）

- 日期：2026-11-03
- 任务：查 `b13_collatz` 段错误（v3.96 遗留）。
- 结果：**找到并修好**，`b13` 主结果正确；但暴露了同族的第二个缺陷（B，未修）。

## 缺陷 A：syscall 例程破坏了变量寄存器

`_gen_cgt_elf` 与 `_gen_syscall_elf` 直接用 `rdi`/`rsi` 传内核参数。
但 **`RSI` 和 `RDI` 是变量寄存器池的第 6/7 个**（v2.51 加进来的）——
调用者完全可能把变量放在那里，于是调用返回后变量被静默改掉。

**症状极有迷惑性**：

| 形态 | 结果 |
|---|---|
| `if` 里单条赋值 + `now_ns` | ✅ |
| `if` 里**两条**赋值 + `now_ns` | ❌ 段错误 |
| `if` 里两条赋值，**无** `now_ns` | ✅ |

只有"多一个活跃变量"时才会用到第 6/7 个寄存器，于是恰好踩到。

**修法**：`push rdi / push rsi` → 传参 → `syscall` → `pop rsi / pop rdi`。

顺带修了 `_gen_alloc` 的 `mmap` 分支：它破坏 `rdi`/`rsi`/`r8`，而
`_gen_alloc` 只保存了 `VirtualAlloc` 的破坏集合（`rcx/rdx/r9/r10/r11`）。

### 为什么 PE 侧一直没暴露

PE 的 `now_ns` 走 IAT 调用（`QueryPerformanceCounter`），形状完全不同，
且 `RT_*` 约定里 PE 的运行库例程本来就不碰 `rsi`/`rdi`（v2.51 加寄存器时
专门审计过那 3 个例程）。ELF 是我新写的，没做这层审计。

**教训**：往运行库加例程时，必须核对该例程用到的寄存器**是否在
`_cs_reg` 的 7 个变量寄存器里**。这条规则 v2.51 就写进文档了，
但新写代码时没对照。

## 顺带修：`b15_loopsum` 基准本身是错的

原来写的是 `s = s + i`，GCC `-O2` 直接把它折叠成闭式解（C 只要 0.1 ms，
qlmc 要 264 ms —— 那不是语言差距，是基准写错了）。

改成依赖链（`x = (x*31+i) | 1; s += x & 1023`），三语言同步改，
现在 C 和 quelmara 都输出 `102300000512`，量级可比。

## 发现的缺陷 B（未修，已登记 §7.50）

修好 A 之后 `b13` 主结果正确了，但**计时是负数**。追下去发现：

```
t0 = 496984376801797   ✅
x  = 4199136           ❌（= 循环耗时）
y  = 1                 ❌
t1 = 496984377995391   ✅ 又对了
```

IR 层：`buf`（vreg 2）住 R8，`RT_CGT` 之后 `LOAD dst=5(r8) a=2` **就地覆盖了
R8**，而后面 `LOADD a=2` 还要用 `buf` 读 nsec —— 此时 R8 已经不是 buf 了。

**这是活跃区间分析（`vstart`/`vend`）的缺陷**，不是发射器。寄存器够用时
`buf` 和 `dst=5` 会分到不同寄存器；池子被挤时分配器就复用了同一个槽。
