# v2.56 — 打破 SSE 假依赖 + f64 字面量进帧常量槽（b2_float 再快 1.5 倍）

- 日期：2026-10-26
- 任务：v2.55 把 f64 搬进 XMM 之后，**CI 上的比值只从 8.5× 降到 4.0×**，
  而本机是 1.5× —— 差距这么大说明还有别的东西在拖。查下去是 **SSE 的部分
  寄存器写造成了跨迭代假依赖**
- 影响面：`bootstrap/qlmc/qlmc.qma`（`_sse_mov_reg` 新增 / `_to_xmm` `_from_xmm`
  改用 movaps / f64 字面量改成帧常量槽）、文档

## ① `movsd xmm, xmm` 是**部分寄存器写**，会把除法串行化

v2.55 的 `b2_float` 主循环（10 条）：

```
cmp      r12, rbx
jg       end
cvtsi2sd xmm1, r12
movabs   rax, 0x3ff0000000000000
movq     xmm2, rax
movaps   xmm0, xmm2      ← 当时是 movsd
divsd    xmm0, xmm1
addsd    xmm6, xmm0
add      r12, 1
jmp      loop
```

`movsd xmm0, xmm2` 只写低 64 位，**对 xmm0 的旧值有数据依赖**（部分寄存器写）。
而 xmm0 的旧值是**上一轮 `divsd` 的结果** —— 于是每一轮的 `divsd` 都必须等
上一轮 `divsd` 写完才能开始：**除法被完全串行化**。

实测：15 周期/轮，而 C 只要 4 周期/轮（C 那边 clang 用的是完整寄存器写，
重命名器可以直接断链）。

**修法**：寄存器到寄存器的 f64 搬运一律用 `movaps`（`0F 28`，写整个 128 位）。
上 64 位我们从来不读，搬过去无所谓。新增 `_sse_mov_reg`。

**本机 33.2 → 25.4 ms**（单次测量），min-of-7 是 **22.2 ms** —— 与 C 的 22.1 ms 持平。

> 这条经验对所有"把值搬来搬去"的代码都成立：**XMM 的 64 位搬运要用 movaps/movapd，
> 不要用 movsd**。`movsd xmm, m64`（内存形式）是安全的（高 64 位清零，算完整写），
> 只有寄存器形式才是部分写。

## ② f64 字面量放进**帧里的常量槽**

v2.55 的编译期位模式还是每次求值发 `movabs + movq` 两条。既然值在编译期就确定，
就把它**在函数序言里写进一个帧槽**，之后：

- 当 `divsd` 的右操作数 → 直接 `divsd xmm0, [rbp+slot]`（一条，零额外指令）
- 当左操作数/其他用途 → `movsd xmm0, [rbp+slot]`（一条）

实现上把字面量的 vreg 直接标成 `vloc = -(slot+1)`（帧槽），复用已有的
"f64 值可以在帧槽里"这条路径；序言里发 `movabs rax,bits; mov [rbp+slot],rax`，
与 f64 标志槽清零同一个位置（**不能走 IR**，分配已经跑完了）。

主循环 10 → **8 条**：

```
cmp      r12, rbx
jg       end
cvtsi2sd xmm1, r12
movsd    xmm0, [rbp-0x10]     ← 常量槽
divsd    xmm0, xmm1
addsd    xmm6, xmm0
add      r12, 1
jmp      loop
```

C 的同一段是 6 条（它把常量放在 `.rdata`，`divsd` 直接吃内存操作数，省掉那
条 `movsd`）。剩下的 2 条差距是"常量在帧里 vs 在只读段"，要消掉得给 qlmc 加
**f64 常量池 + `.rdata` 重定位**，是下一轮的事。

本机 min-of-7：22.4 ms（与 ① 的 22.2 在噪声内）—— 说明这条循环已经**延迟受限**
（`divsd` 吞吐 + 累加链），指令数再少也换不到时间。但指令数对前端敏感的机器
（CI 的 EPYC）有用，而且代码更干净，所以保留。
