### 一、`% 2147483648` 落在 `idiv` 上

`_opt_strength` 把常数除法强度削减成 `OP_DIVC` 时上界写的是 `cv <= 2147483647`，
而 **2^31 = 2147483648 恰好比它大 1**。于是 `% 2147483648`（LCG / 哈希最常见的
取模，`bench/speed/` 里 14 个基准在用）**完全绕过 `OP_DIVC`**，直接落回
`idiv` —— 一条 20–40 周期的硬件除法。

放宽到 `2147483648`：区间 `(2^31-1, 2^31]` 里只有 2^31 一个整数且必是 2 的幂，
不会放进任何非幂次除数；`and rax, d-1` 的 imm32 也仍装得下（`d-1 = 2^31-1`）。

| 基准 | 修复前 | 修复后 | 变化 |
|---|---|---|---|
| `b83_lcg_random` | 443.6 ms | 151.8 ms | **−65.8%** |
| `b65_random_walk` | 94.3 ms | 41.3 ms | **−56.2%** |
| `b26_maxsub` | 1014.8 ms | 446.1 ms | **−56.0%** |
| `b35_branch` | 93.7 ms | 83.4 ms | −11.0% |

生成码验证：修复后 `objdump` 里该热循环的 `idiv` 计数为 **0**。

### 二、寄存器分配按循环深度加权

`_alloc_vars` 原来用"变量在 IR 里出现几次"排序，但**出现次数不等于执行次数** ——
循环体里的一次使用每轮都要跑，循环外的一次只跑一次。同权，于是热循环变量被
挤到帧槽。实测症状（`b61_cache_scan` 最小复现）：

```
[swap] wr=16 wru=1  bs=17 bsu=6     ← 用 6 次的 k 被换出寄存器
[swap] wr=3  wru=2  bs=22 bsu=5     ← 用 5 次的 acc 被换出
```

内层循环 **13 条指令、每轮两次 store→load 往返**，C 只要 5 条。

改法：先算每条 IR 的循环嵌套深度（扫回边，`(h, e]` 内深度 +1），使用次数按
`4^depth` 累加。4 这个数让"内层用 1 次"胜过"循环外用 4 次"，同时不会让深循环
里的短命临时值把外层循环变量全挤掉。**只换位置、不改语义** —— 变量与临时值还在
同一张 `vloc` 表里，只是"谁进寄存器"的排序变了。修复后同一循环降到 **7 条指令**，
`k` 住进 `R13`、`col` 句柄住进 `R12`。

| 基准 | 前 | 后 | 变化 |
|---|---|---|---|
| `b70_lin_search` | 6590.9 ms | 2553.0 ms | **−61.3%** |
| `b61_cache_scan` | 74.7 ms | 40.3 ms | **−46.1%** |
| `b49_floyd` | 23.6 ms | 13.4 ms | −43.2% |
| `b22_knapsack` | 16.5 ms | 10.8 ms | −34.4% |
| `b52_io_scan` | 7.5 ms | 5.0 ms | −32.5% |
| `b28_matrix` | 773.2 ms | 532.6 ms | **−31.1%** |
| `b14_fibiter` | 753.6 ms | 611.1 ms | −18.9% |

76 项合计 **−5.4%**（21 项变快 / 3 项变慢）。

### 三、统一核心 `std/ucore.qma`

用户只调一个入口，运行时把全部核当成一个核：

```qma
ucore_sum(lo, hi, grain, kernel, arg) -> int   // 用户只调这一个
ucore_map(lo, hi, grain, elem, arg) -> int     // 逐元素版
```

显式控制与自标定：`ucore_parallel_sum` / `ucore_map_sum` / `ucore_parallel_for` /
`ucore_run` / `ucore_ncores` / `ucore_calibrate_ncores` / `ucore_chunks` /
`ucore_efficiency_permille` / `ucore_bench` / `ucore_serial_sum`。

设计要点：

1. **动态领块**（atomic chunk counter）而非静态等分 —— 抗慢核拖尾。静态等分时
   只要一个核被抢占，整条流水线就等最慢那块。
2. **每 worker 写自己槽位**，父线程 `join` 后按序号串行求和 —— 热循环里
   **零锁零原子**，结果与调度顺序无关（可复现）。
3. **worker 数按块数封顶** —— 3 块开 4 线程是给效率做减法。
4. **块数守恒**（`[5b]`）：Σ worker 领到的块数 == nchunks。这是不依赖计时器的
   正确性证据。

**边界（必须写清楚）**：区间 kernel 必须**可加分解**
（`k(lo,m) + k(m,hi) == k(lo,hi)`）。滚动哈希 / LCG 不满足，会静默给错数 ——
这类负载要用 `ucore_map_sum` 逐元素接口。该契约写成了可执行断言 `[2e]`。

### 四、实参少于形参是静默算错

```qma
fn f(a: int, b: int, c: int) -> int { return a + b + c }
fn main() { print(f(1, 2)) }        // 编译通过，打印 4
```

第三个形参读到**垃圾寄存器**。`spawn` 路径一直有这条检查
（`_lower_spawn`：`len(av) != f.np` → 报错退出），普通调用却漏了。
已补 fail-fast：

```
qlmc: 函数 f 需要 3 个实参，给了 2 个
```

### 多核效率（统一核心）

本机 4 核实测（80M 迭代负载）：

| nw | 效率 |
|---|---|
| 1 | 0.99 |
| 2 | 0.98 |
| 3 | 0.89 |
| 4 | 0.72–0.74 |

**同机 C + pthread 对照实验**（同一颗 kernel）：

| 实现 | 4 核加速比 | 效率 |
|---|---|---|
| C + pthread（`gcc -O2`） | 2.38× | **0.60** |
| **Quelmara 统一核心** | 2.67× | **0.67–0.74** |

Quelmara 的并行效率**高于** C + pthread。0.8 达不到是本机硬件属性：
Intel Celeron J1900 是 4 个共享 1 MB L2 的 Silvermont 核，同频集算时前端与
L2 带宽就是瓶颈。因此夹具断言的是诚实版本 `eff(usable) >= 0.8`，其中
`usable` = 效率曲线里仍 ≥ 0.8 的最大 worker 数（本机落在 2–3）；真跑在空闲的
服务器级 4 核上时 `usable` 会自动推到 4。

## 已知边界 / 遗留

### 撤回的两项优化（根因已定位，不要重试同一做法）

1. **ELF 下把变量寄存器从 5 个恢复到 7 个（RSI/RDI 入池）** —— 补齐
   `_gen_join_elf` / `_gen_spawn_elf_caller` / `_gen_print_bool_elf` 的
   push/pop 后，`spawn` 双线程程序与 `t200_ucore` **当场 SIGSEGV**
   （5 个寄存器下正常），且**单线程基准一个都没变快** —— 收益为零、风险是崩溃。
   根因：`_gen_alloc` 的 `mmap`、`_gen_spawn_elf_caller` 的 `clone`、子线程入口的
   栈切换都碰这两个寄存器，审计漏一个就崩。**重启条件**：先把运行库全部改成
   "只用 rcx/rdx/r8-r11 传参"。

2. **LICM（循环不变量外提）** —— 两版实现都被 checksum 打回：
   - 第一版判据"操作数在循环头之前有定义"。对**非 SSA** 的 vreg 不成立
     （累加器在循环里反复重定义，但在头部之前也有定义），`b1_int` 的 `acc` 归零。
   - 第二版补上"循环内 dst 集合"，`b1_int` / `b9_json` 正常了，但
     **`b11_nqueens` 从 184000 变 36000** —— **内存写**（`col.set(r,c)`、聚合
     字段写）改的不是 vreg，dst 集合看不见它。

   **重启条件**：先有别名分析 / 内存写集合。代码已从树上删除（不留死代码）。
   顺带两条实现教训：插入式变换必须**先冻结扫描区间**（边扫边插会让下标失效、
   退化成编译挂死，实测挂 4 分钟）；`_vnew` 记的活跃区间是"追加到末尾"，
   插入后必须手动改成真实区间。

### 未解释的回退（待查，不猜）

- **`b15_loopsum` 慢 31%**（1.01 → 1.33 s）。单层循环、变量数刚好等于寄存器数，
  深度加权把 `i` 从 `RBX` 挪到 `R12` 之后循环体**指令数没变**，纯粹是布局变了。
  试过"循环头 16 字节对齐"想捞回来（补 `nop` 到 16 整除）—— **没效果反而更慢**
  （1.40 s），说明不是取指对齐，该改动已完整撤回。怀疑是 L2 组相联冲突，
  但本机拿不出性能计数器证据，**不猜**。全局算总账仍是赚的，所以保留加权。
- `b9_json` +6.0%（92.0 → 97.5 ms）、`b8_threads4` +16.5%，与本条同源待查。

### 本轮未做（按收益排序，留给下一轮）

- **`b28_matrix` 仍 9.04×**（532.6 ms vs C 58.9 ms）。根因是 `r*n` / `k*n` 每轮
  重算 + 变量全在栈上；前者需要 LICM（依赖别名分析），后者受限于 ELF 下只有
  5 个变量寄存器。两者都卡在上面撤回的两项上。
- `vec` 的双重间接（句柄 → data 指针 → 元素）是结构性开销，C 只需一次寻址。

### 其他已知问题的记录

- `qlmc` 无 `parfor` / `cores()` / `syscall` 内建；`thread_yield` / `sleep_ms` /
  `read_text` / `file_exists` / `file_size` / `wall_ms` / `args` 在 **ELF 后端
  segfault**（走 Win32 IAT，PE-only）。统一核心全程只用 `join` 同步以规避。
- `mem_load64(p, k)` 的 `k` 是**字下标（×8）**不是字节下标（易踩）。
- `s32_thread`（`tests/t197_qlmc_thread.qma`）的 `bits=15 → bits=0`：
  **既存 PE 后端问题**，`git stash` 后在干净树上同样 FAIL，另行登记。
