# v4.96 — 句柄字段缓存跨语句生效（整体 −14.8%）

- 日期：2026-11-10
- 任务：优化**整体性能**（按绝对耗时贡献排序，而不是只看比值）
- 影响面：编译器（`_vec_field` 的缓存扫描判据）

## 为什么换排序口径

之前一直按"相对 C 的比值"排序优化，但那个口径会误导：

| 基准 | 相对 C | 绝对耗时 | 占总耗时 |
|---|---|---|---|
| `b17_bubble` | 3.1× | **37299 ms** | **46.4%** |
| `b12_gcd` | 1.06× | 11050 ms | 13.8% |
| `b18_insertion` | 2.6× | 10930 ms | 13.6% |

`b17_bubble` 的比值只有 3.1×（看起来不惊人），但它**一项就占了全部 76 个基准总耗时的 46.4%**。而 `b12_gcd` 比值 1.06×（几乎追平 C），却占 13.8% —— 它已经没有优化空间（核心是运行期的 `idiv`）。

按绝对贡献排序后，前三项 = 73.8% 的总耗时。

## 根因：`_vec_field` 的缓存**跨语句从未命中**

`_vec_field(fc, h, off)` 负责读 `vec` 句柄的 `[h+0]`（data 指针）/`[h+8]`（len），
它有一个"往回扫最近的 `ADDRF h,off` + `LOAD` 并复用"的缓存。但停止条件写的是：

```
if _opt_pure(w.op) == 0 { break }
```

而 **`_opt_pure` 不含 `OP_LOAD`**。于是"中间读过一次内存"就让缓存失效 ——
可 `vec.get` 之间必然夹着别的 LOAD（比较、下标计算），所以这个缓存
**只在同一个短表达式内有效，跨语句从来命中不了**。

实测症状：

- `b18_insertion` 内层循环：`a.get(y)` 在 `if` 里读一次、在
  `a.set(y+1, a.get(y))` 里又读一次 → **两次都重新解引用句柄**
- `b17_bubble` 内层循环：**重复 5 次** `mov reg,[hnd+0]`
- `b22_knapsack`：**重复 6 次**

## 修法：按"会不会改变缓存值"重写停止条件

原来是"是纯指令才继续"，改成"**会不会改变 `[h+off]` 才停**"：

| 指令类别 | 处理 | 理由 |
|---|---|---|
| `LOAD*`（读内存） | **放行** | 读不改变 `[h+off]` |
| `STORE*` / `COPY` / `ZERO`（写数据块） | **放行** | 写的是数据块，不改句柄头块 |
| 写句柄槽 `h` | 停 | 下面的独立判断已覆盖 |
| 控制流（`LAB/JMP/JCC/PRINT/ARG/CALL/RET/…`） | 停 | 前面那次计算可能不在同一支配路径上 |

**安全性**：缓存复用的是"同一个 `h`、同一个 `off`"的字段值。只要中间没有
写 `h` 本身、没有跨控制流，`[h+off]` 的值就必然相同。写数据块的
`STORE*` 改的是 `data[i]`，与 `[h+0]`/`[h+8]` 正交。

## 效果：76 项总耗时 **−14.8%**（80345 → 68453 ms）

13 项变快，1 项在噪声内，57 项持平。

| 基准 | 之前 | 之后 | 变化 |
|---|---|---|---|
| `b37_swap` | 12.9 ms | 7.7 ms | **−40.2%** |
| `b8_threads4` | 287.0 ms | 172.0 ms | **−40.1%** |
| `b84_pair_swap` | 16.2 ms | 11.3 ms | −30.1% |
| `b18_insertion` | 10930.3 ms | 8416.7 ms | **−23.0%** |
| `b72_sort_insert` | 151.8 ms | 117.5 ms | −22.6% |
| `b17_bubble` | 37299.5 ms | 28999.9 ms | **−22.3%** |
| `b67_bubble_opt` | 195.7 ms | 158.1 ms | −19.2% |
| `b7_sort` | 45.4 ms | 37.3 ms | −18.0% |
| `b79_binary_tree` | 4679.2 ms | 3898.9 ms | −16.7% |

变快的集中在**排序 / 数组遍历**这类"循环里反复 get/set 同一个 vec"的负载 ——
正是缓存该命中的场景。

`b61_cache_scan` 在全量跑里显示 +5.5%，复测（各 3 次）为
旧 40.6–43.0 ms vs 新 40.7–42.1 ms，**在噪声内，不是回归**。

## 已知边界 / 遗留

- **`b17_bubble` 仍差 3.1×**（29000 ms vs C 的 4206 ms）。C 版的内层循环被
  clang **向量化**了：`movdqu` 一次加载两个元素 + `shufpd` 交换，循环体仅 8 条。
  qlmc 没有自动向量化，无论怎么省句柄解引用都追不上 —— 这是结构性差距。
- **`b12_gcd` 1.06×**：核心是运行期 `idiv`，两边一样，没有优化空间。
- 剩下的 `b28_matrix`（9×）、`b54_merge_sort`（6.2×）等，根因是 `vec` 的
  **双重间接**（句柄 → data 指针 → 元素），C 只需一次寻址。要靠改内存布局
  （`vec` 内联 data）解决，那是大改。
