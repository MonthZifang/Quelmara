# v2.51 — 变量寄存器池扩到 7 个（`RDI`/`RSI`）

- 日期：2026-10-25
- 任务：严重优化性能与加速比（落地 §7.31(e)）
- 影响面：自举层（寄存器表 / 两个运行库例程 / 5 个调用点）+ 新增回归夹具

## 为什么以前只用 5 个

Win64 ABI 里 **非易失（callee-saved）的通用寄存器有 7 个**：`RBX`、`RBP`、`RSI`、
`RDI`、`R12-R15`。`RBP` 是帧指针，剩下 **7 个**可用 —— 但 qlmc 一直只用了
`RBX + R12-R15` 这 5 个，`RSI`/`RDI` 白放着。

没用的原因很实在：**运行库例程会踩它们**。一旦踩了，住在 `RSI`/`RDI` 里的变量会被
**悄悄改值**（不崩溃，只出错值），是比崩溃更难查的一类 bug。所以这一版的前提是
**先把所有例程审计干净**。

## 审计（第一版是错的）

写了 capstone 脚本扫编译产物的 `.text`，找"目的操作数触及 `rsi`/`rdi`"的指令。

**第一版只查了 `op0.type == REG`** —— 结果漏掉了**内存目的操作数**：
`__memset` 的 `mov byte [rdi], 0`。于是 3 个用例（`s8_map` / `s20_mem` /
`s23_map_grow`）在改完之后全崩在 `__memset` 的循环里。

修正后的判定：`op0` 是 **REG 或 MEM**，且（对 MEM）`mem.base`/`mem.index` 落在
`rsi`/`rdi` 上。另外分组阈值从 200 字节改成 40 —— 200 会把相邻的两个例程并成一组，
我第一次就是这样把 `__memset` 的 `inc rdi` 误读成 `__str_cat` 的一部分。

**最终审计结果**（跨 5 个二进制取并集，含 stage-2 自己 —— 它用遍了所有内建）：

| 例程 | 用 `rsi`/`rdi` 做什么 | 处理 |
|---|---|---|
| `__memcpy` | 源/目的指针（手写字节循环） | 实参改 `r9`/`r8` |
| `__memset`（`_gen_zero`） | `mov byte [rdi],0` + `inc rdi` | 改 `[r8]` / `inc r8` |
| `__str_cat` | 内部临时寄存器（算 data、拼指针） | **自己 push/pop** |

其余例程（`__print_*` / `__die` / `__alloc` / `__f64_fmt` / `__i64_fmt` /
`__fparse` / `__join` / `__itof` / `__ftoi` / `__str_to_int` / 入口 / 线程入口）
**一个都没碰**。

## 改了什么

1. **`__memcpy`**：`mov al,[rsi]; mov [rdi],al; inc rsi; inc rdi` →
   `mov al,[r9]; mov [r8],al; inc r9; inc r8`
   （`41 8A 01` / `41 88 00` / `49 FF C1` / `49 FF C0`）。
2. **`__memset`**：`[rdi]` → `[r8]`（`41 C6 00 00` / `49 FF C0`）。
3. **`__str_cat`**：内部仍用 `rdi`/`rsi`，但**自己保存**：
   `push rdi; push rsi` 在 `sub rsp,0x68` **之前**，`pop rsi; pop rdi` 在
   `add rsp,0x68` **之后**。两个 push 是 16 字节，所以 `sub` 之后 `rsp` 仍
   ≡ 0 (mod 16) —— 后面调 `__alloc`/`__memcpy` 的对齐不受影响。
4. **5 个调用点**（`OP_COPY` / `OP_MEMCPYN` / `OP_ZERO` / `OP_ZERON` /
   `OP_RETAGG`）：实参改 `r8`/`r9`。**必须先落到 `RAX`/`RCX`/`RDX` 再搬** ——
   它们是发射器保留的、永远不持有 vreg，否则"某个操作数本来就在 `r8`/`r9` 里"
   会被提前踩掉。
5. **寄存器表**：`_cs_reg`/`_cs_index` 加 `RSI`(5)/`RDI`(6)，`N_VARREG = 7`；
   `_new_var` 的上限、`_emit_fn` 的 `used[]` 与三个循环都跟着改。

## 新增回归夹具 `s24_varreg`

这个改动唯一的风险是"某个例程踩了 `RSI`/`RDI`"，所以专门构造那个形状：

- `work` 有 9 个标量变量 → 前 7 个进寄存器（含 `RSI`/`RDI`），后 2 个落帧槽；
- 循环里反复调 `__memcpy`（vec 扩容 + 结构体按值拷贝）与 `__str_cat`；
- 每轮把 7 个常量变量**全部**加进累加器 —— 任何一个被踩，和就变了。

已注册进 `tests/qlmc_test.py`（现在 58 个夹具）。**这个夹具在 v2.50 就能编过，
是 v2.51 才需要它** —— 属于"改动自带回归"。

## 结果

| 基准 | v2.50 | **v2.51** | C | qlmc / C |
|---|---|---|---|---|
| `b6_hash` | 46.8 | **39.5** | 40.4 | **0.98×**（又快于 C） |
| `b8_threads4` | 105.1 | **87.1** | 43.8 | 2.0× |
| `b4_array` | 30.9 | **29.5** | 10.8 | 2.7× |
| `b9_json` | 28.1 | 27.2 | 6.9 | 3.9× |
| `b7_sort` | 24.3 | 23.7 | 14.9 | 1.6× |
| `b1_int` | 43.6 | 41.9 | 11.3 | 3.7× |
| 其余 | — | — | — | 噪声内 |

- **并发加速比 3.30× → 3.85×**（334.9 → 87.1 ms；C 2.05× / Go 3.91× / Python 0.88×）。
- **stage-2：395 776 → 390 656 字节（−1.3%）**，自编译 0.7s → 0.5s。
- 代码体积（对 v2.45 基线）：**−10.1%**。
- **40 个校验和全部不变。**

**诚实评价**：单看基准，收益不大（多数项在噪声内）—— 因为基准里的热函数大多只有
5 个变量，本来就没溢出。这个改动的价值在于**大函数**（`jval`、`qsort`、qlmc 自己的
`build_pe` 之类），以及把两个白放的寄存器用起来。真正的验证是 stage-2 缩小 1.3%。

## 剩下的（§7.31）

- **`b9_json` 3.9×**：每字节一次越界检查（要范围分析），以及局部变量溢出。
- **`b1_int` / `b8` 3.7×**：魔数除法序列 16 条指令（C 的 6 条）；要再压得省掉符号
  重算，但 RAX/RCX/RDX 三个保留寄存器不够用。
- **`b2_float` 2.9×**：f64 仍住帧槽，要上 XMM 寄存器文件（另一个量级的工程）。
- **`b4_array` 2.7×**：内存带宽。
