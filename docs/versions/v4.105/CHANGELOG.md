# v4.105 — CSE 重新启用并修对：`b35_branch` 热循环 13 → 8 条

- 日期：2026-11-11
- 任务：优化 `b28_matrix`/`b34_bitops`/`b35_branch`（CI quelmara/C 分别 12.7×/6.9×/20.1×）
- 影响面：编译器（优化 pass）

## 修好了 v4.93 撤回的 CSE —— 根因是 **pass 的位置**

v4.93 的 CSE 实现本身没错，但它被放在流水线**偏后**的位置（`_opt_fuse` 之后）。
试过两个位置都失败：

| 位置 | `b49_floyd` | `b75_fib_matrix` |
|---|---|---|
| fuse 之前 | 0（应 173）| 988098（应 491479）|
| fuse 之后 | 0 | 988098 |

**两次错误完全相同**，说明与 fuse 无关。

### 根因：`LAB` 在后面的 pass 里会被删掉

CSE 靠 `OP_LAB` 判定**基本块边界**（跨块不能复用表达式）。但 `_opt_copy` /
`_opt_fuse` / `_opt_dce` 会删掉或合并 LAB —— 等 CSE 跑到时，块边界已经不在了。

`b75_fib_matrix` 就是典型：

```qma
while n > 0 {
    if n % 2 == 1 {
        let t = (a0 * a1 + a1 * a3) % 1000003    // ← 块内
        ...
        a0 = t   // 改了 a0..a3
    }
    let b1 = (a0 * a1 + a1 * a3) % 1000003       // ← 块外，表达式相同
    ...
}
```

块内改了 `a0..a3`，块外的 `a0*a1+a1*a3` 必须重算。但 LAB 被删后 CSE 认为
它们在同一个块里，直接复用了块内的结果 —— 于是 `b75` 从 491479 变成 988098。

**修法：把 CSE 放到流水线最前面**（`_opt_ndef` 之后、`_opt_copy` 之前）。
那时所有 LAB 都还在，块边界可信。

## 效果

**76/76 checksum 全部正确**（含之前失败的两个），自举两代逐字节不动点。

`b35_branch` 热循环 **13 条 → 8 条**：

```
400d37: mov r9,r14        ← 现在只剩一条副本
400d3a: and r9,0x3
400d3e: jne ...
```

原来 `(i & 3)` 在 `if` 条件里算一次、两个分支里各用一次，重复计算。
CSE 之后只算一次。

实测（本机，各 5 次取最小）：

| 基准 | 之前 | 之后 | 变化 |
|---|---|---|---|
| `b35_branch` | 88 ms | **83 ms** | **−5.7%** |
| `b61_cache_scan` | 41 ms | 41 ms | 噪声 |

76 项总耗时 68138 → 68095 ms（**−0.06%**）。

> 注：`b35` 改善的 5.7% 恰好抵消了 v4.103 那次 peephole 尝试造成的回退
> （当时 83 → 88）。两轮合起来看是"回到原位"，不是净增。

## `b28_matrix` 的 `imul` 为什么没减少

`r*n` 在 `a.get(r*n+k)`、`c.get(r*n+j)`、`c.set(r*n+j)` 三处各算一次，看起来
该被 CSE 消掉两个，但实测**循环仍是 36 条、4 个 imul**。

原因：每次 `_lower_expr` 求值 `r*n` 时**生成的是新的 vreg**（`r` 和 `n`
也是新读出来的临时值），CSE 的键 `(op,a,b)` 因此各不相同。要消除它们，
需要**值编号（value numbering）**——识别"不同 vreg 但同源"的表达式，
那是比 CSE 更强的分析。

## 已知边界 / 遗留

- CSE 只在**单个基本块内**生效。跨块（含循环回边）需要支配树分析。
- 只对纯算术白名单生效；`OP_BINI`/`OP_DIVC` 因 `b` 槽不是 vreg 而排除。
- **值编号**是下一个明确方向：它能让 `b28` 的三个 `r*n` 合并成一个。
- 总耗时基本持平，说明 CSE 在这批基准上命中的重复表达式不多。
  真正的瓶颈仍是寄存器溢出（`b28` 的 5 次 store→load 往返，占 42%）。
