# v3.38 — 补 `mem_diff` / `mem_xchg`：qlmc 覆盖率 37 → 39

- 日期：2026-10-30
- 任务：用户要求"继续"；推进"编译器核心改用自研语言"
- 影响面：**核心（Quelmara 源码）** `bootstrap/qlmc/qlmc.qma`
  （2 个内建 + 2 个运行库例程），基线从 37 上调到 39
- 版本：按 `00-convention.md` §5.1 建版本目录

## 起点：先核实上一版的判断

v3.37 的 CHANGELOG 写着：

> `vec[vec[T]]` 那条更值得优先：它是 **stage-0 与 qlmc 的共同缺口**，
> 修了能同时改善两边。

这一版先去核实，结果**判断错了**：

```bash
$ grep -n 'vec\[vec' tools/stage0/qlm_native.py
2521: # 嵌套 vec：get 返回内层句柄，重挂内层标签——v1.12 vec[vec[T]] 解锁
```

**stage-0 从 v1.12 起就支持嵌套 vec**，只有 qlmc 不支持。所以那是
qlmc 单方面的缺口，不是"共同缺口"。上一版的判断没有核实就写进了文档。

### 为什么没有当场修

分析 qlmc 的类型编码：

```quelmara
const TY_VEC   = 0x8000     // 0x8000 + elem
const TY_MAP   = 0x10000    // 0x10000 + (K<<8) + V
const TY_SLICE = 0x20000
```

`vec[vec[int]]` = `0x8000 + 0x8000` = `0x10000`，**正好是 `TY_MAP` 本身**。
要修必须改编码方案（位域 `TY_VEC | (elem << 12)` 之类），而那会波及
**34 处** `>= TY_VEC && < TY_MAP` 形式的范围比较。

34 处全改成掩码判断，是高风险重构，不适合塞进"推进一版"。所以这版
选了低风险但确定的项，**把类型编码重构留给专门的一版**。

## 这版做的：两个内建

### `mem_diff(p1, p2, n)`（2 个模块用）

返回**首个不同字节的下标**，全等返回 `n`（等价于"公共前缀长度"）。
gzip deflate 的 LZ77 匹配长度用它。

手写机器码要点：

* 返回值直接是循环变量 `r9` —— 全等时 `r9 == n`、找到不同时 `r9` 是下标，
  **两种情况同一个寄存器**，不需要额外分支；
* `cmp r9, r8` 用 `4D 39 C1`（REX.W|B，`rm=r9` 需要 B）；
* `movzx eax, byte [rcx+r9]` 的 SIB 是 `04 09`（base=rcx, index=r9）。

### `mem_xchg(addr, val)`（2 个模块用）

返回旧值、写入新值。std/net 的多 io 线程自旋锁靠它。

**只有 6 字节机器码**：

```
48 89 D0    mov rax, rdx      ; 待换入的值
48 87 01    xchg [rcx], rax   ; 隐含 LOCK，返回旧值在 rax
C3          ret
```

`xchg [mem], reg` **隐含 LOCK**，不需要额外前缀 —— 这是 x86 的特例
（其它 RMW 指令都要显式 `lock`）。

## 验证方式

手写机器码的坑在于**错了不会崩，只会静默算错**。所以每个内建都用
**stage-0 / qlmc 对拍**：

| 表达式 | stage-0 | qlmc |
|---|---|---|
| `mem_diff(a,b,3)`（第 2 字节不同） | 2 | 2 |
| `mem_diff(a,b,2)`（全等） | 2 | 2 |
| `mem_diff(a,b,0)`（n=0） | 0 | 0 |
| `mem_xchg(w,222)`（旧值 111） | 111 | 111 |
| `mem_load64(w,0)`（写入后） | 222 | 222 |

夹具 `t182_qlmc_memdiff.qma` 还覆盖了：第 0 字节就不同、`n=0` 不读内存、
重复交换、旧值为 0 的槽。

## 结果

| 指标 | v3.37 | v3.38 |

| **qlmc 覆盖 `std/`** | 37 / 70 | **39 / 70** |

## 回归

全量 Windows 回归见 CHANGELOG 末尾（本版新增 1 条 `qlmc_memdiff`）。

## 剩余 31 个失败的分布

| 数量 | 原因 | 难度 |
|---|---|---|
| 4 | `vec[vec[T]]` 类型码撞区间 | **高**（要重排编码，34 处比较） |
| 4 | vec 方法不全（`.clear` / `.pop` …） | 低 |
| 2+2 | `xmm_load` / `xmm_mov` | 中（SIMD 寄存器） |
| 6+ | `tcp_listen` / `udp_*` / `file_size` / `wall_ms` 等 | **高**（要接 Winsock/文件 API） |
| 1×N | 语法子集缺口（`期望标点` / `const 初值`） | 中 |

**下一步建议**：vec 方法（4 个，低风险）→ 类型编码重构（专门一版，
收益最大但要小心）→ 网络内建（独立工程量）。

## 一个流程反思

上一版我把"共同缺口"这个判断写进文档时**没有 grep 验证**。这次的教训是：
**写进 CHANGELOG 的因果判断也要核实**，不然下一版会基于错误前提做决策
（这一版差点直接去改 stage-0 的类型编码，那是白费功夫）。
