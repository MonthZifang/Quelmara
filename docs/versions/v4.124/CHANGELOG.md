# v4.124 — let 变量当除数不再退化到 idiv（b69 3.83× → 2.53×）

- 日期：2026-11-19
- 任务：修当前跑分最差、性能差距最大的那一项。

## 选靶：不是挑出来的，是测出来的

`docs/06-status.md` 里最后一次全量排名还是 v4.122 的数（榜首 b28_matrix 5.4×）。
本版先跑一次**当前真实排名**：qlmc 与 C 都编成原生 ELF，同机交替跑、min of 5、
校验和必须一致，76/76 全部成功。

```

b28_matrix                215.2ms     65.2ms   3.30x
b23_lcs                    42.3ms     13.1ms   3.22x
b9_json                    93.0ms     30.3ms   3.07x
b13_collatz               345.4ms    117.9ms   2.93x
```

**b69_hash_fib = 3.83×，是 76 个基准里差距最大的一项。**

## 根因：常量源要求"必须是临时值"，把 let 变量挡在门外

`b69` 的热循环是 `((key*2654435761) % cap + cap) % cap`，`cap = 524288 = 2^19`。
`_opt` 的常量传播里，把 `key % cap` 压成 `OP_DIVC`（常数除数快路径）需要
右操作数"已知是常量"，而判定条件是：

```quelmara
if op == OP_CONST {
    // 只有**单定义**的临时值才能当常量源
    if fc.vpin.get(ins.dst) == 0 && ndef.get(ins.dst) == 1 {
```

`vpin.get(dst) == 0` 要求那是个**临时值**。可 `let cap = 524288` 降级出来的是
`CONST dst=2`（临时值）+ `MOV dst=1 a=2`（搬进变量）—— `cap` 是 vreg 1，
`vpin=1`，永远不满足。于是 `% cap` 一路落到 `idiv`（20–40 周期），热循环里
**两次**。

反证很直接：把常量直接写进表达式（`% 524288`）就降到 43ms；用 `const CAP`
声明也是 43ms。**只有 `let` 变量这条路径断了。**

## 三处改动

### ① 放宽常量源的判定（`_opt`）

```quelmara
// 去掉 vpin 限制，只留 ndef == 1
if ndef.get(ins.dst) == 1 {
    cok.set(ins.dst, 1)
    cval.set(ins.dst, ins.imm)
}
```

**安全性靠 `ndef == 1`**：整个函数里这个 vreg 只被写一次，所以"这一处 CONST
的值"就是它在任何读取点的值。变量是否落在帧槽（`vpin=1`）不影响这条推理 ——
位置固定只意味着它住在内存里，不意味着值会变。

同一趟里其余 4 处 `vpin` 限制一并去掉（MOV 折常量、二元折叠、强度削减、
CMP/JCMP 压立即数），它们都是同一条推理。

### ② **补上 MOV 折常量后的登记**（真正的关键）

第一版只做了 ①，b69 **一点没变**。诊断打印道出原因：

```
[diag3] i=0 op=1 dst=2 imm=1024     <- CONST 临时值
[diag3] i=1 op=2 dst=1 a=2          <- MOV 进变量 cap
[diag]  MOD b=1 cok=0 ndef=1        <- cap 仍是 cok=0
```

MOV 分支会把 `MOV dst=1, a=2` 改写成 `CONST dst=1`，**但没有把 `cok[1]` 置位**。
后面的 `% cap` 看的是 `cok[1]`，仍然是 0。补上登记后：

```
  9  DIVC  dst=8(r8)  a=5  b=7  imm=1024
```

> 这条弯路值得记：只改"判定条件"不够，**改写 IR 的 pass 必须同步更新
> 它为下游维护的那张表**。否则判定放宽了，数据源却没接上，症状是"改了
> 等于没改"，而静态读代码看不出问题。

### ③ 没有第③条 —— 运行时与发射器一行未动

`OP_DIVC` 的快路径（2 的幂 → 单条 `and`/`shr`，其余 → 魔数乘）v4.122 就有了，
本版只是让更多表达式**够得着**它。

## 为什么不是榜首

按"差距最大"选靶，b69 是 3.83×；但**按"最值得修"**看，它是这一档里唯一的
**纯优化器缺口**：

- b28_matrix（3.00×）/ b23_lcs（3.02×）/ b9_json（3.07×）的根因分别是
  寄存器饥饿、vec 双重访存、调用 ABI —— 都要动调用约定或分配器，
  `PERF-ROADMAP.md` 把它们归为"三大结构性工程"。
- b69 只需要**让已有的快路径够得着**，零 ABI 风险、零语义变化。

在"修得动"和"差得多"的交点上，b69 是唯一的选择。
