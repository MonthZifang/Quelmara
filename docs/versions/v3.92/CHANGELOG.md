## 一、`parse_args` 静默丢弃断言（§7.48，**最严重**）

v3.91 登记 §7.48 时写的是"qlmc 不认 `and`/`or`，stage-0 两个都认"。
**前半句对，后半句错。** 补完 qlmc 的 `and` 支持后对照 stage-0 才发现两边不一致，
追下去撞出这个：

```quelmara
fn main() {
    let a = 30
    let b = 999
    assert(a == 30 and b == 40, "should fail")
    print("SILENTLY PASSED")        // stage-0 真的会打这句
}
```

**`b` 是 999，明显不等于 40，断言却"通过"了。**

**机制**：`parse_args` 缺"实参之间必须有逗号"的检查 ——

```python
while not self.at("SYM", ")"):
    args.append(self.parse_expr())
    if self.at("SYM", ","):
        self.next()
    # ← 既不是逗号也不是右括号时，什么都不做，继续循环
```

于是 `a == 30 and b == 40` 被拆成三个实参 `[a == 30, and, b == 40]`，
`assert` 只取第一个和"第二个（当消息，非 str 就忽略）"，**后半条断言凭空消失**。

**影响面**：`tests/` 里有 **33 处** `assert(... and ...)`，分布在 13 个文件。
它们**从来没有真正验证过后半段**，一直显示"通过"。

**修法**：实参之间既不是逗号也不是右括号 → `SyntaxError`，并针对
`and`/`or` 给出专门提示（本语言用 `&&`/`||`）。

**修完之后**：把 13 个文件里的 `and`/`or` 改成 `&&`/`||`，重跑 —— 33 处断言
**全部真的成立**。所以这些测试原本是"碰巧正确"，现在才是被验证过。

> 第一次批量替换时正则把 `floor` 改成了 `flo||`（`or` 在标识符内部）。
> 已回退重做，改用严格词边界（前后都不能是字母数字下划线）。

## 二、`E_ARRLIT` 出现在表达式位置（§7.49）

```quelmara
assert(first_of([300, 5]) == 44, "narrow array param truncates at entry")
```

qlmc 以前对 `[...]` 在非 let/赋值/字段初始化位置直接 `exit(2)`。
现在照 `E_STRUCTLIT` 的套路（开临时区域逐元素写进去、值 = 区域地址）实现，
`_lower_into_agg` 里本来就有这段逻辑，`_lower_expr` 复用即可。

## 教训

**写"某方支持 X"之前必须正反两面都测。** 我当初只测了
`assert(1 == 2 and ...)` 看到 EXIT=1 就以为对了 —— 那其实是因为第一个条件
为假，`and` 后面的部分本来就没被求值。补测 `assert(1 == 1 and 1 == 2)` 立刻暴露。

**更一般的**：一个"永远为真"的断言比没有断言更糟 —— 它给的是**虚假的绿灯**。
这类缺陷只能靠"故意让它失败"来发现。
