## 本轮没有性能改动（三个尝试都撤回）

按项目纪律（净收益为负/无法验证就不留在树上），如实记录。

### 尝试 1：`_bin_alias` 加 fast path（撤回）

想法：`d == b` 时无条件先搬 `b` 到 RAX 再搬 `a` 到 `d`。若 `a` 不在 `d` 里，
理论上可跳过 RAX 中转。

写完发现**正确性隐患**：若 `b` 恰好住在 `d` 里，先搬 `a` 会踩掉 `b`。
补上 `bloc - 1 != d` 条件后正确性对了（checksum 一致），但**热循环指令数没变**
（22 → 22）——因为实际场景里 `b` 就在 `d` 里，命中的是原路径。

### 尝试 2：`dst = dst <op> X` 复用 dst（撤回）

`_lower_into_raw` 的 `E_BIN` 分支原来无条件 `let l = _lower_expr(fc, nd.b)`，
`acc = acc + X` 因此重新读一遍 `acc` 得到独立临时值，最后再写回 dst
（生成 `mov r9,r13 ; ... ; mov r13,r9`）。

改成：`nd.b` 解析出的 vreg 恰好等于 dst 时，`l` 直接用 dst。

**诊断确认匹配到了**（打印 `lid=13 dst=13`），但**热循环指令数仍是 22 → 22**。
说明 IR 层优化被发射器某处抵消了，而我没定位到那处。

### 尝试 3：位运算后省 `cmp`（v4.103 已撤回，本轮未重试）

上轮实测 `b35` 83 → 88 ms（慢 6%），已知是布局效应，不再试。

## 交付：修好 `asm_audit.py` 的循环识别

上轮的工具对 `b17_bubble`/`b28_matrix` 显示"43 条、7%"，那是**同一个错误匹配**
（运行库循环），完全没有区分度。

三次迭代都记在代码注释里：

| 选择策略 | 结果 |
|---|---|
| 跨度最小（最内层） | 全匹配到运行库 6 条自旋，无区分度 |
| 指令数最多 | 匹配到**外层**循环（`b34` 显示 50 条 2%，而实际最内层是 20 条 45%） |
| **浪费密度最高**（最终） | 有区分度，且与手工分析吻合 |

现在的输出：

```
bench                      循环指令      溢出往返    冗余mov      浪费占比
b28_matrix                   36         5        5       42%
b34_bitops                   22         1        7       41%
b17_bubble                   32         2        6       31%
b18_insertion                32         2        6       31%
b35_branch                   10         0        2       20%
```

`b34_bitops` 的 22 条 / 41% 与上一轮手工逐条分析的 20 条 / 45% 吻合
（差 2 条是回边边界），说明识别可信。

## 工具暴露的新事实：`b28_matrix` 才是最大目标

```
--- b28_matrix 热循环 36 条 ---
  401518: mov [rbp-0x170],rax    ← 溢出
  40151f: mov r11,[rbp-0x170]    ← 立刻读回
  401537: mov [rbp-0x178],rax    ← 溢出
  40153e: mov rax,[rbp-0x178]    ← 立刻读回
  40154d: mov [rbp-0x180],rax    ← 溢出
  40155b: imul r10,[rbp-0x180]   ← 从内存读操作数
  40156a: mov [rbp-0x170],rax    ← 又溢出
  401571: mov r11,[rbp-0x170]
  401582: mov [rbp-0x178],rax
  401589: mov rax,[rbp-0x178]
```

**5 对 store→load 相邻往返**，全在同一个内层循环里。这是 `b28_matrix`
（CI 上 quelmara/C = 12.7×，全项目最差）的直接原因，而上轮只是在猜。

## 已知边界 / 遗留

- 工具按"浪费密度"选循环，对**多层嵌套**只报最值得优化的那一层，
  不会列出全部。要看具体某一层得手工指定地址。
- 只统计 3 类模式（store→load 同槽、`mov rX,rY`、循环指令数），
  未覆盖分支布局、指令选择、向量化机会。
- **下轮明确目标**：`b28_matrix` 的 5 次溢出往返。根因是内层循环活跃值
  超过可用寄存器（3 个变量 + 多个临时值抢 7 个变量寄存器 + 4 个临时池）。
  可行方向：按"活跃区间长度"而非"定义顺序"分配，或对 `r*n + j` 这类
  地址表达式做归纳变量强度削减。
