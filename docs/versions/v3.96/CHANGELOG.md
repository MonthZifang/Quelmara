# v3.96 — 8/9 基准在 qlmc ELF 后端跑通

- 日期：2026-11-03
- 任务：把 v3.95 遗留的 `b13`/`b27` 修掉，并提高堆上限。
- 结果：**8/9 跑通且结果与 C 完全一致**；`b13_collatz` 仍崩，已登记为已知缺陷。

## 修好的

### ① 堆上限 64 MB → 256 MB

`b27_sieve` 要 `vec[int].new(N+1)`，而 Quelmara 的 `vec[int]` **每元素 8 字节**
（C 侧用 `uint8_t` 只要 1 字节）。5000 万元素 = **400 MB**，直接把 64 MB 堆顶爆
（症状：ELF 下退出码 3 —— `__alloc` 的 OOM 路径）。

两件事一起做：
* 堆提到 256 MB（`VirtualAlloc`/`mmap` 都是按需分页，不增加实际常驻内存）；
* **基准规模从 5000 万降到 1000 万** —— 不是为了迁就 qlmc，而是因为
  400 MB 的临时分配在 CI 上本身就不合适。C/Go/quelmara 三份同步改，
  保持可比性。

### ② `mmap` 破坏 `rdi`/`rsi`/`r8`

`_gen_alloc` 的冷路径只保存了 `rcx/rdx/r9/r10/r11`（那是 `VirtualAlloc`
的破坏集合）。但 `mmap` 的 syscall 参数要摊到 `rdi/rsi/rdx/r10/r8/r9`
六个寄存器上，其中 **`rdi`/`rsi`/`r8` 没被保存**。

现象很有迷惑性：单赋值循环能跑、双赋值循环崩 —— 多一个活跃变量就恰好
踩到被破坏的寄存器。

修法：ELF 分支额外 `push rdi / push rsi / push r8`，`syscall` 之后反序 pop。

### ③ `now_ns` 里的重复 `OP_ARG`

`OP_ARG` 写了两遍同一个参数槽。虽然两次写同值无害，但那是复制粘贴留下的。

## 仍然崩的：`b13_collatz`

已二分到最小形态：

| 变体 | 结果 |
|---|---|
| 双赋值 + 无 `now_ns` | ✅ |
| 单赋值 + `now_ns` | ✅ |
| **双赋值 + `now_ns`** | ❌ 段错误 |

必须**同时**有"`if` 里两条赋值"和"`now_ns`"。这强烈指向"`now_ns` 展开的临时值
把调用者的帧挤爆"或"某个活跃寄存器被运行库破坏"，但已经排除了
`rdi/rsi/r8` 这一组。**登记为已知缺陷**，继续查需要 dump 对比 IR + 机器码。
