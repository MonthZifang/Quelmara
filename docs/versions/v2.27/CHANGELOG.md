# v2.27 — vec 扩容，子集 S13；顺带把 vec 布局改成"头块 + 数据块"

- 日期：2026-10-25
- 任务：vec 容量可变（用户清单里没单列，但固定容量会让真实代码到处预估容量，
  是"能不能写真实程序"的前置条件）
- 影响面：自举层（qlmc 后端 / 降级）/ 测试 / 文档 / 新增一个排查工具

## 主事件：vec 扩容

```quelmara
let v = vec[int].new(2)     // 只有 2 格
let mut i = 0
while i < 40 { v.push(i * 3) ; i = i + 1 }
print(len(v))               // 40 —— 一路翻倍 2→4→8→16→32→64
print(v[39])                // 117
```

对齐 stage-0 的 `__vec_grow`：`len == cap` 时 `ncp = max(cap*2, 4)`，分配 `ncp*8`
字节，搬 `len*8` 字节，更新头。**下限 4 不是装饰**：`new(0)` 的容量是 0，翻倍还是 0，
没有下限就会往 0 字节的块里写，踩下一块堆。

## 前置改动：vec 布局必须换成"头块 + 独立数据块"

旧布局是**单块** `[len][cap][data...]`（数据紧贴头后面）。这样一扩容就必须整块换掉，
**句柄随之变化**——任何别名变量（`let w = v`）立刻指向旧块。stage-0 早就是
`[data][len][cap][ew]` 32 字节头块 + 独立数据块，qlmc 当初图省事写成了单块。

现在头块 24 字节 `[data][len][cap]`，扩容只改 `[h+0]`/`[h+16]`，**句柄恒定**：

| 环节 | 变化 |
|---|---|
| `_lower_vecnew` | 两次 `__alloc`：头块 24 + 数据块 `n*8` |
| `_vec_field` 的调用点 | len `0`→`8`，cap `8`→`16`（map 的两个偏移**不动**：map 是独立对象） |
| `_vec_elem_addr` | 入参从"句柄"改成"**数据指针**"，先 `[h+0]` 再 `ADDRX` |
| vec 切片基址 | 原来是 `_map_base(h)`（恰好等于旧的 `h+16`），现在必须 `[h+0]` |
| 索引 `v[i]` / `.get` / `.push` / `.len` / `len(v)` | 同步改偏移 |

## 新增 IR 操作码 `OP_MEMCPYN`

搬 `len*8` 字节，长度是**运行时值**，`OP_COPY` 只吃立即数，所以加一条：

```
OP_MEMCPYN：memcpy(a, b, dst)   // a=目标 b=源，字节数塞在 dst 槽（Ir 只有 4 个槽）
```

两个配套细节：

1. **`dst` 槽在这里是"被读"的**，`_ir_emit` 必须给它记一次 use（`vend`），否则分配器
   认为活跃区间在指令前就结束，把寄存器复用掉。
2. RT_MEMCPY **不清 caller-saved**（只碰 rdi/rsi/rcx/rax + 标志位），所以它**不能**
   登记进 `_alloc` 的跨调用计数（对比 v2.25 的 `OP_CALLIAT`：那个是真调用，必须登记）。

## 热路径：常见路径不能为扩容付代价

第一版把 `len/cap/data` 全部提前钉进帧槽再判断，push 的机器码从 26 条涨到约 40 条
（`mov [rbp-8]` 之类一堆）。改成**冷路径自包含**：

```
push:
  x  → pin
  hp → pin
  len0 = [hp+8] ; cap0 = [hp+16]
  cmp len0, cap0 ; jl .push        ← 常见路径到此为止
  _vec_grow_body(hp)               ← 冷路径自己重读头字段、自己分配、自己搬
.push:
  len  = [hp+8]                    ← 汇合点后重读（顺带保证不跨调用）
  data = [hp+0]
  [data + len*8] = x
  [hp+8] = len + 1
```

常见路径回到约 34 条（比 v2.26 多的那几条是"句柄 → 数据指针"多一次 load，
是新布局的固有成本，不是扩容的）。实测编译耗时看不出差异（见 §验证）。

## 找到并修掉的真实 bug：`OP_CMP` 的条件码写成了 jcc 码

`OP_CMP` 的 `imm` 是 **setcc** 码（0x9x），`OP_JCMP` 的 `dst` 是 **jcc** 码（0x8x），
差 0x80。我给 `OP_CMP` 传了 `0x1C`（本该 `0x9C`），编出来的字节是：

```
4d 39 c1     cmp r9, r8
0f 1c c0     ← 不是非法指令，是 Intel 的多字节 NOP
```

CPU 照跑不误，只是**比较结果变成"上一次的 AL"**。现象：`ncp = max(cap*2,4)` 恒等于 4
（因为 AL 里还留着 `cap*2`，非零 → `jz` 不跳 → 走"ncp=4"分支），于是每次 push 都扩容、
还按 `len*8` 拷贝越界，数据被搅成**周期 4 的重复串**：

```
期望  1 1001 2001 3001 4001 5001 ...
实际  1 1001 2001 3001 1    5001 ...        // 只有"最后一次扩容之后"的元素是对的
```

排查路径（值得记下来）：IR 转储看着完全正确 → 说明问题在编码层 →
`capstone` 反汇编**停在 `cmp` 后面那条**（流式解码遇非法字节即停，停的位置就是答案）→
读原始字节看到 `0f 1c c0`。

**修法两层**：① 传对 `0x9C`；② **两个发射器都加条件码范围守卫**——`OP_CMP` 只收
`0x90..0x9F`、`OP_JCMP` 只收 `0x80..0x8F`，越界直接 `exit(2)`。这类"编出 NOP"的错
必须 fail-fast，不能靠跑测试撞。

顺带产出一个工具：**`tools/dev/dumpasm.py`**（反汇编 .text，支持 RVA 区间，
解码提前结束时直接报"问题就在这里"）。

## 已知边界

- **`vec[vec[T]]` 仍然不支持**：`TY_VEC = 0x8000 + elem` 存的是完整 TY 码，
  嵌套时 `0x8000+0x8000 = 0x10000` 正好落进 `TY_MAP` 区间，会被当成 map 处理
  （报"map 只支持 .set/.get/.has/.len"）。根因与修法见 `07-gaps.md` §7.18，
  需要把元素类型改成"类型表下标"，不能只给 `TY_VEC` 打补丁。
- 聚合作 vec 元素、map 扩容、`rc`/`Drop` 仍然缺；扩容只翻倍、不收缩，
  也不做 `__realloc`（qlmc 的 bump 分配器没有 realloc，旧块直接放弃）。
- 扩容只在 `push` 里触发；`v[i] = x` 仍然要求 `i < len`（越界 `exit(1)`，与 stage-0 一致）。

## 下一版建议：位运算 / 移位

顺手试了一下 `qlmc` 编译**自己的源码**，第一个报错是：

```
qlmc: 不认识的字符 '&' @ line 1613      // code.push(v & 0xFF)
```

全文件二十余处 `& | << >>`。也就是说**自举的第一个硬阻塞不是泛型、不是接口，
而是最便宜的位运算**——而且它自己写机器码时到处都在用（`0xFF` 掩码、`<< 3` 缩放、
`& -8` 对齐）。这一项应该是下一版，优先级高于 f64/泛型。
