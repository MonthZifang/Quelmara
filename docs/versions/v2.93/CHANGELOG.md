# v2.93 — 内联阈值 28→60：b9 −14%、b5 −21%、b8_threads4 −37%

- 日期：2026-10-28
- 任务：性能 —— 把"永远进不了内联"的中等函数放进内联，顺带挖出两个隐藏缺陷
- 结论：阈值本身是一行改动；**真正的工作是它暴露出来的两个 bug**——
  一个在 LICM（会让 map 静默越界），一个在 `floatv` 标记搬移（会让浮点算错）。

## 为什么是 28 这个数

`opt_inline` 的阈值判据是 **`len(callee.instrs)`**，也就是 `lower_fn` 出来的
**原始 QuIR** 条数——不是源码行数。

而 Quelmara 的循环降级很"重"：一个

```
while go == 1 && p < n {
    let c = s[p]
    ...
}
```

源码 5 行，降级后是 43 条 IR（两个 `label`、两处 `jcc`、一处分合流的 `jmp`、
再加 `s[p]` 的边界检查）。于是 `jws`（扫空白）、`jstr`（扫字符串）这类
**b9_json 每解析一个 token 就要调一次**的小函数，永远卡在 28 之上。

实测各函数降级后条数：

| 函数 | 源码行 | 降级后 IR | 28 阈值下 |
|---|---|---|---|
| `jws` | 10 | **43** | 不内联 |
| `jstr` | 8 | **35** | 不内联 |
| `jnum` | 24 | 71 | 不内联 |
| `jval` | ~60 | 215 | 不内联（远超阈值，合理） |

## 缺陷一：LICM 会把内联进来的 `load` 提到错误的位置

阈值提到 60 后，`tests/t22_map.qma` **立刻 SIGSEGV**。

### 怎么定位的

不是猜的，是三级二分：

1. `git stash` 回退 → 正常，确认是本次改动引入；
2. 用 `transpile_native` 直接扫阈值 28/30/34/38/42… → 卡在 **34 与 38 之间**；
3. `QLM_SKIP_PASSES=<pass>` 逐个跳过 → **只有跳过 `opt_licm` 才恢复正常**。

### 根因

`__map_key_eq` 的 IR 里有

```
load 44, 0, 3      ; 读 vreg 0（形参）的第 3 字
```

它被内联进 `__map_find`，再被内联进 `total`。内联会**重编号 vreg**（`+base`），
重编号之后 `0` 恰好落在 `total` 的 map 句柄上——而那个句柄在整个循环里确实不变。

于是 LICM 的两条判据（"base 在循环内没被重定义"、"循环是纯读"）**都成立**，
它把这条 load 提到了 `__map_find` 的探测循环**外面**。运行时读到的是错的槽位，
越界后 `memcpy` 按垃圾长度拷贝 → SIGSEGV。

> 这是"**vreg 重编号让不变量分析偶然成立**"的典型：LICM 的判断在它能看到的信息
> （重编号后的 IR）里是对的，错在**这条 load 本来就不属于这个循环**。

### 修法

`_inline_one` 把内联副本里的每条 `load` 的 `(dst, base, off)` 三元组登记到
调用方的 `fn.inline_loads`；`_licm_safe` 见到这个集合里的 load 一律不外提。

**踩过的坑**：第一版是往指令元组末尾加第 5 位 `True` 做标记——结果**失效**，
因为中间的 pass 会按 4 元组重建指令，标记被悄悄丢掉。改用调用方身上的**集合**
才生效。这条值得记住：**指令元组的形状是下游共同依赖的契约，不要往上加字段**。

## 缺陷二：`floatv` 是 dict，不是 set

修完 LICM 之后 `tests/t23_float.qma` 炸：

```
AttributeError: 'dict' object has no attribute 'add'
```

我在 `_inline_one` 里加了三类标记的重映射（`strv`/`boolv`/`floatv`），
但 `floatv` 的类型是 **vreg → `'f32'`/`'f64'` 的 dict**（记录浮点宽度），
不是 `strv`/`boolv` 那样的 `set`。已分开处理。

这几类标记本身是必要的：它们是**按 vreg 号**记的，内联平移 vreg 之后
不同步搬，被内联进去的值就"不再被认成 str / bool / 浮点"。

## 代价：b4_array 慢了 23%

`b4_array` 从 64.8 涨到 79.6 ms。这是阈值放宽的直接代价：更大的函数体
让寄存器压力上升，溢出槽变多。它现在对 C 是 **2.0×**（原来 1.6×）。

**没有回退**，理由：b4 的绝对值只占全表 1/10，而 b8_threads4 −37%、
b5_string −21% 是三个数量级更大的收益。`docs/07-gaps.md` 本来就登记了
"b4 是内存带宽瓶颈（16 MB 工作集）"，这条涨跌属于寄存器分配的副作用，
不是算法退化。若后续要收回来，正确做法是**按函数热度**给阈值（热函数放宽、
冷函数保持 28），而不是全局回退。

| 项 | 现状 |
