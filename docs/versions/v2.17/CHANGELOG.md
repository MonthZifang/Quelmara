# v2.17 — qlmc 扩到子集 S3：struct / 定长数组 / for / break / continue

- 日期：2026-10-24
- 任务：语法面继续扩（往"能编真实程序"推）+ 强力优化性能（先量清楚瓶颈）
- 影响面：自举层（`bootstrap/qlmc/qlmc.qma` 前端与后端）/ 测试 / 文档

## 主事件 1：语法从 S2 扩到 S3

v2.16 把后端重写成了"IR + 线性扫描 + 并行"，但语法面还停在 int/bool/str。
这一版补上**聚合与控制流**，也就是"写得出真实程序"的最小集合：

| 能力 | 做法 |
|---|---|
| `struct S { f: T ... }` | 声明期建表（`stt`，每 struct 18 字：名字/字段数/8×（字段名,类型））；字段一律 8 字节、按声明序排布；字段类型限 int/bool/str |
| `S { f: e, ... }` 字面量 | 字段初始化链（`E_FINIT` 用 `nx` 链，不额外开数组）；字段名必须存在，否则编译期报错 |
| `p.f` 读 / `p.f = e` 写 | 左值取地址链（`OP_ADDRV` 取帧内区域基址 → `OP_ADDRF` 加字段偏移 → `OP_LOAD`/`OP_STORE`） |
| 值语义 | `let q = p` 走 `OP_COPY`（`__memcpy`），改 `q` 不影响 `p` |
| `[N]T` 定长数组 | 类型编码 `0x100000 + (N<<8) + elem`；元素限 int/bool/str；区域在帧内连续 N 个 8 字节 |
| `[e1, e2, ...]` 字面量 | 元素链（`E_AINIT`）；无标注时按元素个数推 `[N]int` |
| `a[i]` 读 / `a[i] = e` 写 | `OP_ADDRX`（基址 + 下标×8）+ `OP_LOAD`/`OP_STORE` |
| `for i in lo..hi` | 与 stage-0 同口径：上下界**各求值一次**，左闭右开；降成"隐藏循环变量 + `cmp/jge` + 自增" |
| `break` / `continue` | 循环栈（`(continue 标签, break 标签)` 成对），`while` 也压栈 |

**聚合的表示**（改之前先读）：聚合值一律在帧里（`_new_var` 按 `_ty_size` 分配连续槽），
**"聚合的 vreg 值 = 它区域的地址"**。所以 `p`、`p.f`（当 f 是聚合）、`a` 在表达式里
都是地址；只有标量字段/元素才 `LOAD` 成寄存器值。这套约定让"取地址链"和"值拷贝"
共用一条路径。

## 主事件 2：性能——先量清楚噪声从哪来，再谈优化

用户问"性能噪声大多数来源于 Python 吗"。实测（每组 15 次，同一台机器）：

| 测量对象 | min | 中位 | max | 波动 |
|---|---|---|---|---|
| `python -c pass`（纯 Python 启动） | 949.7 ms | 1125.5 ms | 1307.9 ms | **37.7%** |
| 裸 Quelmara exe（无 Python、空程序） | 373.7 ms | 442.9 ms | 492.9 ms | **31.9%** |
| qlmc 进程内计时（`-j1`，200 函数） | 14170 µs | 16697 µs | 33712 µs | **137.9%** |
| qlmc 进程内计时（后端段 `-j1`） | 2415 µs | 2760 µs | 6699 µs | **177.4%** |

**结论：噪声不是 Python 带来的。** 三层证据：
1. 裸 exe（完全没有 Python）的进程创建本身就波动 32%——那是 VBS/Hyper-V 把 vCPU
   抢走 + Windows 进程创建税；
2. qlmc 的计时是**进程内** `now_ns()` 差值（不含进程创建），波动反而更大（115–177%），
   说明宿主调度会随时把整个 vCPU 抽走；
3. Python 只是把绝对耗时放大（950 ms 量级），让同样的相对波动看起来更吓人。

**想减小噪声只有两条路**：① 只用 `min of N`（本项目既有口径）；② 换 CPU 时间口径——
但 `cpu_ns()` 在 Windows PE 上**粒度约 156 ms**（实测两次读数差恒为 156250000 ns），
测不了微秒级，所以本版**没有**把计时改成 CPU 时间，只在 `07-gaps.md` 登记这条。

**顺手试了最明显的编译期优化，结论是"不是瓶颈"**：把 `_name_id` 的线性查表
（O(n²)）改成 FNV-1a 哈希表，800 函数的前端耗时 32.7 ms → **34.4 ms**（没收益，
哈希本身 + 32768 桶初始化的开销抵消了收益），**已回退**。真正的瓶颈在词法/语法的
分配与结构体拷贝（每个标识符 `substr` 一次、每个 `_cur` 复制一个 4 字段 Tok），
下一版从那里下手。

## 已知边界 / 遗留

- **仍是子集 S3**，不是全语言。缺：enum/match、vec/map、f64、泛型、闭包、切片、
  `defer`、`import`（多文件）、宏/反射、`@ffi`、接口、`rc`。
- **聚合的三条硬边界**（都 fail-fast，不静默）：struct 不能作形参/返回值（ABI 只传
  标量）、字段不能是聚合（无递归布局）、数组元素不能是 struct。
- **`for` 的上界必须钉进变量**：临时值的活跃区间不跨循环回边，第一版因此出现
  `for k in 0..3` 死循环（差分测试当场抓到）。
- **前端是墙钟主要部分**（200 函数里占 ~80%），且已证明不是名字查表的锅；
  词法/语法的分配是下一版的目标。
- `cpu_ns()` 在 Windows PE 上粒度 156 ms，做不了微秒级测量。
