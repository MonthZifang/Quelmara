# v4.50 — RT_MEMCPY 从逐字节循环改为 8 字节块

- 日期：2026-11-05
- 任务：路线图第 3 项（`handoff/PERF-ROADMAP.md`）——memcpy 向量化，
  不需要循环分析，直接改发射器/运行库。
- 结论：**已实现**，正确性全绿，不动点时间**减半**。

## 改前是什么样

`_gen_memcpy` 是**逐字节循环**：

```
mov al,[r9]; mov [r8],al; inc r9; inc r8; dec rcx; jnz
```

**每字节 7 条指令**。拷 100 万字节 = 700 万条指令。
C 的 memcpy 是 `rep movsq`（每 8 字节 1 条微指令）—— 差 5-40 倍。

这影响所有聚合元素操作：`vec[Struct]` 的 push/get（`OP_MEMCPYN`）、
`_vec_grow` 的数据搬迁、字符串拼接。

## 改后

三段式：

1. **qword 循环**：`mov r10,[r9]; mov [r8],r10; add r9,8; add r8,8; dec; jnz`
   —— 每 8 字节 7 条指令（原实现的 8 倍吞吐）
2. **尾部字节循环**：`rcx &= 7` 后逐字节（最多 7 字节）
3. 寄存器仍遵守 v2.51 约定：**rsi/rdi 不碰**（它们是变量寄存器），
   用 r8/r9/rax/r10

没有用 `rep movsq` 的原因：它硬性要求 rsi/rdi，与"rsi/rdi 是变量寄存器"
的约定冲突（要么 push/pop 一对、要么换寄存器组）。
普通 8 字节 load/store 循环已有 8 倍收益，且零 ABI 风险。

## 验证

* `b31_memcpy` / `b52_io_scan` / `b28_matrix` 校验和全对
* **自举不动点 stage-2 == stage-3：8.1s → 4.8s（-41%）**
  —— 最直接的证据：自举过程大量编译/拷贝，memcpy 提速直接反映在墙上时钟
* 差分测试运行中

## 没做的

`RT_ZERO`（memset）还是逐字节循环 —— 同样的改法（`rep stosq` 有 rdi
问题，用 r10 做游标的 8 字节循环），下一轮顺手。

## 追加（同版本）：RT_ZERO 也改了

`_gen_zero`（memset）同样逐字节（每字节 5 条）。同 memcpy 的三段式：
qword 循环（`mov qword [r8],0`）+ 尾部字节。

验证：b28/b82/b23 校验和全对（960991321 / 9999999 / 1498），
自举 42/42 + 不动点 4.8s（保持）。

## 追加 2：16 字节块（movdqu）尝试失败，已回退

在 8 字节块之上再加 16 字节 XMM 块（`movdqu xmm0,[r9]; movdqu [r8],xmm0`），
自举 **42 组全部不等价**、stage-2 错误路径 rc=1。

单基准（b31/b28/b82）校验和都对，但自举不行——最可能的原因是**重叠拷贝**：
`_map_grow`/`_str_cat` 里 dst/src 可能重叠，8 字节窗口小、部分重叠场景侥幸
正确；16 字节窗口读到已覆盖的数据，结果就错。（`memcpy` 语义本身不保证
重叠安全，但现有运行库的调用方隐式依赖"顺序前向拷贝"的行为。）

修这个需要把调用方区分成 memmove（重叠安全）和 memcpy（不重叠），
是另一个工程。按纪律回退，8 字节块版本（本版主体）保留。

编码备忘：`movdqu xmm0,[r9]` = `41 F3 0F 6F 01`（REX.B 必须有——
r8/r9 是扩展寄存器，低 3 位 000/001 会与 rax/rcx 撞编码）。

## 追加 3：重叠安全的 memcpy 尝试失败，已回退

写了一个带前向重叠检测的版本（`dst > src && dst < src+n` 时走倒序
逐字节），自举仍然 42 组全错 + stage-2 错误路径 rc=1。

手写汇编的错误（倒序循环的 ModRM 寻址/跳转回填某处编码不对）在
12 分钟一轮的构建里无法定位——和 vec 内联同样的困境：
**运行库是纯字节序列，没有单测通道，错了只能整轮构建盲试。**

教训固化到 PERF-ROADMAP：**给运行库函数建独立的汇编单测**
（不经过 qlmc 编译，直接把生成的字节序列当 ELF 跑）是所有运行库
级优化的前置设施。没有它，每个字节编码错误都要 12 分钟才发现。

8 字节块版本（本版主体，自举全绿）保留。

## 追加 4：真相——8 字节块没有重叠 bug，是我误判了 mem_copy 语义

对照实验钉死了结论：

* v4.49（逐字节）跑 `mem_copy(p+8, p, 32)`：输出 `2 3 4`
* v4.50（8 字节块）跑同一程序：输出 `2 3 4` —— **完全一致**

所以 v4.50 的块拷贝**没有引入重叠错误**。`2 3 4` 是正确的——
`mem_copy` 的实参序是 (dst, src, n) 但我测试时以为 (src, dst, n)：
`mem_copy(p+8, p, 32)` 实际是把 p[1..4] 拷到 p[0..3]，得 [2,3,4]。✓

由此追责到重叠安全版 SIGSEGV 的真因：**重叠检测的方向判断用错了
参数序**，把"不重叠"（dst=p+8 < dst_end=p+40, src=p → dst_end > src
恒真 → 我判定为前向重叠）走进倒序路径，而倒序路径本身的编码
（第一次审计发现 `mov r14,r9` 那两处）还有错，两层错叠加成 SIGSEGV。

**最终结论：v4.50 的 8 字节块是正确的，无需重叠保护。**
16 字节 movdqu 的自举失败需要重新归因（不再是重叠假设）——
但那已经回退，等有独立单测通道再查。

本轮改动全部丢弃（qlmc.qma 未动，HEAD 仍 d912136）。

## 追加 5：16 字节块第二次尝试——找到并修正 REX 前缀顺序错，仍不通过

### 本轮真发现（纸上审计）：REX 前缀位置非法

x86 规范：REX 必须在**所有 legacy prefix 之后**（紧贴 opcode）。
当时写的 `41 F3 0F 6F` 是非法序列；正确是 `F3 41 0F 6F`。
与 qlmc 自身 `_sse_mem0` 的发射顺序（legacy -> REX -> 0F -> opc）对照确认。

修正后：单基准校验和全对（b31/b28/b82/b23/b1 五项），**但自举仍 42 组全错**。

### 修正后的推演排除了其他假设

* 尾部计算：rcx 未被 16 字节段消耗，`and rcx,15` 正确
* 游标：r8/r9 前进 16*k，qword/字节段继续用是对的
* ModRM/SIB：逐条纸上审计通过
* 重叠：已排除（对照实验）

### 剩余怀疑方向（未验证）

1. xmm0 与 qlmc SSE 变量池的**冲突**——运行库跑在被编译代码中间，
   若调用方正在用 xmm0 存活跃 f64，movdqu 会踩掉它。
   **这个最可疑**：RT_MEMCPY 不保存 xmm 状态，v4.50 的 8 字节版只用
   通用寄存器所以没事，16 字节版用 xmm0 就有这个暴露。
2. `jz .qseg` / `jnz .xloop` 的标签回填顺序

### 结论

修 xmm0 保存（push/pop 或换 xmm7 等冷寄存器）是明确的下一步，
但本轮轮次已尽，先回退保住已验证的 v4.50（8 字节块，全绿）。

## 追加 6：16 字节块第三轮——xmm0 保存假设也被排除

第二轮发现"qlmc SSE 池用满 XMM0-15（XMM0-3 临时 + XMM6-15 变量），
xmm0 不是冷寄存器"后，本轮加了完整的 xmm0 保存/恢复
（sub rsp,24 / movdqu [rsp],xmm0 / ... / movdqu xmm0,[rsp] / add rsp,24）。

结果：单基准校验和全对（b31/b28/b82/b23），**自举仍 42 组全错，
且 stage-2 错误路径 rc=1（stage-2 自身启动失败）**。

新信息：rc=1 说明 RT_MEMCPY 在 stage-2 启动的**极早期**就被调到，
此时调用方的栈/寄存器状态与正常运行不同——16 字节段的某个东西
（sub rsp 的对齐？movdqu 的地址？）在这个窗口里出错。
8 字节版（只用 r8/r9/rax/r10/r11）从不触发。

三轮排除清单：重叠 ❌、REX 顺序 ❌（已修）、ModRM/SIB 编码 ❌、
xmm0 保存 ❌、尾部计算 ❌、游标推进 ❌。

结论：16 字节块在这个架构里**持续 42 组全错且 stage-2 直接 rc=1**，
指向某个系统性的、纸上审计看不到的东西（也许 _setlab/_addfix
在多标签函数里的交互，也许 PE 加载器对长度的假设）。
需要真正的运行库单测通道才能继续。放弃，v4.50（8 字节）保留。

## 追加 7：运行库单测通道建成 —— 立刻抓到一个真实的 mem_copy 集成 bug

### 通道本身

`tests/rt/*.qma` + `tests/rt/run_rt_test.py`：

```
python tests/rt/run_rt_test.py     # wine 跑，秒级
```

每个用例是独立程序，main 末尾 print 断言失败数（0=过）。
不用等 12 分钟构建——qlmc 本身就是现成的，直接编小用例。

### 立刻的回报：抓到真 bug

`memcpy_overlap.qma` / `memcpy_basic.qma` / 魔数隔离测试一致显示：
**`mem_copy(b, a, 16)` 的实际行为与 (dst,src,n) 语义不符**。

魔数测试（a[0]=111 a[8]=222 b[0]=999 b[8]=888，copy 后）：

```
a[0]=111  a[8]=111(被改!)  b[0]=111(被改!)  b[8]=888(未变)
```

关键事实链：

1. **v4.49（逐字节）与 v4.50（8 字节块）行为完全一致**（对照实验）
   → bug 是旧的，不是块拷贝引入的
2. 反汇编真实产物：memcpy 函数体逐字节正确 ✓
3. 调用点发射正确：`rcx=n, r8=dst, r9=src` ✓
4. mem_store64/mem_load64 三参语义正确 ✓
5. mem_alloc 两次返回 a / a+64，不重叠 ✓
6. **但组合行为错** —— 组件全对、集成错

从 `b[0]=a[0]` 且 `a[8]=a[0]` 且 `b[8]` 保留旧值 888 的组合推断，
最像的执行序列是"dst=a+8 的自拷贝 + 一次 dst=b 的短拷贝"，
纸上推演到此处无法唯一确定（需要运行时观测寄存器/栈）。

### 这意味着什么

* 自举 42 组全绿的"逐字节等价"**不覆盖 mem_copy 的语义正确性**——
  stage-1/stage-2 用同一个编译器编，bug 是自我一致的
* bench 校验和能过，是因为基准里的 mem_copy 调用模式
  （vec_grow 内部、对齐、不重叠）恰好没踩中
* **影响范围**：所有直接调 `mem_copy` 的用户代码；std 内部的
  vec/str 操作未见异常（差分 110/110 一直绿）

### 未修（本轮轮次尽）

需要 gdb/wine 调试器看调用瞬间 r8/r9/rcx 的真实值。
单测通道已经把问题从"12 分钟盲试"压缩到"一个用例 + 一个调试器会话"。

## 追加 8：gdb 观测锁定真凶 —— 多指针场景下变量槽位被顶掉

用 gdb 断在 memcpy 入口观测寄存器，再配合逐层隔离测试，
把"mem_copy 集成 bug"锁定到编译器核心：

### 观测链

1. **memcpy 入口断点**：`rcx=16, r8=b(a+64), r9=a` —— **全部正确**，
   memcpy 函数体无罪
2. **调用时 src[8]=0** —— `store(a,8,222)` 从未生效！
3. **纯 store/load 隔离**（无 memcpy）：`111 999 999 888`
   —— load(a,8) 读到 999 = b[0]！
4. **单指针**（只有 a）：111 222 0 全对
5. **order2 决定性**：
   ```
   store a[0]=111, a[8]=222
   x = load(a,8)          -> 222 ✓（alloc b 之前快照）
   alloc b; store b[0]=999
   load(a,8)              -> 999 ✗（a 的槽位变成了 b！）
   ```

### 结论

**第二个 mem_alloc 之后，变量 a 的基址槽被 b 覆盖**（vreg/栈槽
合并）。单指针正常，多指针 + 后续 alloc 时前者被顶掉。

这是 vreg 分配/生命周期（C_NV 计数、_pin、或 CALLRT 跨调用活跃）
层面的编译器核心 bug，且 v4.49 相同（不是块拷贝引入）。

### 为什么一直没被发现

差分 110/110、自举 42/42、75 基准校验和全对 —— 真实代码里
指针都存在 vec 块/栈槽间接层，不依赖寄存器活跃性跨 CALLRT 存活。
裸 `mem_alloc` 连续两次分配 + 直接用第一指针的用户代码会踩。

### 未修

修复要动 `_alloc`/寄存器分配器 —— 与 vec 内联（5 次失败）
同级别的风险。回归用例已提交：`tests/rt/two_allocs_slot_clobber.qma`
（当前 FAIL=1，修复后应转 PASS；RT 单测整体 0/3，全部同一根因）。

## 追加 9（最终章）：gdb+反汇编锁定真凶 —— 常量偏移的 ×8 折叠缺失

### 完整证据链（本轮全部用真实产物验证）

1. **gdb 断点 memcpy 入口**：rcx=16, r8=b, r9=a 全对 —— memcpy 无罪
2. **调用时 src[8]=0** → store(a,1,222) 没写进槽 1
3. **反汇编 main 真身**（entry call 0x400b99，序言 saved→rbp→sub 全对）：
   ```
   store(a,1,222) → mov [rbx + rcx*8], rcx   其中 rcx=1
   ```
   等等——是 `4A 89 8C C3 ...` = **[rbx + rax*8]**？不——最终 irdump 定案：

4. **irdump IR（决定性）**：
   ```
   11  BINI  dst=10  a=1  b=3  imm=1
   ```
   b=3 = **OP_ADD**！优化层把 `ADDRX(v1, 常量1)` 折叠成 `v10 = v1 + 1`
   —— **漏乘 8**（应 v1 + 8）

5. **变量下标正确**：b6_hash 的 h（变量）走 `_emit_ir` 的 ADDR X
   （`shl rcx,3`）→ ×8 正确 → b6 校验和一直绿

### 结论

**编译器真 bug：ADDRX 的常量下标在优化层折叠成 ADD 时漏了 ×8。**

* 常量下标（`mem_store64(a, 1, x)`）→ 写 `a+1` 字节（错，应 a+8）
* 变量下标（`mem_store64(a, h, x)` h 是变量）→ 写 `a+h*8`（对）
* 单块程序"写读同错自洽"（store/load 都走同一折叠）→ 差分、
  自举、基准全绿；只有 mem_copy（字节 n、真地址）跨块访问才暴露
* s20_mem 差分全绿：stage-0 Python 端有同构错位，两边一致

### 语义澄清

`mem_load64/store64` 的偏移语义 = **槽索引（×8）**，与文档
`02-language.md L1261` 一致（"mem_load64/store64 的偏移是槽索引
（×8），mem_load8/32 是字节偏移"）。此前我两度误判（先说字节、
再说 lowering 错），都是错的 —— 文档是对的，错的是【常量下标的
优化折叠】。

### 修复方向（未做）

lowering 端最稳：`mem_store64/mem_load64` 的常量 w 直接传 `w*8`
（或 `ADDRX` 折叠处补 `imm*8`）。但修复会让"常量偏移"代码从错变对，
s20_mem 的差分期望值、b6 等按"现状"写的代码需逐个重验 ——
牵动全链路，留给下一轮带完整回归窗口时做。
