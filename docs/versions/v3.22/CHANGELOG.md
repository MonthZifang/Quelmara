## 为什么这是一个真实的空白

v3.21 把 reactor 的监听 socket 从 `AF_INET` 改成 `AF_INET6` 双栈后，
**所有连接的对端地址都以 `sockaddr_in6` 返回**（`family = 23`）。
IPv4 客户端在这种 socket 上表现为 `::ffff:a.b.c.d` 映射地址。

`std/net/addr` 的 `addr_text` 里有还原逻辑（`fam == 23` 且前 10 字节全零、
第 11-12 字节是 `0xFF 0xFF` → 取后 4 字节走 `ip4_format`），**v2.07 写的**：

```quelmara
if fam == 23 {
    let mut zero = 1
    let mut i = 4
    while i < 14 {
        if raw[i] != 0 { zero = 0 }
        i = i + 1
    }
    if zero == 1 && raw[14] == 255 && raw[15] == 255 {
        return ip4_format(str_slice(raw, 16, 20))
    }
    return ip6_format(str_slice(raw, 4, 20))
}
```

这段代码在此之前**只在 v4-only 的 socket 上跑过**（那时 `fam` 恒为 2，
`fam == 23` 这个分支根本没被走过）。v3.21 之后它突然成了主路径 ——
**但没有任何夹具覆盖它**。

如果它错了，症状是：所有 HTTP 服务的访问日志里，IPv4 客户端都显示成
`::ffff:127.0.0.1` 而不是 `127.0.0.1`。不会崩、不会报错，只是日志难看、
基于 IP 的限流/白名单全部失效。

## 改动：一个夹具，两层验证

`tests/t174_peer_ip.qma` —— **端到端**与**纯函数**两层，缺一不可：

### 层一：端到端（真实双栈连接）

用 `listen6`（`AF_INET6` + `IPV6_V6ONLY=0`）起一个双栈监听，
先让 IPv4 客户端连、再让 IPv6 客户端连，服务端各自 `peer_ip` / `peer_port`：

| 组 | 内容 | 判据 |
|---|---|---|
| `[1]` | IPv4 客户端 | `peer_ip == "127.0.0.1"`，且**不含 `::`**（映射未还原就会含） |
| `[2]` | IPv6 客户端 | `peer_ip == "::1"` |
| `[3]` | 端口 | 两个家族都 `> 0` 且 `!= 监听端口` |

### 层二：纯函数（`addr_text` 的四种形态）

直接构造 20 字节 raw 视图，把"还原逻辑"与"网络栈"解耦：

| 组 | 输入 | 期望 |
|---|---|---|
| `[4a]` | `fam=23` + `::ffff:127.0.0.1` | `"127.0.0.1"`（映射还原） |
| `[4b]` | `fam=23` + `::1` | `"::1"`（走 `ip6_format`） |
| `[4c]` | `fam=2` + `10.0.0.5` | `"10.0.0.5"`（v4 直通） |
| `[4d]` | `fam=23` + `2001:db8::1` | **不含 `:` 之外不能是点分** —— 不该误判成映射 |

**`[4d]` 是关键负向**：`2001:0db8:...` 前 10 字节恰好**不是**全零，
所以不会误判；但如果有人把判据从"前 10 字节全零"简化成"看最后 4 字节"，
`2001:db8::1` 就会变成 `0.0.0.1`。这条断言钉住它。

**两层为什么都要**：网络跑通不代表还原对（可能两个客户端恰好都走了
同一条路径）；还原对也不代表 `getpeername` 给的 `family` 对。
`[4]` 那组还顺带成了 `addr_text` 的**纯函数单元测试**，
不依赖任何 socket —— 将来跨平台移植（Linux 的 `AF_INET6` 是 10）
时，这一层能独立跑。

## 已知边界 / 遗留

- **只覆盖 Windows**。Linux 的 `AF_INET6` 是 **10**（Windows 是 23），
  而 `addr_text` 的判据是 `fam == 23` —— **Linux 上这段还原逻辑不会触发**。
  但 Linux 侧的 `tcp_peer_raw` 本身是 Windows-only（`@ffi` + `getpeername`），
  所以现在不存在"Linux 上跑双栈 + peer_ip"的场景。将来补 Linux 时，
  `addr_text` 必须同时认 10 与 23，**那时这个夹具的 `[4]` 组要扩一条
  `fam=10` 的用例**。
- **`peer_ip` 在 reactor 回调里没测**。本夹具用的是阻塞式 `listen6`，
  与 reactor 共享同一个双栈 socket 语义，但 reactor 的 `on_connect(fd)`
  回调里拿到的 fd 是否同样能 `peer_ip` —— **没验**。理论上一样
  （都是 accept 出来的 socket），但"理论上一样"不是证据。
- **`t174` 第一版借用了 `static_word` 的高位，那是越界写 —— 已改成堆块。**
  `static_word(i)` 的注释写"共 32 个"，但实现是 `i << 3` 直接加到静态区基址、
  **没有上限检查**（`qlm_native.py` 的 `static_word` 分支只有参数个数校验，
  `static_gid()` 也确实只分配 32 个字）。我第一版用 `static_word(120..123)`
  传字符串长度，那是**写到静态区之外**的未定义行为 —— 只是刚好没踩到别的数据。
  现在改成 `main` 里 `mem_alloc(48)` 一个结果块、指针传给服务端线程。

  **这暴露了一个真实隐患**：`static_word` 没有边界检查，而
  `02-language.md` 的内建表写着"共 32 个（0–31），手工分配、没有登记表"。
  越界不报错、静默踩内存 —— 这条已记进 `07-gaps.md`。
