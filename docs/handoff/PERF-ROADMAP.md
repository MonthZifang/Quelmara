# 性能优化交接文档（qlmc vs C 差距的完整地图）

- 日期：2026-11-06（终版 v2）
- 状态：截至 v4.59（HEAD 1f0dd56）—— v4.50 memcpy 8B、v4.51 ×8 折叠
  修复、v4.52 16B movdqu + labs 边界、v4.58 zero 16B、
  **v4.59 b87 反超 C（0.92x）**

## 目标与现实

用户目标：45 项以上基准跑赢 go/c（≤1.10x 或更好）。
现实：**1/19**。差距是结构性的，不是调参能解决的。

## 已确认的三大结构阻碍

### 1. vec 双重访存（最大头）

`v.get(i)` 生成的机器码：

| 指令 | 作用 | 条数 |
|---|---|---|
| `LOADD dst,[h+0]` | 读 data 指针 | 1 |
| `JCMPVLEN` 系列 | 越界检查 | 2（cmp+jcc） |
| `LOADX dst,[data+i*8]` | 读元素 | 1 |

C 是 `mov rax,[base+i*8]` 一条。**每元素多 4-5 条指令**。

唯一根治法 = vec 内联布局 `[len][cap][data...]`。
**5 次尝试全部失败**（详见 `docs/perf/ANALYSIS.md` 附录 1-4）。
最后一次 trace 定位到：stage-2 死在 `_new_fc` 的 FnCtx 构造
（23 个 vec 字段一次性创建），单独测试全部正常——自引用 bug。

### 2. 寄存器池已满

`N_VARREG = 7`（RBX/R12-R15/RSI/RDI，全部 callee-saved）。
x86-64 扣掉 RSP/RBP/RAX/RCX/RDX（发射器约定用）后只剩这 7 个。
**没有可加的空间**。要改必须动 ABI 或实现真正的图着色分配器。

### 3. 无循环向量化

qlmc 有 7 个 SSE 发射函数（`_sse_rr`/`_sse_mem` 等），但只用于 f64
标量运算。把标量循环转 SIMD 需要循环依赖分析 + 尾部处理，
是数周工程。

## 已落地且验证过的优化（保留）

| 项 | 版本 | 收益 | 验证 |
|---|---|---|---|
| `_mov_rr` 同寄存器不发 mov | v4.41 | 微小 | 自举全绿 |
| `_vec_check` 冷路径精简 | v4.42 | 二进制 -2.5% | 自举全绿 |
| ELF EXIT 走 syscall | v4.16 | 屏障减少 | 自举全绿 |
| `--heap-mb` 堆上限可配 | v4.44/45 | 功能 | 自举全绿 |
| `bounds_check` 开关 | v4.46 | **b18/b72/b23 各 -20%** | 自举全绿 |
| `--trace` 诊断通道 | v4.48 | 调试能力 | 自举全绿 |
| `_map_cap`/`_map_count` 语义分离 | v4.47 | 正确性 | 自举全绿 |

## bounds_check 的坑（重要！）

不是无脑全赢。逐基准实测：

* 循环内 **≥2 次** vec 访问 → **-20%**（b18/b72/b23）
* 循环内 **1 次** vec 访问 → 可能 **+28% 回退**（b70_lin_search）

原因：热循环整体移位带来的 i-cache/分支对齐变化，可能超过省下的
2 条指令。**任何全局开关都要逐基准验证。**

## vec 内联布局：如果想再试

**已修掉 6 个真 bug**（5 次尝试积累）：

1. `_vec_grow_body` 里重复 `_pin(fc, h)` → 迭代内副本，改不到调用方
2. `_lower_vecnew` 死变量 `hdr`
3. `_map_cap`：map 的 `[h+0]` 是 cap，vec 是 data —— **语义相反**
4. `_map_count`：map 的 `[h+8]` 是 count，vec 是 len
5. `_map_slot_of`/`_map_put`/`_map_del` 三处借用 `_vec_field`
6. `_vec_push` 的 `hp = _pin(fc, h)`（同 1，最隐蔽）

**最后一个未解**：stage-2 死在 FnCtx 构造。已排除：
22/23 个连续 vec、struct vec、嵌套 vec、大 vec —— 单测全过。
只在内联代码**自编自己**时出现。

**再做的话**：
1. 先写一个独立的小分配器测试（不经 12 分钟构建就能跑）
2. 或给 `_new_fc` 的 FnCtx 构造逐字段加 trace
3. RT_ALLOC 返回值检查：内联分配是 `16+n*stride`，查是否溢出 imm32

## 建议的下一步（按收益/风险排）

1. **逐基准开 bounds_check**（在 run.py 里按基准传参）——已验证，
   b18/b72/b23 可拿 -20%，零风险
2. `_vec_field` 的 off=0 返回 `h+16` 但**只对 stride==8 的 vec**——
   聚合 vec 先不动，缩小爆炸半径
3. SIMD：先做 `vec[int]` 的 memcpy/memset 向量化（`OP_MEMCPYN` 走 SSE），
   不需要循环分析

## 三大阻碍的最终定性（覆盖上文"建议下一步"）

### 1. vec 双重访存 → **前置需求 = 引用语义（语言特性）**

7 次尝试的完整定案（详见 v4.52 CHANGELOG 追加 4/5）：

* 内联布局本身正确（校验和/RT/基础 vec 全过）
* 卡点是 **grow 的句柄传播**：qlmc 的 vreg 模型是值拷贝，
  grow 换块后"同一 vec 的所有别名看到新块"无法表达
* 复现器：`tests/rt/pin_cross_grow.qma`（秒级，挂起即确认）
* 假设链完整：不 pin 挂 / 双写挂+破坏 / 干净版绿
* **重启条件：实现引用语义（&T / box）后重做内联**

### 2. labs 容量边界 → 已定案（self-host 内部现象）

`ctx.labs = vec.new(64)` 压边界，16 字节版多 2 个标签触发。
**变体 I（仅 +2 空标签即崩）实锤；变体 J（labs 128）修复**。
通用 vec.grow 全形态验证无坑（`grow_edge` 等四用例）——
用户代码无已知坑，规避已生效。机制最后一公里需 qlmc 内部
调试工具（候选 5 个全灭，见 v4.52 追加 2/3）。

### 3. SIMD → 维持原判（需循环向量化分析）

## vec 内联补丁与教训索引

* 布局/发射全套补丁：v4.52 CHANGELOG 追加 4 的重放步骤
* 必须同步的 7 处：`_vec_field` 内联、`JCMPVLEN disp=0`、
  `_lower_vecnew` 单块、push 不 pin（**错**——见下）、push len [h+0]、
  grow 双写（**也错**）、`map.len` 换 `_map_count`
* **grow 句柄传播是死结**：不 pin 挂、双写挂+破坏 min2——
  补丁层面无解，见上"前置需求"
* **补充（终版勘误）**：`_pin` 并不保证栈槽——`_new_var` 在
  `n < N_VARREG` 时仍分配寄存器。第 7 次双写失败的正确解读：
  hp/h 都可能在寄存器，"栈槽间接"方案需要新增 `_pin_slot`
  （强制 `vloc=-(u+1)`）。但多层别名每层都要间接+穿透=引用语义
  本质，终判不变；且 labs 已用 128 规避，_pin_slot 无当下收益。

## vec 内联第 9 次尝试（终）：方案矩阵穷尽，终判加固

第 8 次的 IR 分析定位到【优化器 DCE 删除 grow 回传 MOV】。
后续三个修复方案（均经构建+复现器实测）：

| 方案 | pin_cross_grow | min2 | 结论 |
|---|---|---|---|
| 8. 双 vreg MOV 回传 | 挂 | ✅ | DCE 删 MOV |
| 9a. STORE+ADDRV 回传 | **跑通（94 错）** | ✅ | 方向对，ADDR V imm 错 |
| 9b. 槽降级 + ADDR V（imm 修正） | 仍挂 | ❌ 99 | 降级引入新错 |

**9a 是重大进展**：复现器从"挂起"变"跑完"——STORE 回传方向正确，
余错在 ADDR V 立即数（-loc-1 语义）与 DCE/降级交互。

**终判（加固）**：qlmc 值语义 + 标量不可寻址，grow 跨作用域
句柄传播必须【引用类型】。方案空间穷尽（MOV×2 / STORE+ADDRV /
槽降级），9 次尝试无一通过全 RT。**重启条件不变：实现 &T 形参**。
实现时可直接复用 9a 的 STORE+ADDRV 回传（方向已验证），
只需修 ADDR V imm 与槽降级的 DCE 交互。

**附带收获**：`_pin` 不保证栈槽（终版勘误的实证）、
ADDR V imm 语义 = `-loc-1`、DCE 判死依据 use 计数——
三条编译器内部事实，均为后续工作的地图。

# 函数内联：v4.117 已落地第一批，v4.118 通用内联候选

> 数字一律见 `../06-status.md` §7 与 `../versions/v4.117/CHANGELOG.md`，此处只写方案。

## 为什么是内联

剩余最大比值项的根因是**没有函数内联 / 跨函数常量传播（IPA-CP）**：

- b36_call：`add3(a,b,c){return a+b+c}` 小叶子，C 内联成 `acc+=i+1`。
  **v4.117 已内联，−78.5%，跌出最大比值榜。**
- b57_pow_mod：`pow_mod(base,exp,mod)` 的 `mod` 是形参，`% mod` 走 idiv；
  C 内联后把实参常量 1000003 传播进去，`%` 变魔数乘。**需通用内联（含循环），未做。**

## v4.117 已验证的正确姿势（AST 层，非 IR 拼接）

原以为要"预 lower 候选 + IR 拼接 + 跨线程共享表"，实际**在 `_lower_expr` 的
E_CALL 分支直接 AST 层内联**更简单且首次尝试即过不动点：

- 判据全在 AST（单返回纯表达式、形参全 int、E_VAR 全为形参、节点 ≤25），
  **不依赖 vreg 编号** → 不动点天然安全。
- 复用现成 `_bind_push`/`_bind_pop` 把形参名绑到实参 vreg（`_try_var` 先查 bind 栈），
  直接 `_lower_expr` 返回表达式，不发 OP_CALL。**零新增状态。**
- 关键：被调表达式无调用 → 天然叶子/无递归/无环，无需返回拦截、无需标签重命名。

## v4.118 通用内联（含循环/局部变量）的设计难点（已勘察）

要内联 b57 的 pow_mod（含 while + 局部 result/b/e + 末尾单 return），需解决：

1. **返回拦截**：`_lower_stmt` 的 S_RETURN 分支很复杂（聚合 sret、defer 先求值
   再 pin、v4.61 无 defer 不 pin）。内联时 RET 不能返回调用方，要改成
   `MOV 结果vreg + JMP 内联出口标签`。**建议给 FnCtx 加内联上下文**
   （inline_ret / inline_exit），S_RETURN 命中时走拦截分支；lower 完发出口标签。
   务必复刻 defer/pin 语义，否则静默错编。
2. **变量名碰撞**：被调局部名（result/b/e）若与调用方**活跃变量**同名，
   `_try_var` 从 vmap 尾查会命中被调局部 → 调用方读错。保守做法：
   **内联前检查被调所有形参/局部名是否与调用方 vmap/bind 里的名字冲突，冲突即跳过**
   （b57 的 main 无 result/b/e，恰好不冲突，可内联）。彻底做法是重命名，但名字 id
   是 names 表下标，重命名要造新名字，复杂——先用"冲突即跳过"。
3. **叶子限制**：第一批通用内联仍只内联**体内无调用**的函数（pow_mod 满足），
   避免嵌套内联爆炸；递归/含调用者不内联。
4. **帧压**：被调局部并进调用方，警惕 416 槽（坑表 #1）；节点/局部数阈值要小。
5. **不动点**：判据仍是 AST 纯函数；"冲突即跳过"依赖调用方 vmap 内容，
   而 vmap 内容由降级顺序决定、是确定的 → 仍不动点安全，但**必须差分验证**。

## 验证门槛（防第 N 次回退）

差分夹具（内联 vs 非内联结果一致，含碰撞/defer/循环/多 return）→ 种子引导不动点
→ 42/42 selfhost → 76/76 跨语言校验 + 交替复测 → 冷缓存严格自举。
**任何一步不过就回退**，不把半成品内联留在树上。参照 v4.116 四个坑，内联只会更多。
